あなたはこのプロジェクトの自動メモリシステムの週次メンテナンス担当として起動された。
対象ディレクトリ: {{MEMORY_DIR}}
（このディレクトリ内の `MEMORY.md` がインデックス、サブフォルダ(01_〜40_)内の `*.md` が個々のメモリ本体。統合時もフォルダ構成は維持し、`work_status/` と `_backups/` は対象外）

## 目的
このメモリシステムに溜まった学び(project/feedback/user/reference memory)を棚卸しし、
「読み込むたびに新鮮で使えるもの」に保つ。今日の日付を基準に、以下を行うこと。

## 手順
1. **必ず最初にバックアップを取る**: `{{MEMORY_DIR}}/_backups/<今日の日付YYYYMMDD>/` を作成し、
   `_backups` 自身を除く `{{MEMORY_DIR}}` 直下の全ファイルをコピーする(Bashツールでcp -R)。
   このバックアップがあるので、以降の変更は多少大胆でも安全に取り消せる。
2. `MEMORY.md` と、そこからリンクされている全メモリファイルを読む。
3. **ファイルの削除は「重複の統合」の場合に限る。老朽化・完了済みを理由にした削除は一切行わないこと**(2026-08-23にユーザーから明示された制約)。
   内容が古そう・もう使わなそうに見えても、単独では削除しない。削除してよいのは手順4の「重複統合の結果、内容が別ファイルに完全に吸収された元ファイル」だけ。
4. 以下の観点で「重複」を探す:
   - 同じ事実・同じ設定情報が複数ファイルにほぼそのまま書かれている(表現が違うだけで実質同一内容、を含む)
   - → 1つに統合し、他のメモリからは `[[name]]` でリンクする形にする。統合時は情報を欠落させない(和集合を取る)。
   - 統合後、内容が完全に統合先に吸収された元の重複ファイルは削除してよい(これが今回唯一許可された削除理由)。
5. 以下の観点で「パターン」を探す:
   - 似たテーマのfeedbackメモリが複数あり、より一般化した1つのルールにまとめられる場合、統合した新しいfeedbackメモリを作る
   - ただし手順3の制約により、元の個別メモリが完全な重複(手順4)でない限り削除しないこと。新しい統合メモリを作り、元のメモリ側から `[[統合後のname]]` でリンクを追加するに留める(元ファイルは残す)
   - project memoryについては安易に一般化しない(プロジェクト固有の事実は事実のまま残す)
6. 変更を適用する:
   - 統合・一般化したメモリは既存のfrontmatter形式(name/description/metadata.type)を踏襲する
   - feedback/projectタイプは「ルール・事実」→「**Why:**」→「**How to apply:**」の構造を踏襲する
   - `MEMORY.md` のインデックスも変更に合わせて更新する(1行、150字程度、リンク切れなし、200行以内)。削除していないファイルのインデックス行は残すこと。
7. `{{MEMORY_DIR}}/work_status/` に、今日の日付でこの週次レビューの実施記録を追記する形で残す
   (何を統合したか・何を削除したか・何を残したかの要約。ファイル名は `memory_weekly_review_<今日の日付>.md`)。
   既存のwork_statusファイルは削除しないこと。
8. `{{MEMORY_DIR}}` の外(CLAUDE.md、プロジェクトの他のファイルなど)には一切手を触れないこと。

## 出力
最後に、変更点の要約を2〜5行程度でテキスト出力すること(このテキストがそのままTeams通知に使われる)。
変更が何もなければ「変更なし」とだけ出力すること。

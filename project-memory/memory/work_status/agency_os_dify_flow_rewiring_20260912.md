## 実施した配線変更(中村さん作業、Claudeは手順ガイドのみ)
1. Difyの「テキスト抽出」ノード(このバージョンでの「ドキュメント抽出」相当の名称)を追加。
   入力変数は`ユーザー入力/files`(Array[File])に正しくバインド、docx含む主要ファイル形式に対応済み。
2. **問題発覚1**: LLMノードの「コンテキスト」欄はナレッジ検索結果専用の型(Array[Object])で、
   テキスト抽出の`text`(Array[String])を直接入れると知識検索の結果が消えることが判明。
   → 対応: コンテキスト欄は知識検索のままにし、SYSTEM prompt本文中に`{{#テキスト抽出.text#}}`を
   ラベル付きで変数挿入する方式に変更(実施済み)。
3. **問題発覚2(中村さん自身の気づき)**: テキスト抽出ノードが知識検索ノードより後に配置されており、
   知識検索の「クエリテキスト」が`sys.query`(ユーザーの短い入力文、例:「これです」)のみを見ていて、
   添付資料の内容が検索クエリに一切反映されていなかった。
   → 対応: 知識検索の「クエリテキスト」欄は変数を1つしか受け付けない仕様のため、間に
   「テンプレート」ノード(Jinja2)を追加。入力変数`query`(sys.query)と`doc_text`(テキスト抽出.text)を
   結合する以下のコードを設定:
   ```jinja
   {{ query }}

   {% if doc_text %}
   添付資料の内容:
   {% for t in doc_text %}
   {{ t }}
   {% endfor %}
   {% endif %}
   ```
   このテンプレート出力(`output`)を知識検索のクエリテキストに接続。ファイル未添付時は
   queryのみのシンプルなクエリになり、添付時のみ本文も加わる設計。
4. 中村さんから「LLMに入るのは知識検索の出力だけでなく添付資料の情報も要るのでは」との質問があり、
   Claudeが役割分担を説明: テンプレート→知識検索は「検索クエリを作る」ため、テキスト抽出→LLM
   プロンプト直接挿入は「LLMが本文を読んで回答する」ため、の2経路が両方必要(片方だけでは不十分)。

## 現状のフロー(想定、中村さん報告ベース、スクリーンショット未確認)
`スタート → テンプレート(query+doc_text結合) → 知識検索(結合クエリで検索) → LLM(コンテキスト=知識検索結果+プロンプト内にテキスト抽出.text) → 回答`
テキスト抽出ノード自体は知識検索より前段(テンプレートの入力として)に必要なため、実際には
`スタート → テキスト抽出 → テンプレート → 知識検索 → LLM → 回答`という並びになっているはず
(中村さんの「作業完了しました」報告のみで、最終形のスクリーンショットは未確認)。

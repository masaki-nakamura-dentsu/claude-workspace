## 2026-08-06 (sixth pass): root-caused why direct-edits to the Teams file stopped appearing — AutoSave upload-lock conflict

After the slides-14/15 rebuild, the user reported the change wasn't visible — not just in the desktop app, but also in the **browser/Teams preview** (checked explicitly at the user's request), ruling out simple app-side caching. Root-caused via OneDrive's own sync diagnostics rather than guessing further:

- `~/Library/Logs/OneDrive/Business1/SyncDiagnostics.log` showed `numFileFailedUploads = 8`, `failedBytesUploadedTotal = 122474626`, `successfulBytesUploadedTotal = 0` for the sync session covering this work.
- The raw `SyncEngine-*.odl` trace logs (readable via `strings <file>.odl`) contained repeated `X-ClientErrorCode:UploadSessionInProgress` server responses, plus a JSON conflict record with mismatched `Cloud`/`Database`/`Disk` hashes for the file.

**Mechanism**: with PowerPoint's AutoSave ON and the file open, PowerPoint itself holds an active co-authoring **upload session** against the SharePoint-backed cloud copy. When OneDrive's background sync engine then tries to upload *my* direct filesystem edits to the same cloud item, the server rejects it with `UploadSessionInProgress` — the upload fails silently, every time, for as long as PowerPoint has the file open with AutoSave. The local file on disk was correctly edited on every pass this session (verified repeatedly via python-pptx/qlmanage) — it simply never reached the cloud, so nothing the user viewed (desktop app reconnect, browser, Teams preview) ever showed it. Quitting and relaunching PowerPoint didn't fix it either, because either the failed upload doesn't get retried before the app re-locks the session on reopen, or the conflict itself needs resolving, not just a fresh open.

**This is a general Microsoft 365 architecture limitation, not fixable from the terminal** — direct filesystem edits to an AutoSave-enabled OneDrive/SharePoint file cannot reliably reach the cloud while any Office desktop app has that same file open with AutoSave on, regardless of how carefully the edit script itself re-checks MD5/mtime before writing (that check only guards against a different class of problem — a second *local* writer — not this upload-lock conflict).

**Recovery for this instance**: saved the fully-fixed content (which was correct locally in `_20260805.pptx` the whole time) as a new file, `進撃の巨人×TOYOTA_Hyryder特別仕様車_デザイン提案_20260806_01.pptx`, for the user to manually merge/replace in the co-authored file themselves.

**Standing workflow decided with the user going forward for this specific Teams file**: before any future direct edit to `_20260805.pptx` (or whichever file is later the live canonical one in that Teams folder), explicitly ask the user to **fully quit PowerPoint** (not just close the window) and confirm before editing — then it's safe to edit in place as before. Do not resume the "edit live even if open" assumption from earlier in the day without this explicit close-first step. If the user can't guarantee PowerPoint is closed (e.g. colleague might have it open), default back to the new-dated-file-for-manual-merge pattern instead. General version of this lesson saved separately as [[feedback_autosave_cloud_file_direct_edit]] since it applies to any AutoSave-enabled OneDrive/SharePoint file, not just this project.

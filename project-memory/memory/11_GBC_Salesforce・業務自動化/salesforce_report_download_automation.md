Built and verified end-to-end 2026-08-03, in direct response to the user asking whether Claude could open Salesforce and do the download itself for [[gbc_gyokyo_mitooshi_report_workflow]]'s monthly report.

## Why this exists
The GBC weekly report (Salesforce report ID `00O7F00000AxREaUAN`, "GBCすべての週報：事業企画局提出用(過去30日)") is the raw data source for the monthly 業況見通し report. Manually downloading it every month via the browser was the last fully-manual step in that workflow.

## Scripts (all in `~/SalesforceExport/`)
- `download_step1_export.py` — launches Chrome with `--remote-debugging-port=9224` and a dedicated persistent profile (`~/SalesforceExport/browser_profile/`), navigates to the report URL, clicks through Export → confirm (defaults: フォーマット済みレポート / Excel形式 .xlsx — these already match the historical file format, no need to change). If Salesforce doesn't demand identity verification this run, the file downloads immediately and is saved straight into `今後の業況見通し/<YYYYMM>/` (auto-created, current month by `datetime.now()`). If verification IS required, it stops and tells the user to check email.
- `download_step2_enter_code.py <code>` — enters the 6-digit code into the still-open verification tab, captures the resulting download, saves to the same month folder. Run this after the user reports the code from their email.
- Diagnostic/exploration scripts also left in the folder (`dump_frames.py`, `dump_buttons.py`, `screenshot.py`, `click_export.py`/`click_export2.py`, `confirm_export2.py`, `find_export_btn.py`, `screenshot_verify.py`, `login_and_open_report.py`, `inspect_export_ui.py`) — not needed for normal use, kept only in case the UI changes and the export flow needs re-discovering.

## Key technical findings (Salesforce Lightning report UI, 2026-08 org config)
- **Session persistence works**: reusing the same `browser_profile` dir across separate Chrome launches (even fully separate processes, not just Playwright-managed ones) carries the dentsu SSO session via silent SAML re-auth — no interactive login needed on repeat runs, exactly like [[continuous_data_capture_setup]]'s Teams daemon pattern.
- **The report toolbar (編集 button, "..." export menu) lives inside an iframe**, not the top-level page: `https://dgx.lightning.force.com/reports/lightningReportApp.app?reportId=...` (frame name matching `lightningReportApp.app`). `page.get_by_role()` on the outer page won't find it — must locate the frame via `page.frames` first.
- The "..." dropdown trigger's accessible name is **`追加アクション - 編集`** (not something obviously named "more" or "export"). Click it, then `get_by_text("エクスポート", exact=True)` inside the same frame.
- The resulting **export-options modal (フォーマット済みレポート/詳細のみ + 形式 dropdown) is portal-rendered into the OUTER page**, not the iframe, even though it was triggered from inside the iframe. The final blue "エクスポート" confirm button must be located via `page.get_by_role(...)` on the top-level page, not the frame.
- Defaults (フォーマット済みレポート, Excel形式 .xlsx) already match what's needed — no changes required in the dialog.

## 2026-09-03: live end-to-end test succeeded, one implementation bug found and fixed
Ran a real test download via the shared browser (port 9226) against the same report (`00O7F00000AxREaUAN`). Found that clicking "別の検証方法を使用してください" via Playwright's `.click()` did NOT navigate (the link is `href="javascript:srcUp('/_ui/identity/verification/policy/VerificationStartUi/e?...')"`- a javascript: URI, and Playwright's click dispatch doesn't trigger the browser's native javascript: href execution the way a real user click does). Fixed by reading the link's `href` attribute, URL-decoding it, regex-extracting the `srcUp('...')` argument (a relative path), and `page.goto()`-ing directly to `origin + path`. This lands on a "検証方法を選択してください" screen listing 4 options: 仮の確認コード / パスキー(おすすめ) / **Salesforce Authenticator** (exact text match works) / ワンタイムパスワードアプリケーション. Selecting Salesforce Authenticator navigates to `ToopherVerificationFinishUi` ("モバイルデバイスを確認... [承認]または[拒否]をタップしてください") and a push notification does arrive on the user's iPhone. The user approved it, and `page.expect_download(timeout=300000)` correctly fired and captured the download once approved - confirming the whole Authenticator-approval flow works end to end. This fix was applied to both `download_all_reports.py`'s `select_salesforce_authenticator()` and `download_step1_export.py`'s inline equivalent (import `re`, `urllib.parse`, `urlparse` added to both files).

Would need the user to actually register a passkey through that link first; not attempted this session (scope was "get the happy path working," not "eliminate the verification step entirely").

**2026-08-31 update — step 1 now fails on d14461 if [[sf_reports_qbr_download_automation]]'s shared bot browser is already running.** Both scripts point `PROFILE_DIR`/`browser_profile` at the same directory (`~/SalesforceExport/browser_profile`), but this script hardcodes its own `DEBUG_PORT=9224` while the QBR pipeline's shared browser runs on port 9226. When the shared browser (9226) is already up, `launch_chrome()`'s `open -na "Google Chrome" --args --remote-debugging-port=9224 ...` doesn't start a genuinely new debug-port process — macOS just opens a new tab in the *existing* Chrome instance (still only listening on 9226), so the script's own `connect_over_cdp(...9224)` call fails with `ECONNREFUSED`. **Practical fix used successfully 2026-08-31**: skip this script entirely and instead write a small one-off script that imports `download_one_report` from `~/SalesforceExport/reports_pipeline/download_all_reports.py`, connects to port 9226 (the shared browser), and calls it with `{"id": "00O7F00000AxREaUAN", "folder": "<YYYYMM>"}` (patching that module's `TARGET_ROOT` to the 業況見通し folder first). Worked immediately, no verification code needed that run. **Next time**: check `lsof -i :9224` / `lsof -i :9226` first — if 9226 (shared browser) is already running, go straight to the reports_pipeline-based workaround rather than trying `download_step1_export.py` first.

## Related: monthly reminder
First tried a Power Automate flow (recurrence + hand-built weekday/day-of-month condition expression + self-email) since Claude Code has no durable local push-notification mechanism. **Superseded same day**: the user pointed out Outlook's own recurrence UI already has a built-in "the first Weekday of every 1 month(s)" monthly-recurrence option — no condition-expression logic needed at all. Decided this is simpler and sufficient; the Power Automate setup doc (`.../今後の業況見通し/POWER_AUTOMATE_SETUP_REMINDER.md`) was deleted, and the user should instead create a plain recurring Outlook calendar event with that built-in recurrence pattern (Claude cannot create Outlook calendar events directly — no write access to the user's calendar — so this is a manual one-time setup step for the user).

**Also clarified for the user, 2026-08-03**: nothing (Power Automate or otherwise) can directly trigger Claude Code to act — there is no external-system-to-Claude-Code webhook/wake mechanism on this Mac. Claude only runs when a session is actively invoked by the user, or via a `CronCreate`/`/loop` schedule that only persists within an already-running session (max 7 days, dies with the session/reboot) — nothing can "wake" a new session from outside. Combined with the fact that the export's emailed verification code needs a human to read it regardless, full end-to-end automation with zero human involvement isn't achievable no matter the notification channel. The realistic flow stays: calendar reminder → user opens a Claude Code session and gives the trigger phrase below → Claude runs the two-step script above, asking the user only for the emailed code.

**Exact trigger phrase (set 2026-08-03)**: the user will say **「業況見通し用のSalesforceをダウンロードして」**, not the generic "Salesforceダウンロードして" — he expects to ask Claude to download other Salesforce reports for unrelated purposes in the future, so the phrase must specifically name 業況見通し to disambiguate which report/script this refers to. Recognize this specific phrase as the trigger for this exact workflow (report ID `00O7F00000AxREaUAN`, the two scripts in `~/SalesforceExport/`); don't assume a bare "Salesforceダウンロードして" always means this task.

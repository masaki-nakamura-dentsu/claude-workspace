ユーザー指示(2026-09-04): [[overseas_staff_list_sync_automation]]で自動取得している月次スナップショットから
[[overseas_staff_assignment_history]]の「駐在履歴」xlsx(日付付きファイル名、粗い粒度)を再生成しているのに加えて、
`~/Library/CloudStorage/OneDrive-電通/Global Q - 駐在員リスト/海外駐在員_異動履歴まとめ.xlsx`
(固定ファイル名、ユーザーが「こちらの方が見やすい」と指定)も同時に自動更新してほしいとの依頼。

## 対象ファイルの構造(解析結果)
- シート「タイムライン」: 列A-D=氏名/国・都市/開始年月/終了年月、列E以降=2019年9月〜最新月の月次列(1列=1か月)。
  地域ごとに見出し行(Americas=青FF2E75B6・EMEA=緑FF375623・APAC=オレンジFF7F6000、白太字)でグループ化し、
  各行内で在籍期間に該当する月だけオレンジ(FFF4B942)で塗りつぶすガントチャート形式。氏名/国・都市/開始/終了の
  4列は薄青(FFD6E4F7)で塗る。年ヘッダー行(行1、濃紺FF1F3864)と月番号ヘッダー行(行2、濃灰FF404040)。
  国→地域の対応表(21か国、Unknown国が出た場合は要マッピング追加): Americas=アメリカ/カナダ/ブラジル、
  EMEA=イギリス/フランス/ポーランド/ロシア、APAC=それ以外(インド/インドネシア/オーストラリア/シンガポール/
  タイ/タイランド/ニュージーランド/フィリピン/ベトナム/ミャンマー/マレーシア/中国/台湾/韓国)。
- シート「異動履歴」: 氏名/赴任先(日本語)/国・都市(1列に結合)/所属/開始年月/終了年月。国・都市やLA/NY等の
  表記ゆれは正規化されていない(生データのまま)。

## 実装(新規スクリプト `~/OverseasStaffList/build_timeline_workbook.py`)
[[overseas_staff_assignment_history]]の`build_assignment_history.py`が持つ`collect_unique_files`/
`parse_snapshot_date`等を再利用しつつ、正規化なし+所属列も取得する専用の`parse_file_raw`を実装。

**セグメント分割ルールが既存の駐在履歴スクリプトと異なる(重要)**: 既存スクリプトは(国,都市)が変わるまでを
1セグメントとするが、このファイルは元々もっと細かく、(国,都市,赴任先(日本語))が変わった時点でも新セグメントに
分割されている(実データで検証済み)。所属の変化だけでは分割しない(所属はセグメント内で最後に確認できた値を
参考情報として保持するのみ)。**ハマった点**: 赴任先(日本語)列は年代によって存在しない/空欄になる月があり、
単純に「前月と違えばセグメントを切る」ロジックだと欠落月でNoneに変わったせいで誤って分割されてしまう
(実測で1126→792→540と、判定ロジックを直すたびにセグメント数が減った)。対策として「赴任先が空の月は直前の
既知の値を引き継いだとみなす」ロジックにしたところ、既存ファイルの実データ(565行)にほぼ一致する540行になった
(残差は赴任先名の全角/半角等の表記ゆれによるものと推測、実用上問題ない範囲と判断)。
赴任先名の比較にはNFKC正規化+空白除去した比較用キーを使うが、**表示上は生の文字列をそのまま使う**
(NFKC正規化を表示にも使うと今度は全角カッコが半角に化けるなど別の表記崩れが起きるため、表示は正規化しない
という判断をした — 今後同種の「表記ゆれ吸収」処理をする際、比較用キーと表示用値は別に持つべきという教訓)。

## 運用
- `~/OverseasStaffList/weekly_update.py` に3番目のステップとして追加(sync→駐在履歴再生成→このタイムライン
  ワークブック再生成、の順)。既存の週次launchd(毎週月曜7:30)でそのまま自動実行される。
- 出力ファイルは**日付なしの固定ファイル名で毎回上書き**する設計(既存の`overseas_staff_assignment_history_<日付>.xlsx`
  とは異なり、ユーザーが「このファイル自体を」見やすい参照先として使い続けたいと明言したため)。
  グローバルルールの「既存ファイルは上書きせず新規保存」原則とは一見矛盾するが、今回はユーザーが同じファイル名を
  名指しして「これを自動更新して」と明示指示したケースであり、かつ保存先がSharePoint同期フォルダで
  バージョン履歴が自動的に効くため、上書き運用とした。
- 2026-09-04に手動で1回実行し、即時反映済み。次回自動反映は次の月曜7:30。
- Teams通知は既存の`common.send_teams`をそのまま利用(成功/失敗どちらも通知)。

## 2026-09-04追記: 年ヘッダーのバグ修正
初版は「9月にも年の数字が入ってしまう」バグがあった。原因: 行1の年ラベル表示条件が
`mo.month == months[0].month(=9) or mo.month == 1` になっており、初回列(2019年9月)用の
特例のつもりが「毎年9月」にもマッチしてしまっていた。ユーザー指摘を受け`mo.month == 1`のみに修正
(2019年は範囲内に1月が無いため年ラベル自体が出ない仕様に変更、ユーザーの「1月の上にのみ表示」という
指示どおり)。また月列の幅が狭く(width=3)年の数字("2020"等)が収まらず見えない問題があったため、
年ラベルのセルだけ`Alignment(horizontal="left")`にして右隣の空セルへオーバーフロー表示されるようにした
(月番号セルは中央揃えのまま)。中央揃えのまま幅を超える文字列を置くとExcelは左右均等にはみ出そうとして
うまく表示されないことがあるため、オーバーフローさせたいラベルは左詰め(または右詰め)にするのが定石。

**続けて「##のように表示される」との指摘**: 原因は年の値を`mo.year`(int)のまま入れていたこと。
Excelは数値セルが列幅に収まらない場合`###`表示にするだけで、文字列と違って隣の空セルへは
オーバーフローしない(オーバーフローは文字列セル限定の挙動)。`value=str(mo.year)`に変更して解決。
**今後の教訓**: 狭い列に収まらない前提でオーバーフロー表示を狙うラベルは、必ず文字列型で入れること
(数値・日付型はオーバーフローしない)。

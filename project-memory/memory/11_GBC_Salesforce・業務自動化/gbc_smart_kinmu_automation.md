## Background

Every month, 小松瞳さん(HRM, hitomi.komatsu@dentsu.co.jp)sends 9 per-department Excel files (raw HRM export) to the user, who has been manually running an old `SK Format_v3.py` (just `pd.concat`s the 9 files into `GBC SK Combined_YYYY_MM.xlsx`) and then hand-pasting columns A:M into the previous month's `YYYYMM_GBC_to cleansed.xlsx` (per `_勤務登録分析マニュアル.docx` in the `GBC戦略企画部_Smart-KINMU` OneDrive folder). This hand process was error-prone and the goal was to automate it end-to-end.

## Root cause found (the recurring "ずれ" bug)

The raw department Excel files are apparently derived from a CSV export at some point upstream (by 小松さん's side, not visible to us). When a free-text field — almost always 作業詳細(column C), rarely JUセル(column A) — contains a literal comma, that comma caused the field to split into two physical Excel cells during that CSV→Excel step, shifting every column after the split point one to the right for that row. The classic recurring case: 山本高之さんの「AP1,2部部会オブザーブ」→ splits into `C='AP1'`, `D='2部部会オブザーブ'`, pushing 作業時間/ユニットNO/負担組織/etc. one column right, and the 作業時間 value ends up lost when someone (the user, manually) tries to fix it without realizing the shift extends past just the two split cells.

Confirmed via a 7-month scan (2601–2607): this shift happens roughly 1–2×/month, always shift-by-1 (never seen shift-by-2+), and the split point is either C (作業詳細, the vast majority of cases — 山本さん's is a literal monthly recurrence since he always writes "AP1,2部" that way) or occasionally A (JUセル containing a client name with "Co., Ltd." — only seen Jan–Mar 2026 for one specific Taiwan client, not recurring since).

**Confirmed the existing hand-fixed 2607 file actually has this bug uncorrected**: 山本さん's row had 作業詳細 merged back correctly (someone had manually joined the two cells) but 作業時間 was left blank (`None`) instead of being shifted back into place — a real ~1.5h data-integrity loss in production data that had gone unnoticed.

## make_gbc_cleansed.py — fixed pipeline, replaces both "Combined" and manual-paste steps

Location: `GBC戦略企画部_Smart-KINMU/make_gbc_cleansed.py` (copy into each new month's folder before running, same convention as the old `SK Format_v3.py`).

- Reads the 9 raw department files directly (no intermediate "Combined" file needed — the user explicitly said Combined isn't the goal, cleansed is).
- Detects the shift by looking for the first time-like value (`datetime.time`/`timedelta`/`datetime`) starting from where 作業時間(col D, 0-indexed 3) should be. If it's not there, walks forward to find it, and the gap tells you the shift amount.
- Distinguishes *where* the split happened (C/作業詳細 vs A/JUセル) by checking whether the physical B-column value is a known 作業領域 value (built from a vocabulary collected from this month's own unshifted rows — no hardcoded list, adapts automatically). If it's a known 作業領域, the split was in C; otherwise assumes it was in A. Rows that can't be classified confidently are left alone and flagged `review` rather than guessed at.
- **Year/month is read from each raw file's filename** (`_YYYY年M月.xlsx`), never from "today − 1 month" — this was an explicit fix requested by the user because Komatsu-san's delivery timing is unreliable (sometimes late), so trusting the run date would silently mis-date the output in exactly those late-delivery months. Majority-vote across the 9 files with a warning if any disagree.
- Copies the previous month's `*_GBC_to cleansed*.xlsx` (auto-found in the sibling YYMM folder, latest-mtime if multiple like a `_更新` variant exist) into the new month's file, clears only A:M in the `Format` sheet (rows 12–1500 — this range already has N:W formulas pre-filled all the way to row 1500 from however the template was originally built, so nothing needs to be re-extended), writes the new fixed data into A:M, sets `fullCalcOnLoad` so Excel recalculates on open.
- **Verified end-to-end against the real, already-completed 2607 file**: 816/816 data rows match exactly (order-independent; the only surface differences were row order — alphabetical processing vs whatever order the old glob-based script used — and int-vs-float string reprs of numeric fields, both cosmetic). The one real difference: this script correctly preserves 山本さん's 01:30:00 that the hand-fixed real file had lost.
- **Known limitation, told to the user**: openpyxl re-serializes the whole workbook on save, and a load-time warning already shows the file has an unsupported data-validation extension somewhere — that specific Excel feature (probably a dropdown list validation on some cell) will likely be dropped on save. Doesn't affect the Format sheet's actual data. Told the user to eyeball-check the output once before relying on it blindly, especially the first month or two.

## _infer_missing_juekisha.py — automating HRM's steps 5–7 (受益者テーブル更新)

User asked to also automate the manual/HRM side (steps 5–7: W列チェック・受益者テーブル更新・次の担当者送付), specifically: infer missing 事業区分/受益者区分 for rows that fail (W列=0) from past registration data, auto-fill, and color the affected cells so HRM reviews rather than researches from scratch.

**Rejected the user's first-suggested matching key (作業領域 prefix like OO/IO/OI) after empirically testing it** — validated via a proper train/test split (2601–2605 as training, 2606's 545 already-confirmed W=1 rows as ground truth): 作業領域-prefix-only majority vote scored only 73–83% accuracy (found by testing, e.g., "選択しない" splits ~30/28/26% across three different categories — no reliable majority). Found and proposed a better alternative instead, presented transparently as "your idea underperforms, here's what worked better, want to proceed with this instead":
- Tier 1: exact 作業詳細 text match against historical W=1 rows (single unambiguous candidate only) → 24.6% coverage / 95.5% accuracy
- Tier 2 (fallback when Tier 1 has no match): (社員名, 負担組織) combination, majority vote, gated at ≥3 historical occurrences and ≥85% agreement → +17pp coverage, 95.9% accuracy standalone
- Combined: **41.5% coverage / 95.1% accuracy** on the 2606 validation set; **11.5% coverage (32/278 rows)** when applied to the real, currently-unresolved 2607 backlog (lower because the "hard" unresolved rows are, almost by definition, less likely to have appeared before — expected to improve automatically each month as more resolved months accumulate as training data).

**Scope of what actually gets fixed**: rather than trying to replicate the full S→T→U→V→W formula chain's error propagation in Python (decoded all five formulas from the live workbook; genuinely intricate — COUNTIF/IF chains that may or may not propagate Excel errors depending on exact inputs), narrowed the fix to the single, well-defined root cause the manual itself names for this step: **ユニットNO not yet present in Juekisha Table** (excluding rows whose 負担組織 is a "GBC総掛" department, which don't need Juekisha Table at all per the S/U formulas' own special-case branch). For each such unit, if Tier 1/2 infers a value: appends a new Juekisha Table row (B:G core fields + I:U raw A:M audit-trail copy, matching the sheet's existing hand-authored convention exactly, including that C/D/E are `=N{row}`/`=O{row}`/`=M{row}` same-row formula references, not literal values), ensures the value exists in `Code_210714update`'s D/F valid-code lists (appends to first blank cell in the existing hardcoded COUNTIF ranges D4:D42/F4:F51 if missing — found this triggers more often than expected, ~2 per month, not the "near-zero" originally predicted, because Code_210714update's list and Juekisha Table's own F column are two independently-valid sources per the R-column formula, so a value can be W=1-valid via Juekisha Table alone without ever having been added to Code_210714update), and appends a matching row to `Predictions (Update)` using the exact same combined-key formula the sheet's own T/V columns already use (`負担組織+JUセル+作業領域+社員名+扱組織+作業詳細+得意先`, no separators). Colors the Format sheet's S and U cells (light green, `FFC6EFCE`) on every row sharing that unit, not just the first occurrence.

**Verified end-to-end in an isolated scratch sandbox** (symlinked real 2601–2606 as read-only training data, a fresh scratch-regenerated 2607-equivalent as the mutable target — never touched the real production 2607 file): first hit a severe performance bug (`ws.cell()` random access in openpyxl `read_only` mode is pathologically slow — a run that should take seconds hung for 10+ minutes across 6 files; fixed by switching to `ws.iter_rows(values_only=True)` sequential access, after which the same run took ~5 seconds). After the fix: 16 distinct missing units found (31 rows), 3 successfully inferred and written; confirmed idempotent (re-running afterward correctly found only 13 remaining missing units and inferred 0 new, no duplicates); confirmed `Code_210714update` only gained the 2 genuinely-missing entries, not spurious ones (row-by-row diffed against the untouched original).

**Found a pre-existing template quirk while validating, not something introduced by this work**: the Format sheet's `S` column VLOOKUP has a hardcoded range ending at `Juekisha Table!G477`, while the `U` column's equivalent VLOOKUP ends at `F480` — a 3-row inconsistency baked into the original template, unrelated to anything built this session. A newly-appended Juekisha Table row (e.g. row 478) resolves correctly for `U` but will show a genuine `#N/A` for `S` specifically, forever, because that formula literally cannot see rows past 477. This turned out to be harmless in practice for our purposes — `T` (the AC/"final" counterpart of `S`) still resolves correctly via the `Predictions (Update)` XLOOKUP fallback (which is exactly why the user's ask to update Predictions too, not just Juekisha Table, mattered), and the ultimate `W` pass/fail check came back `1` (correct) even with `S` showing `#N/A`. Not fixed (would mean rewriting a formula across 1500 rows in someone else's business-critical template, out of scope for this task) — just documented here and worth mentioning to the user if `S` column `#N/A`s on newly-inferred rows ever draw a question.

## Critical bug found and fixed: openpyxl silently corrupts the ENTIRE workbook's cached formula values on every save

While doing a final round of validation (comparing `empty_v`/`nonempty` counts per the pre-existing [[openpyxl_empty_v_tag_corruption]] memory's diagnostic method, done as a habit before declaring the scripts done — not prompted by any visible symptom yet), discovered that **every prior script in this pipeline (`make_gbc_cleansed.py`, and by extension `_receive_and_process.py`) had been silently producing corrupted output the whole session**: the real production file's Format sheet has `nonempty=10499` cached N:W formula values; running it through `make_gbc_cleansed.py` produced `nonempty=0, empty=16385` — every formula cell in the *entire* workbook (not just the ~13 columns the script actually writes) loses its cached value, because openpyxl doesn't preserve cached results on any `wb.save()`, full stop. This would have shown Excel's "repair this file?" prompt to the user on first open, and/or shown broken data in Tableau (same failure mode as documented in the referenced memory, just newly hit here).

**Fixed by building `_xlsx_recalc_fix.py`** (generic, reusable across projects — not GBC-specific), exporting `fix_and_recalc(path, wait_seconds=45)`: strips the invalid empty `<v></v>` tags (prevents the repair prompt), then drives real `Microsoft Excel.app` via AppleScript (open → sleep 45s, sized for the ~30k-row Predictions sheet → save → close) to force an actual recalculation, restoring real cached values. Wired into **both** `make_gbc_cleansed.py` and `_infer_missing_juekisha.py`'s own save paths independently (not just the last script in the chain) — since either script can be the last `wb.save()` in a given run (e.g. someone running `make_gbc_cleansed.py` standalone without ever running the inference step), relying on only one place to clean up would leave the other path silently broken again.

**Verified end-to-end after the fix, full pipeline**: `make_gbc_cleansed.py` → `_infer_missing_juekisha.py` in sequence, each independently fixing+recalculating its own save. Final file: Format sheet `nonempty=10492` (vs. original 10499, gap is real data differences not corruption), `W` column read back real 0/1 integers for all 816 rows (541 pass / 275 fail — the 3-row improvement from 278→275 exactly matches the 3 units the inference step successfully fixed), and the inferred rows' `U`/`T`/`V`/`W` all resolved correctly per the quirk note above.

## Bug found and fixed (2026-09-02): training-file selection picked unconfirmed data, causing wrong auto-inferred 受益者・事業区分

User reviewed the 2608 (2026年8月) auto-generated cleansed file and reported the auto-inferred S/U column values (from `_infer_missing_juekisha.py`) had many errors, asking to "learn from what Komatsu-san actually entered historically" instead.

**Root cause**: `build_training_maps()` picked each history month's training file via `max(files, key=mtime)` — whichever cleansed file in that month's folder had the latest modification time, without regard to whether it was Komatsu's confirmed `_更新` (corrected/final) version or just our own unconfirmed generated file. For most months this coincidentally worked (the `_更新` file naturally arrives/gets saved later), but **2606 is a counter-example**: `202606_GBC_to cleansed_更新.xlsx` (10:07) is 2 minutes *older* than `202606_GBC_to cleansed.xlsx` (10:09, regenerated during the 2026-08-06 validation session) — so the mtime-based pick silently used the wrong (unconfirmed, possibly containing our own past mis-inferences) file as ground truth for that month, letting errors potentially propagate/reinforce into later months' inference.

**Fix**: added `select_training_file()` — if any file in the folder has `更新` in its name, always use that one (latest among those if multiple), regardless of mtime; only fall back to mtime-based pick when no `_更新` file exists (currently true for 2604, 2605 — no confirmed correction received yet for those months, should be revisited once/if Komatsu sends them).

**Verified impact**: re-running inference on a freshly-regenerated (clean) 2608 file with the fix dropped the inferred-unit count from 6 to 3 — the 3 dropped (HAUSUPDATA案件 unit, a no-detail unit affecting 6 rows, USポカリ提案準備 unit) no longer had an unambiguous single-candidate match once trained only on confirmed data. The remaining 3 (INT MTG, 創立記念式典Day 1, トヨタLINE公式アカウント) were individually cross-checked against 2606/2607's confirmed `_更新` files and matched exactly every time (same 事業区分/受益者/employee) — high confidence these are correct.

**Operational note going forward**: since production `make_gbc_cleansed.py`+`_infer_missing_juekisha.py` runs happen before Komatsu has reviewed/corrected the *current* month (obviously — she hasn't seen it yet), and her `_更新` reply for month N typically arrives well after month N+1's data is already being processed, expect the auto-inference to sometimes rely on not-yet-confirmed recent months for training. The `_更新` preference fix eliminates the *avoidable* part of this (using our own stale/wrong regenerated files over her real corrections when both exist) but doesn't eliminate the inherent lag. **When the user reports "many errors" in future months' auto-inferred S/U cells, first check whether a newer `_更新` file exists for a training month that isn't being picked up correctly, before assuming the Tier1/Tier2 matching heuristic itself is wrong** — this exact bug is the more likely culprit based on this incident.

**Also discovered**: the old buggy inference had appended wrong entries to `Juekisha Table`/`Code_210714update`/`Predictions (Update)` for the 3 bad units in the original 2608 file, and there's no "undo" function — cleanest fix each time this happens is to fully regenerate the month's cleansed file from the raw department files via `make_gbc_cleansed.py --source-dir {YYMM} --force` (safe/idempotent, raw files are still sitting in that folder after the move step) and then re-run the (now-fixed) inference cleanly, rather than trying to patch out specific wrong rows in place.

**Outlook draft complication hit during this same incident (unrelated root cause, worth knowing)**: the compose window created by `create_outlook_draft_with_attachment()` sometimes doesn't reliably surface as a real draft — earlier in this session a call that should have created the Komatsu-bound draft instead left only an empty, contentless "無題" (untitled) compose window (confirmed via AppleScript: `object of window` was `missing value`, i.e. not bound to any message), while `get every outgoing message` returned empty both before and after. Re-invoking `create_outlook_draft_with_attachment()` directly worked correctly the second time (window title showed the real subject). Cause not fully diagnosed (possibly a timing/focus issue when Outlook itself wasn't frontmost yet) — if a created draft "goes missing" again, don't assume it's just not visible; check `window`'s `object` property via AppleScript (`missing value` = phantom/empty window, not a real draft) and just retry the creation call. Also note: Claude could not `close` the stray phantom window itself — blocked by the auto-mode permission classifier as a risky action — so leftover phantom/duplicate compose windows need the user to discard them manually in Outlook.

**Then user reported T/V (事業区分/受益者区分, "AC" columns) still showed hardcoded values, not formulas, in the file they checked** — they fixed it manually and asked this not to recur. **Process fix committed to the user, apply going forward**:

Don't just assert success from having *run* the no-inference regeneration; check the actual cell content type.
2. **Stop creating a new Outlook draft on every intermediate correction.** Each fix in this session (buggy 6-unit → fixed 3-unit → no-infer clean) got its own `create_outlook_draft_with_attachment()` call, producing a pile of same-subject drafts (plus at least one confirmed phantom/empty compose window) that were hard for the user to tell apart or clean up (Claude's own `close window` calls are blocked by the auto-mode permission classifier, so cleanup falls on the user). **New rule: while a month's cleansed file is still being iterated on/corrected, just update the file in place at its fixed path (`{YYMM}/{YYYY}{MM}_GBC_to cleansed.xlsx`) and tell the user that path — don't call `create_outlook_draft_with_attachment()` again until the content is actually final.** Only create the one real draft at the end.

## Root-cause investigation (2026-09-02): T/V (事業区分/受益者区分) columns being static values instead of formulas is a longstanding, pre-existing issue — NOT something this pipeline introduced

After the process fixes above, user pointed to a saved-off copy of what the pipeline actually produced (`2608/202608_GBC_to cleansed_old.xlsx`, kept before their own manual fix) and said Claude's output had hardcoded values in T/V, not formulas — clarifying that the formulas the earlier verification saw were already the user's own manual restoration, not what the pipeline had generated.

**Investigated properly this time** (openpyxl `data_only=False`, checked whether each cell's value is a formula string/`ArrayFormula` object vs a literal): found **353 of 816 rows** in the pipeline-produced `_old.xlsx` had literal (non-formula) values in T and/or V. Cross-checked against the source this file's N:W range was copied from, `2607/202607_GBC_to cleansed_更新.xlsx` (Komatsu's own confirmed file) — **exactly the same 353 row numbers, byte-for-byte identical set.** Then checked every other available historical month back to the very first one (2601, `_更新` where available):

| month | data rows | rows with literal T/V | 
|---|---|---|
| 2601 | 707 | 245 |
| 2602 | 768 | 434 |
| 2603 | 811 | 315 |
| 2604 | 776 | 276 |
| 2605 | 776 | 301 |
| 2606 | 796 | 387 |
| 2607 (確定版) | 816 | 353 |
| 2608 (this pipeline's output) | 816 | 353 (identical row set to 2607) |

**Conclusion: this is not a bug introduced by `make_gbc_cleansed.py`, `_infer_missing_juekisha.py`, or any Claude-built tooling.** The ~30–50%-of-rows literal-value pattern already existed in 2601, months before this automation project started (2026-08-04) — back when the file was still produced by the old manual `SK Format_v3.py` + hand-paste process. `make_gbc_cleansed.py` only ever overwrites A:M and otherwise copies the previous month's N:W range **byte-for-byte** (by design, per the original 2026-08-04 build note that "this range already has N:W formulas pre-filled all the way to row 1500" — an assumption that turns out to have been wrong/incomplete even back then, just never actually checked at the individual-cell level). So whatever formula/value split existed positionally in row *r* of the source month is carried forward unchanged into row *r* of the new month, **even though row *r*'s actual A:M content (employee, unit, work item) is now completely different data.** The literal T/V value sitting in that row is a frozen leftover from whatever month/employee last "held" that physical row position, not a live computation of the current occupant's data.

**This is more than cosmetic — W's own pass/fail formula reads T/V directly**, not S/U:
```
W = IF(OR(COUNTIF(Code_210714update!$F$4:$F$51,V{r}), COUNTIF('Juekisha Table'!$F$3:...,V{r})), COUNTIF(Code_210714update!$D$4:$D$32,T{r}), 0)
```
So for any row where T/V are stale frozen values rather than a live XLOOKUP result, W's 1/0 verdict for that row is computed from data that has nothing to do with the row's actual current contents. Whether this has been silently producing wrong W results for years, or whether it happens to not matter in practice for some reason not yet understood, is **unresolved** — not investigated further this session per explicit user instruction (user had already manually fixed and sent this month's file to Komatsu-san; asked only for root-cause + a note for next time, no action needed now).

**Not determined**: the exact mechanism by which a cell transitions from formula to static value in the first place (i.e., who/what "pastes values" over these specific rows, and why only ~30-50% and not all). Since the pattern predates any Python/openpyxl tooling in this project (present already in 2601), it's almost certainly either (a) a manual Excel "paste values" step Komatsu or a predecessor has performed at some point per confirmed row (maybe as a stability/performance measure once a row's classification is confirmed and no longer expected to change), or (b) an artifact of how the original template (`000000_GBC_Format_v3.4.xlsx` etc., 2021–2023 vintage files sitting in the root of this folder) was originally built, with only a subset of rows ever getting real formulas. Not conclusively identified.

**For whoever picks this up next**: the actual fix, if wanted, would be to make `make_gbc_cleansed.py` (or a new repair pass) regenerate the canonical T/S/U/V formula for every data row from a known-good template (the formula pattern is mechanical/row-relative, e.g. `=IF(AND(R{r}=0,COUNTIF(Code_210714update!$D$4:$D$42,S{r})=0), XLOOKUP(Y{r},'Predictions (Update)'!$F$2:$F$40000,'Predictions (Update)'!$C$2:$C$40000,"N/A",0), S{r})` for T, similarly for V/S/U) rather than trusting whatever the previous month's cell happened to hold — but this touches ~40% of every month's rows across a business-critical sheet, so should be scoped and validated carefully (compare recomputed W against the existing W for a full historical month first) before ever running for real, and should probably be raised with the user as its own dedicated task rather than folded into a routine monthly run.

## Bug found and fixed (2026-09-03): predicted data-validation-loss caveat actually hit — T/V column dropdowns disappeared

The `make_gbc_cleansed.py` caveat noted back on 2026-08-04 ("that specific Excel feature... will likely be dropped on save") materialized for real: 小松さん(HRM)reported the T列(事業区分(AC))・V列(受益者区分(AC)) dropdown lists were gone in the 2608 file sent to her on 2026-09-02.

**Confirmed via direct xlsx internals inspection**: the dropdowns are stored as a modern-Excel `x14:dataValidation` extension inside `<extLst>` at the very end of the Format sheet's XML (`xl/worksheets/sheet1.xml`) — `T12:T1500` sourced from `Code_210714update!$D$4:$D$42`, `V12:V1500` from `Code_210714update!$F$4:$F$51`. Confirmed present in 2607's `_更新` (Komatsu's confirmed file) and completely absent in the pipeline-produced 2608 file — openpyxl drops the whole `extLst` block on any `wb.save()` (separate failure mode from the already-known [[openpyxl_empty_v_tag_corruption]] cached-formula-value bug, same root cause category: openpyxl doesn't round-trip everything modern Excel writes).

**Fixed**: added `restore_format_dropdowns(path)` to `_xlsx_recalc_fix.py`, wired into `fix_and_recalc()` (called by both `make_gbc_cleansed.py` and `_infer_missing_juekisha.py`) right before the Excel-recalc step. It locates the Format sheet's actual XML filename via `workbook.xml`→`_rels` (robust to sheet reordering), checks for `x14:dataValidations` already present (idempotent no-op if so), and otherwise injects the exact extLst XML block (hardcoded, matches the confirmed-good 2607 file byte-for-byte) via raw zip patch just before `</worksheet>`. Runs before the AppleScript Excel-recalc step so real Excel opens/saves a version that already has valid dropdowns and doesn't need to (and won't) strip them again.

**This closes the caveat permanently for all future monthly runs** — no further code changes needed; both pipeline scripts already call `fix_and_recalc()`.

**Immediate remediation for the reported 2608 file**: created `2608/202608_GBC_to cleansed_20260903.xlsx` (dated copy per [[feedback_pptx_filename_versioning]]'s general versioning rule, applied here since the original was already delivered externally to Komatsu-san — did not overwrite `202608_GBC_to cleansed.xlsx` in place) with the dropdown restored, verified via openpyxl reload + zip integrity + direct XML re-inspection. Created an Outlook (classic) reply draft to hitomi.komatsu@dentsu.co.jp / cc yamada.keita@dentsu.co.jp explaining the cause briefly and attaching the fixed file — **draft only, not sent**, per this project's established practice.

**New AppleScript gotcha found**: the previously-documented phantom-draft check (`object of window` returning `missing value` = phantom, per the 2026-09-02 note above) gave a **false positive** this time — two drafts were actually created successfully (confirmed via `outlook` CLI / Outlook Web search showing both with correct subject/body/attachment) despite `object of window` reporting `missing value` for both. **This diagnostic can no longer be trusted as-is** — verify draft creation via the `outlook` CLI (`outlook list "<unique phrase from subject>"`) instead, not via the `object of window` AppleScript property. Also: retrying `create_outlook_draft_with_attachment()` after an apparent (but actually false) phantom-failure produced a real duplicate draft — don't reflexively retry without checking via `outlook list` first, since the first attempt may well have already succeeded.

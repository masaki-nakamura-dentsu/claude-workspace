Masakiの依頼で、8つのQBR Tableauワークブック(twbx+pptx)とPower BIダッシュボード(.pbix)の数値を突き合わせ検証。CAS側は完全一致だったが、貢献売総側で重大な列取り違えを発見・修正した。局内リリース前の重要な検証作業。

## 検証手法(再利用可能)

1. **Tableau側の正解値抽出**: `.twbx`はcp437で文字化けするファイル名を含むzip。`zipfile`でinfoの`filename.encode('cp437').decode('cp932')`により正しく展開可能([[qbr_2026q3_8gatsu_update_20260906]]の続きで確立)。`.pptx`のエクスポート画像(QBR APPダッシュボードのスライド)がTableauの「見たまま」の数字のground truthとして最も信頼できる。
2. **Power BI(.pbix)の中身を直接解析**: `pbixray`ライブラリでDataModel(VertiPaqバイナリ)からDAXメジュー・Power Query M式を直接読める。**重要: pbixrayはPython 3.9でしか動かない**(3.14だとCython依存の`xpress8`/`xpress9`ホイールが存在せずビルド失敗)。`/usr/bin/python3`(Apple同梱の3.9.6)で新規venvを作れば`pip install pbixray`が素直に通る。**2026-09-08時点、会社Mac(d14461)に`~/pbixray_venv`として永続venvを作成済み**(Dropbox外のホームディレクトリ直下、[[feedback_venv_outside_dropbox_sync]]準拠)。以後は毎回作り直さず`~/pbixray_venv/bin/python3`をそのまま使う。会社Macでのpip installには`https_proxy=http://proxy1.dentsu.co.jp:8080`が必要([[feedback_d14461_pip_needs_corporate_proxy]])。個人Mac(ICPTokyo2022)で使う場合は同様に新規venv作成が必要(未作成)。使い方:
   ```python
   from pbixray import PBIXRay
   model = PBIXRay('/path/to/file.pbix')
   model.tables          # テーブル一覧
   model.dax_measures     # DataFrame: TableName, Name, Expression, DisplayFolder, Description
   model.dax_columns      # DAX計算列
   model.power_query      # DataFrame: TableName, Expression(M式)
   model.schema           # 全列名一覧(PQ由来含む)
   model.dax_tables       # 計算テーブルの定義(DATATABLE/UNION/{...}等のDAX式)。「指標選択」のような手入力の選択肢テーブルもここで定義文が見える
   ```
   これがなければ「どのメジューのどの部分を直せばいいか」を正確に特定できなかった。今後もPower BIの数値検証で同様の話が出たら真っ先に使う。`model.get_table()`(実データ取得)は本ファイルの列では動いたが、他の列(例: 手入力の小さな計算テーブル)では内部メタデータ参照エラーで失敗することがある([[kgikpi_cas_uriage_soritsuki_rename]]で確認、2026-09-08)——実データが必要なら`dax_tables`の定義文やPower Query側から読む方が確実。

## 発見1: 貢献売総の列取り違え(最重要)

Salesforceの`GBC__c`オブジェクトには、似た名前で意味が違う2つの貢献売総フィールドが存在する:

| Tableau表示名 | Salesforce API名 | 意味 | GM承認との関係 |
|---|---|---|---|
| 月別集計用/GBC貢献売総(A)/**Att.Rev(A)**(JPY) | `GBCMonthContributionGross__c` | 確度A(100%)の attributed revenue。GM承認の有無に関わらず値が入る | 無関係(GM未承認でも非ゼロ) |
| 月別集計用/GBC貢献売総(計上)/**Attrib. Rev(Rec.)**(JPY) | `GBCMonthContributionGrossP__c` | 実際に"計上"された(会計上認識された)額 | **完全に連動**(GM承認=Falseなら必ず0、例外なし) |

**検証事実(2026年度データで実測)**: `GM承認/Auth.`=Falseの行は449行あり、そのうち**449行全てでAtt.Rev(計上)=0**(例外0件)。GM承認=Trueの行は242行、Att.Rev(計上)合計は1,309,357,390円(部署フィルタ未適用時)。つまりAtt.Rev(計上)はSalesforceの計算式レベルで「GM承認済みでなければ0」という設計になっている。一方Att.Rev(A)はGM承認Falseの144件中144件が非ゼロで計上されており、GM承認とは無関係。

**QBRの「貢献実績(計上済)」は必ずAtt.Rev(計上)を使うべき**。GM承認の有無を明示的にDAX/M側でフィルタする必要はなく、この列を使えば自動的にGM承認済みだけが集計される。

**当初の誤り**: Power BIの元の7メジューは正しくAtt.Rev(計上)を使っていたが、ある時点で正樹さんが「Tableauの`6. QBR_貢献実績+見込 V1.0.twb`と数字が合わない」ことを発端に検証したところ、TableauのCOMBINED側が2026-09-06朝の更新で誤ってAtt.Rev(A)ベースで「貢献売総」列を構築していたことが先に見つかり、それをPower BIの「正」だと誤認してPower BI側をAtt.Rev(A)に「修正」してしまった(¥385M近く数字が変わった)。その後、正樹さんの同僚がSalesforce上で直接検索して出した公式値(2026年=1,295,626,390円、確度A・Att.Rev(計上)ベース)と突合して初めて、Att.Rev(計上)が正しく、最初の「修正」が誤りだったと判明。**教訓: 2つのTableauファイルの数字が食い違った時、どちらが「正」かを外部の権威(この場合は同僚のSalesforce直接検索+GM承認との相関という一次証拠)なしに推測で決めてはいけない**。[[feedback_verify_against_official_totals]]の追加事例。

## 発見2: 部署フィルタにNS部が誤って含まれていた

正樹さんの同僚がSalesforceで使った公式検索条件:
```
月別見込親案件: フェーズ/Phase 次の文字列と一致しない (空)
年月 = 202601〜202612 (2026年全月)
月別見込親案件: 部署名/Dept. 次の文字列と一致する: AP1部,AP2部,AP3部,BD部,SK部,SP1部,SP2部
月別集計用/部署名 次の文字列を含む: BD,GS,NB
確度 = A
月別用重複確認 = False
```
Power BIの`貢献実績`テーブルのPower Query(`GBC_月別_自己結合_Base`から`フィルター処理された行`ステップ)は、部署名リストに`"業管","NS部","HRM","局付け"`を余分に含んでいた(確度も`{"A","B","C","X","","null"}`で実質フィルタなしだった)。2026年のNS部だけで2行あり、これが¥13,731,000円のズレの原因(公式値1,295,626,390 vs 部署フィルタなしの1,309,357,390)。

修正: `貢献実績`テーブルのM式の`フィルター処理された行`ステップを以下に統一(正しい部署リスト`{"AP1部","AP2部","AP3部","BD部","SK部","SP1部","SP2部"}` + `[確度] = "A"`の厳密一致に変更)。**この修正は`貢献実績`テーブル自身のM式にだけ適用**(共有クエリ`GBC_月別_自己結合_Base`は触っていない、`CAS見込`/`貢献見込`など他テーブルへの影響なし)。

## 発見3: DAXエディタの「先頭行消失」バグ(Power BI Service ブラウザ版)

メジューの中身を「全選択→貼り付け」する際、貼り付けテキストの**先頭の`VAR SelectedYear = `(または`VAR ClientIsFiltered = `)がごっそり消えて構文エラーになる**現象が複数回再現した。原因は不明(貼り付け時のIntelliSense干渉と推測)だが、**測定値名(`貢献実績_合計 = `)を貼り付けテキストの1行目に必ず含める**ことで解消した(既存のフィールドが空でない状態で全選択→貼り付けすると、既存の`測定値名 = `部分も含めて丸ごと置き換わるため、それを自分で明示的に含めないと消える)。[[feedback_give_full_code_not_partial_diffs]]の類似事例として記録。今後Power BI Serviceでメジューを丸ごと貼り替える時は、必ず`測定値名 = \n<式>`の形で渡すこと。

## 発見4: file④(貢献実績単体.twb)とfile⑥(COMBINED.twb)は別々の(食い違った)計算式を持つ

`4. QBR_貢献実績 V1.0.twb`(前任者作成、正樹さんも意図不明)は独自の計算フィールド`Calculation_1399775071524532225`(表示名「貢献売総」)を持ち、中身は`IF [Att.Rev(計上)]=0 THEN NULL ELSE [Att.Rev(計上)] END`で**確度によるフィルタが一切ない**(A/B/C/X全部、非ゼロなら計上)。ワークシート「Overall (A)」「Actual (Q)」「Actual (A) (2)」など、file④のQBR APPダッシュボードの数字は全てこれを使っている。**正樹さんは実運用では`6. QBR_貢献実績+見込 V1.0.twb`(COMBINED)の方だけを使うと明言**、file④はそのままで良いとの判断(前任者の遺物、触らない)。もしfile④を今後使う場面が出たら、この不整合を再度説明すること。

## 発見5: JCIピッチのPipeline差はデータ鮮度の問題(バグではない)

`7. QBR_Japan Client ピッチ状況.twb`のPipeline額がPower BIと¥63,141ズレていた件。原因は**Tableauが参照する`GBC 日系ターンアラウンド_APAC_Pitch-List_All_v1_3.xlsx`が2026-08-14付けで3週間以上更新されていない**こと(Power BIはSalesforce直結でリアルタイム)。さらにこの間にSalesforceのフェーズ(ピックリスト)ラベルが「仕掛中/未受注 (In Progress)」→「New（新規）」に改名されており、Tableauの判定式(`フェーズ="仕掛中/未受注 (In Progress)"`→Pipeline)とPower BIのPower Query判定(`GBCPhase__c="New（新規）"`→Pipeline)は同じ意図でラベルだけ違う。次回このExcelファイルを最新化すれば解消する見込み(未対応、優先度低)。

## 発見6: 「計上済み除外」ロジックが15個のメジューに重複コピペされていた(2026-09-06追加)

`貢献見込`(GM未承認の見込額)は「実績(計上済)」と二重計上しないよう、`'貢献見込'[貢献売総_計上] = 0`(GM承認済み=計上済みの行を除外)という条件が必要だと判明(同僚の公式数字との突合で発覚: colleague's「A」列(承認+非承認合計)から「承認実績」を引いた額が正しい見込Aだった)。

**ところがこの条件は、共通の`貢献見込_合計`メジュー経由ではなく、`SUM('貢献見込'[貢献売総])`を直接呼ぶ形で最低15個のメジューに個別にコピペされていた**(集計ロジックを一元化せず、ページ/ビジュアルごとに似た式を都度複製する設計だったため)。1つ直しても他が直らず、「直したのに数字が変わらない」を3回繰り返した。該当メジュー一覧(全て`'貢献見込'[貢献売総_計上] = 0`を追加して対応):

`積み上げ値`(Raw YTD)、`貢献見込_合計`/`貢献見込比率`(貢献見込)、`見込A_合計`/`見込B_合計`/`見込C_合計`(CAS見込、CAS/貢献両用)、`実績見込_累計`/`案件別ブレンド値`/`見込A_合計_部署別`/`見込B_合計_部署別`/`見込C_合計_部署別`/`積み上げ値_表紙`/`残り_実績A`/`残り_実績AB`/`残り_実績ABC`(全てRaw YTD)。

**教訓**: 「このメジュー1つ直せば直るはず」と決め打ちせず、`貢献見込[貢献売総]`のような列を参照している**全メジューを横断検索**(`dax['Expression'].str.contains(...)`)してから着手すべきだった。特にこのモデルは同じ集計ロジックをページごとに複製する設計になっているため、1箇所の計算ロジック変更は必ず横断検索で全該当箇所を洗い出すこと。CAS側にも同様の構造(`見込_合計`、CAS見込ベース)があるので、CAS側で同種の修正が必要になった時も同じ手順を踏むこと。

## 発見7: 「計上済み除外」は最終的に18個のメジューに分散していた、visual.jsonで正確な紐付けを特定する技法

発見6の15個(列参照ベースの横断検索)に加え、`SUMX('貢献見込', ...)`で列参照せず独自にGroup売総×貢献度を再計算していた`貢献見込_A`/`貢献見込_B`/`貢献見込_C`(表紙ページ用)の3個が追加で見つかり、**合計18個**を修正して完了。この3個は列名ベースの正規表現検索(`貢献見込'\[貢献売総\]`)ではヒットしないため、`'貢献見込'` and `SUMX`のような緩い条件でも横断検索をかけ直す必要があった。

**「直したのに反映されない」が発生した時の切り分け技法**: DAXの呼び出し関係を辿るだけでなく、`.pbix`を展開して`Report/definition/pages/*/visuals/*/visual.json`を直接grepする方法が最も確実。例えば`grep -rl "前年同期実績" Report/definition/pages/*/visuals/*/visual.json`のように**表示ラベルの文字列で検索**すれば、その列が実際にどの物理メジュー名(`queryState.Values.projections[].field.Measure.Property`)にバインドされているか一意に特定できる。DAXの呼び出しチェーンを目で追うより速く確実(このセッションで「売上総利益_前年同期間」と「売上総利益_前年度_遡及」が実は同一の`[貢献実績_前年合計]`を指していた事故もこの方法で確定できた)。

**もう一つの罠(発見済み、要記録)**: `売上総利益_前年同期間`(同期間限定)と`売上総利益_前年度_遡及`(通年)は、CAS側では正しく別ロジックだったが、貢献売総側だけ両方とも同じ`CALCULATE([貢献実績_前年合計], ALL('月'))`を指す誤りがあった(コピペ時に片方だけ実装し忘れたと推測)。「前年同期実績」列と「前年度」列が常に同じ値になっていたら、この2メジューの分岐を疑うこと。

**スライサーの罠**: 「実績ABC」スライサー(実績/A/B/C複数選択)は`凡例_実績見込[項目]`という非接続テーブルに紐づいているが、`見込A_合計`等の個別メジューはこのテーブルを一切参照していないため、スライサーで絞り込んでもKPIカード/表の個別行は無条件に表示され続ける(合計値である`年度着地見込`は`SUMX(VALUES(...), ...)`パターンで間接的にスライサーを尊重するため、集計行と内訳行で挙動が食い違って見えた)。個別行をスライサーに追従させるには、表示側のSWITCH測定値(`KPI値`等)で`COUNTROWS(FILTER(VALUES('凡例_実績見込'[項目]), [項目]="X"))>0`のチェックを追加する必要がある。

**完了状態(2026-09-06セッション終了時点)**: CAS側は完全一致、貢献売総側(実績・見込A/B/C・前年同期実績・前年度・KPI表のスライサー追従)は全て修正・確認済み。JCIピッチのPipeline差(データ鮮度、優先度低)と貢献見込のExcelファイル自体の部署制限は未着手のまま(次回)。

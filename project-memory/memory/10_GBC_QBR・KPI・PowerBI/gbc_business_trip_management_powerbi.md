# GBC出張管理システム

[[gbc_department_move_2026]] に一覧記載の自作社内ツールの一つ。2026-06-10〜2026-07-02頃に**ChatGPT**と作り込んだシステム（Claudeでの作業はこれが初回、2026-08-06〜）。

## 構成
- 入力: Microsoft Forms「GBC 出張申請Forms」
- 自動化: Power Automate
- 保存先: SharePoint List（サイト `https://esq365.sharepoint.com/sites/GBCarekoko`）
  - メインリスト「GBC出張管理」（通常出張情報）
  - 別リスト（緊急連絡先/個人情報用、終了日から90日で自動削除フローあり）
- ダッシュボード: Power BI（マネージャー向け、本命）。Power Apps は過去に試作したが今は補助扱い
- Power BI Pro契約済み、SharePoint埋め込み運用中
- **Mac制約**: Power BI Desktopが使えないため、Power BI Service（ブラウザ）上で運用・編集している

## SharePointメインリスト列
タイトル, 出張内容, 出張者, 出張開始日, 出張終了日, 国名, 都市名, 費用負担, 費用負担部署, クライアント名, 申請者メール, 申請日時, 緯度, 経度, 更新日時, 登録日時, 登録者, 更新者, 表示対象（はい/いいえ）

- タイトル列を「申請ID」相当として使用する設計（Power Query側で `申請ID` を `[タイトル]` から作成）
- 出張者自身ではなく**担当マネージャーがForms入力**する運用（緊急連絡先を出張者本人に直接書かせるのは中止した経緯あり）

## 既存Power Automateフロー
1. **GBC 出張表示対象更新**（毎日1回）: 出張開始日が30日より前のものは表示対象=いいえに、それ以外ははいに更新
2. **GBC出張データ 緊急連絡先情報削除**（毎日1回）: 出張終了日から90日より前の個人情報を削除
3. **承認フロー**（Forms受信 → 回答詳細取得 → 承認待ち[Start and wait for approval] → 承認後にSharePoint登録 → Power BIデータセット更新 → 承認コメントをメール本文に差し込んで結果通知）
   - Power BIデータセット更新はSharePoint書き込み直後だと反映されないため、数分のDelayを挟んで解消済み

## Power BIモデル「GBC出張管理モデル」
- ディメンション: 出張開始日, 出張終了日, 出張者, 国名, 都市名, 出張内容, クライアント名, 費用負担, 費用負担部署, 申請日時, ID, 申請ID
- ビジュアル: KPI(出張者数/都市数), 地図, 滞在者リスト, 出張開始日スライサー, 表示対象True/Falseスライサー
- 既知の問題（引き継ぎ資料時点）: 地図が都市名単独だと誤認識（例: 長崎→東京と誤表示）。対策は「場所」フィールドに国名+都市名を両方入れる、データカテゴリを国名=国/地域・都市名=市に設定、それでもズレるなら緯度経度を使う

### 最終フロー構成(承認を作成の直後、3並列分岐)
1. 「**承認を作成**」(Create an approval, assignedTo=`variables('承認者')`) — 旧「開始して承認を待機」(ブロッキング)を置き換え
2. 分岐: 「**開始して承認を待機**」(Wait for an approval completion、旧アクションと**同名で新規作成**することで既存の手打ち参照 `outputs('開始して承認を待機')` を復旧) → 変数「承認完了」をtrueに設定
   - **この直後(runAfter)に「条件」(Approve/承認で分岐、For eachで情報共有先へ通知)を再接続** — 当初この「条件」は「承認を作成」に対する並列分岐として構成してしまい、`For each`のforeachソースが無効化される設計バグがあった(条件式自体は文字列参照なので検証はすり抜けるが、実行順序が保証されないレースコンディション)。設定タブ「この後に実行する」で依存先を「承認を作成」→「開始して承認を待機」に貼り替えて解消。**今後この並列分岐パターンを組む際は、後続処理が特定アクションの出力に依存する場合、必ず「設定→この後に実行する」でrunAfterを明示的に紐付けること**(暗黙のテキスト参照だけでは実行順序は保証されない)。
3. 分岐: 「実行」(Scope) → **Do untilリマインドループ**: 遅延24時間 → 条件1(`or(equals(dayOfWeek(utcNow()),0),equals(dayOfWeek(utcNow()),6))` = true つまり土日ならTrue分岐=何もしない、平日ならFalse分岐で「リマインドメール送信」アクション実行、宛先=`@{variables('承認者')}`) → ループ停止条件=変数「承認完了」がtrueになったら終了、タイムアウト`P30D`(既定PT1Hから変更必須、かつワークフロー全体の存続期間上限30日を超えられないため元案のP60Dも不可)

### 実装中に踏んだ罠(いずれも解消済み、[[power_automate_gotchas]]に追加検討価値あり)
- **条件式ビルダーへの関数式の直接テキスト入力は、評価式ではなく文字列リテラルとして保存される**(コードビューで確認すると `"equals": ["or(...)", ""]` のようにクォート付き文字列になる)。正しく評価式として保存するには、値フィールドの fx アイコン→式エディタのポップアップに入力→「追加」ボタンで確定する必要がある(コードビューで `"@or(...)"` と `@` プレフィックス付きで保存されれば成功)。
- 並列分岐の一方が他方の出力を参照する構成にすると、`For each`の「前のステップから出力を選択します」フィールドがUIのドロップダウン選択を要求し、実行順序保証のない並列分岐からは選択不可としてエラーになる(パラメーターが無効です)。**根本解決は runAfter を明示的に繋ぎ直すこと**。応急処置として当該フィールドに直接文字列(`@outputs('アクション名')?['body/xxx']`)をタイプすれば設計時エラーは消せるが、runAfter未設定のままだと実行時の非決定性リスクが残るため必ず併用すること。
- Do-untilのタイムアウトは「ワークフローの存続期間」設定(このテナントでは30日)を超えられない。P60Dのような長い値を指定するとPT1H既定値問題とは別に、保存時に`WorkflowRunActionTimeoutLimitInvalid`エラーになる。

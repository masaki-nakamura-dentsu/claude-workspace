2026-08-21、新規Power BIページ構築の準備確認中に、正樹さんから「合計金額が214,185,802だが215,633,242になるべき、AP1の数字が違う」と指摘があり調査。[[powerbi_migration_gbc_dashboard]]・[[cas_csv_download_automation]]の関連。

## 原因

Power BIのRaw YTDが参照する`GBC CAS実績_FY22 TO DATE.xlsx`(QBR作成フォルダ)のAP1・2026年データが、`CAS集計 FY26_GBC_クライアント_件名別_final20260804.xlsx`(CAS集計フォルダ)より**古いスナップショットのまま**になっていた。両ファイルは同じCASデータが起点だが、自動パイプライン導入(8/17)以前の手動運用時代に別々のタイミングで取り込まれたため、その間にCAS側で計上月・金額の補正が入った案件がずれて食い違った。

## 突合手法(次回同種の調査で再利用可能)

1. 単純にheader番号(受発注ヘッダNo)だけをキーにしたdict比較は**誤り**——同じheader番号が複数行(内部組織ルーティング違いの売上行/原価行など)持つのが普通のデータ構造なので、dictがキー衝突で行を握りつぶし、大きく実態と異なる差分になる(最初「9件」と誤認した)。
2. 正しくは`collections.Counter`による**多重集合(multiset)比較**を使う。キーは(受発注ヘッダNo, 計上月, クライアント名, 件名, 売上金額, 原価金額)のような複合キーにする。これで実際は196行 vs 176行という大きな差分が見えた。
3. 最終的な正誤判定は、CASシステムの現在値を直接確認して行う。`~/CASExport/cas_download.py`の`download_month(start_ym, end_ym, out_dir, out_filename)`を使い、疑わしい期間を含めて再ダウンロード(2025-12〜2026-03を指定)。CSVは`pd.read_csv(path, header=18, encoding='utf-8-sig')`(`cas_pipeline_lib.PANDAS_HEADER_ARG`と同じ)で読む。9件のヘッダNoをサンプル確認したところ、CAS集計ファイル(final20260804)がCAS現在値と1円単位・計上月まで完全一致し、QBR作成ファイル側が不完全と確定。
4. 結論: AP1・2026年に関しては**CAS集計ファイルの196行が正**、QBR作成ファイルの176行を丸ごと置き換えるのが正しい対応(個別行diffのパッチではなく、対象org×年の全行スワップの方が安全・確実)。他の組織(AP2/AP3/BD/SP1/SP2)は完全一致していたため対象外。

## 事故: 自動修正中にRaw YTDのほぼ全データ(5,998行)を一瞬で喪失、直後にバックアップから復元

Claudeが「削除→file1データで置き換え」をPythonスクリプトで自動実行しようとした際、`cas_pipeline_lib.find_last_data_row()`が**書き込みモード(`openpyxl.load_workbook(path)`、data_only未指定)で開いたワークブックに対して使うと壊れる**バグを踏み、「最終データ行=1(ヘッダーのみ)」と誤判定。削除対象0件のまま、新データを2行目から**上書き**する形で追記してしまい、既存5,998行のうち5,802行が実質消失(196行のAP1データだけが残る状態)。

**直前に取っていたバックアップ(`QBR作成/Archive - Data for Tableau/20260821/`)から即座に復元し、実害なし。** Power BIのスケジュール更新前に気づけたため事なきを得た。

### 根本原因(2026-08-21、事故後に特定・修正済み)

`Raw YTD`シートのB列(受発注ヘッダNo)は、**過去の大部分の行が`='Raw YTD_Original'!B2`のような数式**(別シート参照)になっている。一方`is_real_value()`は`text.startswith("=")`の値を「実データではない」として除外する実装だった。そのため:
- `data_only=True`(値のみ読む読み取り専用モード)で開けば、数式の計算結果(キャッシュ値)が返るので問題なく動作する ← これまでの読み取り調査は全てこのモードだったため正しく動いていた。
- **`data_only`を指定しない通常モード(保存が必要な書き込み時は必須)で開くと、数式セルは文字列`"='Raw YTD_Original'!B2"`そのものが返り、`is_real_value()`がこれを弾いてしまう** → `find_last_data_row()`が実際のデータ範囲を正しく検出できない。

このバグは`append_rows_to_workbook()`(自動パイプライン`cas_monthly_pipeline.py`が呼ぶ本番関数)も内部で使っており、**次回(2026-09-02予定)の自動実行時に同種のデータ破損を起こすリスクがあった**。

### 修正内容

`~/CASExport/cas_pipeline_lib.py`の`is_real_value()`から`if text.startswith("=")`除外を削除(数式セルも「実データがある行」として正しくカウントされるように)。**スクラッチ上の複製ファイルのみで検証**(本番ファイルは一切触っていない)、修正後は正しい最終行(6019行目、データ6018行)を返すことを確認済み。本番ファイルはこの修正版コードではまだ一度も書き込みを行っていない。

**次回9/2の自動実行後、正しく動作したか(行数・ログ・work_statusエントリ)を確認することを推奨。**

## 最終的な手動修正(正樹さん実施、2026-08-21完了・検証済み)

Claude側の自動化を諦め、以下をClaudeが用意し正樹さんが手動実施:
1. `AP1_2026_置き換え用データ.xlsx`(CAS集計ファイルから抽出・半角変換済みの196行、SendUserFile経由で送付)
2. 手順: Raw YTDでA列=AP1・E列=2026をフィルターして176行を行削除 → 添付ファイルの196行をコピペで追記

結果検証: AP1・2026年合計21,451,446円、全体2026年合計215,633,242円、CAS現在値と完全一致。**完了。**

## 教訓

1. **多重集合比較(Counter)を使う** — 業務データでキー(伝票番号等)の重複は珍しくない、単純dict/setでの差分比較は静かに間違った結論を出す。
2. **「本番データを直接書き換える自動処理」は、たとえ既存の実績あるライブラリ関数を使っていても、呼び出しコンテキスト(read_only/data_only有無)が変わると壊れうる** — 事前にスクラッチ複製で動作確認してから本番に当てるべきだった(今回は不十分だった)。
3. バックアップを先に取っておく習慣([[cas_csv_download_automation]]の設計、および今回Claudeが踏襲した手順)が実害ゼロで済んだ決め手。この習慣は今後も必須。
4. 大規模自動修正でリスクが顕在化した後は、無理に自動化を続けず「正しいデータを用意→ユーザー本人が手動で反映」に切り替えるのが安全([[feedback_token_conscious_powerbi]]とも整合)。

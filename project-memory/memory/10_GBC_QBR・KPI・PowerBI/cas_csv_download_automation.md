## What it does, end to end, with zero Claude tokens per run

A launchd job (`com.nakamura.caspipeline`, `RunAtLoad=true` + `StartInterval=1200`) runs `~/CASExport/cas_monthly_pipeline.py` every ~20 min. Each run:
1. Checks `~/CASExport/cas_pipeline_state.json`'s `last_processed_month` and computes whether the *next* month's CAS actuals have been confirmed yet, using the business-day rule the user gave 2026-08-17: **3/6/9/12月分は翌月の第3営業日、それ以外は翌月の第2営業日に確定**（`jpholiday`パッケージで祝日を除いた平日ベース）. If not yet due, does nothing.
2. If due: downloads that month's CAS「汎用検索」全項目CSV (via `cas_download.py`, Python/Playwright port of the original Node downloader — see history below), saving into `.../GBC戦略企画部_GBC設定実績・見込/CAS集計/<YYMM>/GBC全体_<Y>年<M>月実績明細.csv` (matches the existing manual-era folder/file naming convention exactly, per the user's explicit request to store downloads there instead of `~/CASExport/<month>/`).
3. Transforms it via `cas_pipeline_lib.py` into Raw YTD's 14-column schema, applies profit-split requests from `GBC利益スプリット管理表.xlsx` (same logic as the historical script — see below), then writes to BOTH production files:
   - `CAS集計 FY26_GBC_クライアント_件名別_final<today>.xlsx` (CAS集計/) — full-width text, new dated file copied from the latest existing `final*.xlsx` (matches established versioning pattern, most months in the folder's history got a fresh dated file rather than in-place edits).
   - `GBC CAS実績_FY22 TO DATE.xlsx` (QBR作成/) — same data but **hankaku (half-width) converted** via `jaconv.z2h(kana=True, ascii=True, digit=True)`, appended **in place** (fixed filename, since Power BI/Tableau reference it by exact name), after backing up to `QBR作成/Archive - Data for Tableau/<today>/`.
4. Guards against duplicate appends: before writing, checks whether the target month's (計上年,計上月) already exists in that file's Raw YTD sheet; skips if so.
5. Updates `last_processed_month` in the state file only after both files succeed, and appends a `work_status/cas_csv_download_automation.md` log entry.
6. On any error, stops without advancing state (so the next run retries the same month) and logs to `~/CASExport/cas_pipeline_log.txt`.

## Critical bug found & fixed 2026-08-21 — `find_last_data_row()` / `append_rows_to_workbook()` could corrupt file2 on next real run

While investigating an unrelated AP1 data-gap issue (see [[powerbi_raw_ytd_ap1_gap_incident_20260821]]), discovered that `GBC CAS実績_FY22 TO DATE.xlsx`'s Raw YTD sheet has a large historical row range where column B (受発注ヘッダNo) holds **formulas** (`='Raw YTD_Original'!B2`), not literal values. `is_real_value()` in `cas_pipeline_lib.py` excluded any cell value starting with `"="`, so when the workbook is opened in normal (non-`data_only`) mode — exactly how `append_rows_to_workbook()` opens it, since it needs to save afterward — `find_last_data_row()` badly miscounted the true last row (observed results ranging from 1 to ~5083 instead of the correct ~5999/6019, depending on where the first non-formula literal cell happened to sit). This directly caused a near-total data-loss incident when Claude tried to use this exact code pattern for a manual fix (5,998 rows nearly overwritten with 196, caught and reverted from backup immediately — see incident memory for full story).

**This is the same function `append_rows_to_workbook()` calls on every real automated pipeline run.** The pipeline has not yet had a real run since automation went live (still waiting on August's 2026-09-02 confirm date as of 2026-08-21), so this bug had not yet triggered in production, but would very likely have caused the same kind of corruption on that run.

**Fixed**: removed the `text.startswith("=")` exclusion from `is_real_value()` in `~/CASExport/cas_pipeline_lib.py` — formula cells now correctly count as "real" data rows. Verified against a scratch copy of the live file (not production) that this now returns the correct last row. **Not yet verified against a real production pipeline run** — check the outcome of the next automated run (~2026-09-02) via `cas_pipeline_log.txt` and the `work_status/cas_csv_download_automation.md` log entry, and spot-check row counts in both production files afterward.

## First real production run, 2026-09-02 — 3 more critical bugs found and fixed, plus a still-unresolved Power BI mystery

The 2026-09-02 08月分 confirm-date run was the pipeline's first real (non-"nothing due") execution. Multiple bugs surfaced immediately:

**Bug 1 — CSV header row position isn't fixed.** `cas_pipeline_lib.py` had `PANDAS_HEADER_ARG = 18` hardcoded (the pandas skip-blank-lines-adjusted row index of the real header), based on 2026-08-17's file. The 08月 CSV's「検索条件」block had grown by a couple of lines (extra filter fields like 直受注・直発注区分/カテゴリ分類（OR）now present), shifting the true header to a different offset, so `pd.read_csv(..., header=18)` mis-parsed and threw `Expected 1 fields in line 23, saw 174`. **Fixed**: replaced with `_find_header_line_index()`, which scans the raw file for the line starting with `"受発注ヘッダNo"` and uses `skiprows=<that index>, header=0` — no longer depends on the search-criteria block's line count at all.

**Bug 2 — `find_last_data_row()`/`existing_months()` were catastrophically slow in read-only mode.** The 2026-08-21 fix (above) changed `is_real_value()` but the row-scan itself still used `ws.cell(row=row, column=key_col).value` in a `range()` loop — fine on a normal (writable) worksheet, but on a `read_only=True` worksheet (used by `process_month()`'s existing-month dedup check) this individual-cell-random-access pattern is a known openpyxl anti-pattern and was taking **10-20+ minutes** for only ~6000 rows (confirmed via direct timing: full-file loop never finished in reasonable time; a rewrite using `ws.iter_rows(min_row=2, min_col=key_col, max_col=key_col, values_only=True)` instead completed the same check in ~0.2-0.3s). This looked like a hang and caused real production incidents (see Bug 4). **Fixed**: both `find_last_data_row()` and `existing_months()` in `cas_pipeline_lib.py` now use `ws.iter_rows(...)` streaming access instead of `.cell()` random access — works correctly and fast on both read-only and normal worksheets.

**Bug 3 — openpyxl wipes ALL cached formula values on every `wb.save()`, corrupting file1 for downstream readers.** This is the well-documented [[openpyxl_empty_v_tag_corruption]] bug recurring here: after `append_rows_to_workbook()` saved `GBC CAS実績_FY22 TO DATE.xlsx` (file1, has extensive `='Raw YTD_Original'!B2`-style formula columns), a `read_only=True, data_only=True` reload showed `find_last_data_row()` collapsing from 6019 to 5083 and 8月 data appearing completely absent — not because data was lost, but because the formulas' cached `<v>` values were gone, so `data_only=True` reads returned `None` for huge swathes of historical rows. **Fixed two ways**: (a) copied `_xlsx_recalc_fix.py` (from the GBC Smart-KINMU project, see that memory for the module's own history) into `~/CASExport/`, fixed a latent bug where `fix_and_recalc()` didn't return `force_excel_recalc()`'s success/failure (silently made `if not fix_and_recalc(...)` always falsy), and added a defensive check inside `force_excel_recalc()` — after opening the target file, verify `get name of active workbook` actually matches the expected filename before proceeding, aborting otherwise (protects against a stray `Book1` or another already-open file becoming the accidental target of the save/close calls — this exact failure mode was observed once mid-session when Excel was mid-transition from a prior file). (b) Wired `fix_and_recalc(FILE1_TO_DATE, wait_seconds=60)` into `cas_monthly_pipeline.py`'s `process_month()` right after the `append_rows_to_workbook(FILE1_TO_DATE, ...)` call, so every future automated run re-caches formulas automatically. **`file2` (CAS集計フォルダ) was checked and found to have the same empty-cache issue but confirmed harmless** — its ~574 formula cells are all in a template/buffer row range (row 1229+) beyond the real data (`last_row`=1228), so no fix was wired in for file2, just verified via manual `fix_and_recalc()` once that day.

**Bug 4 — concurrent execution corrupted timing, not data.** While debugging Bug 1-3 interactively, a manually-launched `cas_monthly_pipeline.py` run and launchd's independent 20-minute-interval trigger overlapped, both converging on `GBC CAS実績_FY22 TO DATE.xlsx` around the same time (this is what Bug 2's multi-minute "hang" made possible — a normal <1s run wouldn't have overlapped a 20-min interval). Caught before real corruption happened: both processes were killed, launchd was `unload`ed, a single clean run was done, then launchd was `load`ed again. No lasting damage, but confirms Bug 2 needed fixing regardless of whether it was "just slow" — a 10-20 minute single-file operation lasting longer than the polling interval is inherently unsafe for a script that writes to shared state.

All four fixes are live in `~/CASExport/cas_pipeline_lib.py`, `cas_monthly_pipeline.py`, and the new `~/CASExport/_xlsx_recalc_fix.py`. The end-to-end run that day did successfully land 08月分 (87 raw rows → 95 output rows after profit-split, ¥29,687,397 gross profit) into masaki.nakamura's own OneDrive copy of file1/file2, verified via direct openpyxl re-read after the recalc fix.

## RESOLVED 2026-09-03 — root cause was a hidden column outside the pipeline's known schema, not the OneDrive/Power BI sync mystery

The 2026-09-02 "UNRESOLVED" investigation above was a red herring in one respect: it correctly showed the DAX model had 0 rows for 2026-08, but the actual cause wasn't sync/caching between accounts — it was that **file1's Raw YTD sheet has a 16th column, P, header "DATEVALUE"**, holding a per-row formula `=DATEVALUE(E{row}&"/"&SUBSTITUTE(G{row},"月","")&"/1")` that Power BI's Raw YTD query relies on to get a real date type. `OUTPUT_COLUMNS` in `cas_pipeline_lib.py` only covers columns A:N (14 cols) — `append_rows_to_workbook()` never touched column P at all, so every August row it appended had a **blank P cell**, and Power BI's date-typed filtering silently excluded all of them (0 rows via DAX) even though the 14 known columns were completely correct. Column O (15) is a legitimate blank spacer with no header — not a bug, just noise between N and P.

The user found this themselves by manually inspecting the sheet ("自分で色々と試したら原因が分かりました") after my own diagnostic pass (DAX query, refresh history, Excel Online view, Power Query preview — see the ブラウザでの原因究明手順 exchange this session) failed to catch it, since none of those steps look at the raw column structure of the source file itself. He was explicit that this was a data-verification gap on my part ("あなたのデータ確認不足で原因究明に時間がかかりました") — see [[feedback_verify_full_schema_before_pipeline_writes]].

**Fix applied to `~/CASExport/cas_pipeline_lib.py`** (generalized, not a P-column special case, so any *other* hidden formula/value column added later is handled automatically):
- `detect_last_header_col(ws)`: scans row 1 beyond `OUTPUT_COLUMNS` to find any column with a header (catches P/"DATEVALUE" and would catch a future Q/R/etc.).
- `shift_formula_row_refs(formula, source_row, target_row)`: rewrites same-row cell references (e.g. `E6114`→`E6115`) so a formula copied from the row above works correctly in the new row.
- `append_rows_to_workbook()`: for every such extra column, copies the previous row's formula/value into each newly appended row (with row refs shifted), and **raises `ValueError` before saving** if any extra-column cell that should have been filled ends up blank — so a future variant of this exact bug fails loudly (blocks the save, triggers the existing error-path Teams notification, pipeline retries next run) instead of silently producing a half-correct file again.
- `extend_raw_ytd_table_if_present()`: was hardcoded to truncate any Excel Table's ref to column N on extension — fixed to preserve whatever end column the table actually had (currently a no-op either way since neither file1 nor file2 has an Excel Table object defined, but would have silently re-created this exact class of bug if one were added later).

**Verified** against a scratch copy of file1 only (`/tmp/cas_test/`, deleted after): single-row and 3-row appends both correctly wrote `=DATEVALUE(E{new_row}&...)` into column P with the right row number; column O (blank header) correctly left untouched with no false-positive error. Production file was not touched by this test. The real production file1 already has August's P column filled in — the user fixed it manually themselves before asking for the pipeline fix, so no backfill of past data was needed, only the forward-looking code fix.

## 個別・事後の利益スプリット反映と、青字が透明になるopenpyxlの落とし穴 (2026-09-07)

**重大バグ発見・修正**: `cas_pipeline_lib.py`の`BLUE_FONT_COLOR = '0000FF'`(6桁RGB文字列)を`Font.color`に代入すると、openpyxlが自動的に`'000000FF'`(アルファ00=完全透明)へ変換してしまい、スプリット行の「青字」マーキングが実質見えなくなる。file1側はたまたま`_xlsx_recalc_fix.fix_and_recalc()`(Excelアプリ経由の保存)が色情報を正規化してくれるため症状が出なかったが、file2(CAS集計側)はこの再計算処理を経由しないため透明のまま残っていた。**修正**: `BLUE_FONT_COLOR='FF0000FF'`、`RED_FONT_COLOR='FFFF0000'`(8桁ARGBで明示)に変更済み。次回の自動パイプライン実行(次回9月分の新規split適用時など)で、file2側の青字が正しく見えるか要検証——もし既存のARCHION等の過去行が正しくFF0000FFだったのは、file1由来のfix_and_recalc経由の偶然の副作用だった可能性が高い。

## 青字継承バグ (2026-10-05修正)

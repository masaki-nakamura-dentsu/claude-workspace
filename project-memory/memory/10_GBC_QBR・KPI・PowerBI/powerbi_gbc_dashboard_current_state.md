# 2. Salesforceオブジェクト構造の要点

- 案件マスタ・月別明細ともに単一オブジェクト**`GBC__c`**(和名「GBC案件/Items」)に同居。`RecordTypeId`の`レコードタイプ名`が`"年度月別明細（GBC）"`の行が月別子レコード、それ以外(かつ空でない)がマスタ行。
- 月別子レコードは`SalesByYear_GBC_parent__c`(和名「月別見込親案件」)で親(マスタ)行への自己参照ルックアップを持つ。
- 主要フィールドAPI名対応(マスタ側):

| 表示ラベル | API名 | 備考 |
|---|---|---|
| 案件名/Item title | `Name` | |
| 部署名/Dept. | `GBCorgChoice__c` | `GBCDepartmentName__c`(未使用)・`GBCOrg__c`(非表示予定)は**ニセの候補、使わない** |
| 地域/Region | `GBCArea__c` | |
| 市場/Market | `GBCCountry__c` | ラベルは「Market」だがAPI名は`Country`のまま(過去の改名の名残) |
| 事業(業務)区分 | `GBCJU__c` | 市場と同じくSalesforce**複数選択リスト**(セミコロン区切り) |
| クライアント/Client | `GBCClient__c` | Accountへのルックアップ、Name展開が必要。`GBCParentClient__c`/`GBCClientName__c`は不採用(2026-08-24決着、詳細は[[powerbi_migration_gbc_dashboard]]参照) |

- 月別子レコード側の主要フィールド: `Year__c`(年度、**テキスト型選択リスト、数値比較には`Number.From()`が必須**)、`Month__c`(月、同様テキスト)、`Accuracy__c`(確度、A/B/C/X/空欄)、`GBCSettingSales__c`(見込売総)、`GBCGross__c`(Group売総)、`GBCMonthContributionGross__c`/`GBCMonthContributionGrossF__c`/`GBCMonthContributionGrossP__c`(貢献売総A/AB/計上)、`GBCGMauthorize__c`(GM承認)、`GBCMonthDupChk__c`(重複確認フラグ)、`GBCParentorgChoice__c`(月別集計用/部署名)。
- **貢献度(`GBCContributionPercent__c`)はSalesforce APIだと0〜100の生値で返る**(旧Excelは0〜1に正規化済みだった)。`GBC_月別_自己結合_Base`の最終ステップで`/100`済み。
- **案件IDの桁数**: Salesforceオブジェクトコネクタ経由は18桁形式、旧`案件_Dim`(SF案件リスト由来)は15桁形式だった不一致が過去に発生。現在は`GBC_月別_自己結合_Base`および新`SF案件リスト`の両方とも、最終ステップで`Text.Start(_, 15)`により**15桁に正規化統一済み**。新しいSalesforce起点の結合を書く時は必ず両側の桁数を確認すること。

# 5. メジューの設計パターン(evergreen、新規メジュー作成時に必ず踏襲)

1. **SelectedYear/SelectedMonthパターン**: `計上年`スライサーが月/四半期の軸と同じ行で使われる場合、`SELECTEDVALUE('Raw YTD'[計上年])`はデータの無い将来月でBLANKになる。必ず`CALCULATE(SELECTEDVALUE(...), ALL('四半期'), ALL('月'))`で軸テーブルを先にクリアしてから読む。
2. **多対多ブリッジの「すり抜け」対策(CONTAINSSTRING方式)**: CAS由来ファクト(Raw YTD、案件ID未確定行を含む)は、市場/地域/事業区分スライサーを選択しても案件ID空欄行が素通りしてしまう。行レベルのテーブルには`市場一致`等の`=1`ビジュアルフィルタ(整数、真偽値ではなくINT)、集計メジューには`FILTER(ALL(col), NOT ISFILTERED(bridge) || COUNTROWS(FILTER(VALUES(bridge[col]), CONTAINSSTRING(fact[col], [col])))>0)`をCALCULATE内に追加。Salesforce由来ファクト(CAS見込/貢献実績/貢献見込)は案件ID欠損がないため、このパッチ不要でリレーションシップだけで機能する。
3. **TREATASパターン**: 物理リレーションシップが「列 ''(テーブル '')には重複する値...」エラーで作成できない場合(`クライアント_Dim`/`案件_Dim`で複数回発生、実データに重複は無いことを確認済みの既知プラットフォームバグ)、諦めてTREATASで代替するのが確立した標準対応。
4. **DAX計算列 vs Power Query列**: 月/年関連のDAX計算列(`=MONTH([DATEVALUE])`等)を`FILTER(ALL(col), ...)`のような上書きフィルターで使うと、型表示は正しく見えても謎にBLANKを返すことがある(このプロジェクトで複数回・複数テーブルで再発済みの既知バグ)。**月/年関連の列は必ずPower Query側のネイティブ列として作り、型変換を明示すること**(`月番号2`パターン)。
5. **「遡及」機能(月スライサーでas-of表示)を作る時の4点セット**: ①軸テーブル(月/四半期)と関係のある全ファクトテーブルを洗い出す ②各ファクトの月列がDAX計算列かPower Query列か確認 ③`ALL(DimTable)` + `FILTER(ALL(FactTable[nativeCol]), cond)`の両方をセットで使う ④同じ概念(前年・予算等)を参照する全上位メジューを同時に差し替える。
6. **IFはテーブルを返せない**: `IF(cond, CALCULATETABLE(...), ALL(...))`のような分岐はエラーになる。テーブルVARの分岐が必要な場合は、CALCULATE呼び出し自体を条件分岐の外側に出し、スカラー分岐(ネストIF)で複数の完全なCALCULATE呼び出しを書く。
7. **VAR名はASCII必須**: ブラウザ版DAXエディタは日本語VAR名で構文エラーになる(テーブル/列/メジュー名は日本語OK)。
8. **カード用の百万表示**: カードビジュアルに表示単位ドロップダウンが無いため、`FORMAT([測定値]/1000000,"#,##0") & "M"`でテキストメジューとして返す(`_M`サフィックス)。
9. **マイナス値の赤字表示**: メジュー側カスタム書式コード`[Red]`はリテラル表示されるバグがある。visual側の条件付き書式(セルの要素→フォントの色→ルール、開始条件は必ず「≥」)で対応する。
10. **平均は加重平均が正しいことが多い**: `AVERAGE(貢献率列)`のような単純平均は要注意、`DIVIDE(SUM(計上済), SUM(元の金額))`のような加重平均が正しいケースが多い(貢献度平均で実際に誤りが発覚した実例あり)。
11. **DAXクエリビューでの日本語テーブル名**: `'CAS見込'[...]`のようにシングルクォート必須。通常メジュー内では不要だが、DAXクエリビュー(EVALUATE〜)特有の罠。
12. **M(Power Query)側の特殊文字列名**: `[#"クライアント/Client"]`のようにスラッシュ等を含む列名は`#"..."`で囲む。この2つ(DAXのシングルクォート・Mの#"...")を混同するのがこのプロジェクト最頻出のシンタックスエラー。
13. **複数選択リストのブリッジテーブル、ファクト側IDがユニークなら多対多ではなく一対多+双方向で十分**(2026-08-31、JCI_Pitch_Baseで確認): 既存の市場_Bridge/事業区分_Bridge/地域_Bridgeが多対多なのは、Raw YTD側の案件IDがCAS明細で重複するため。ファクトテーブル側で`Table.Distinct(...,{"Id"})`済みでIDがユニークな場合は、通常の一対多(ブリッジ側が多)+クロスフィルター両方向で足り、多対多特有の「重複値」警告も出ない。
14. **カテゴリ軸で「値が0件のカテゴリも表示」したい場合**: 軸フィールドがファクトテーブル自身の列だと、フィルタで該当行が0件になったカテゴリは軸から消える(既定挙動)。独立したディメンションテーブル(小さな手動テーブルで可)を作りリレーションシップで繋いだ上で、軸をディメンション側の列に差し替え、ビジュアルの「空の値を表示」をONにする必要がある。**この設定はPower BI Web版では書式ペインになく、軸/凡例フィールド自体の「∨」ドロップダウンメニューにある**(探す場所を間違えやすい)。
15. **貢献売総の列取り違え(2026-09-06確定)**: Salesforceに似た名前の2列(`Att.Rev(A)`=`GBCMonthContributionGross__c`/`Att.Rev(計上)`=`GBCMonthContributionGrossP__c`)があり、前者はGM承認の有無に関わらず値が入るが、後者はGM承認=Falseなら必ず0(例外なしで確認済み)。QBRの「貢献実績(計上済)」は必ず`Att.Rev(計上)`を使うこと。`貢献実績`テーブルの7メジュー(貢献実績_合計/貢献度平均/貢献実績_全期間合計/貢献度平均_全期間/貢献実績_前年合計/貢献度平均_前年/貢献実績比率)全てがこれで統一済み(2026-09-06)。同テーブルのPower Query行フィルタも、部署リストから「業管/NS部/HRM/局付け」を除外し確度を`="A"`の厳密一致に修正済み。詳細・検証手順は[[qbr_powerbi_tableau_verification_20260906]]。
15. **Tableauのtwbファイル(XML)は色・フィルタだけでなく列順序・ソート条件も復元できる**: 対象ワークシートを`<worksheet name='...'>...</worksheet>`でgrep/パースすれば、`<rows>`/`<cols>`タグから正確な列順・フィルタ条件・ソート条件が取得できる。画像の目視や推測に頼らず、twbが手元にあれば直接読むのが最も確実(2026-08-31、`ALL ITEM+`ワークシートの再現で有効だった)。

# 6. 既知のバグクラス一覧(再発時にすぐ気づけるように)

1. **カーディナリティ方向逆転バグ**: リレーションシップ作成ダイアログの「テーブルから」が多側という直感と逆の挙動(§4参照)。
2. **DAX計算列のALL()上書きフィルター無効化バグ**: §5-4参照。
3. **空欄クォートの重複値エラー(プラットフォームバグ)**: 「列 ''(テーブル '')には重複する値...」、実データに重複なしを確認しても直らない。TREATASで回避。
4. **IFがテーブルを返せないバグ**: §5-6参照。
5. **クエリの「読み込み無効化→再有効化」でリレーションシップ・DAX計算列が消える**: 本番クエリのデータソースだけ差し替えたい時は、クエリのリネーム・無効化ではなく**既存クエリのM式を直接丸ごと上書き**する方式を使うこと(テーブル実体を維持するため安全)。
6. **Table.Distinctのキー選択ミスによるファンアウト**: 複合キーでdedupすると、意図と異なる粒度で重複が生き残り、後続の結合で行が増殖する(2026-07-27の11,106,923円ズレの実例)。総額が合わない時は必ず疑う候補の一つ。
7. **ページ内の「すべて」スライサーでも診断は要注意**: 過去、市場/地域/事業区分の多対多ブリッジ関連で、フィルターなしの時だけ想定と違う挙動が出た事例が複数ある。総額不一致の切り分けは「フィルターありは正しいがフィルターなしだけ違う」パターンかどうかをまず確認する。
8. **スライサーの「クリア」と「フィルター」ペインのカードは別物(2026-08-26)**: ページ上のスライサーをすべてクリアしても、ビジュアル/ページ/レポートレベルの「フィルター」ペインに個別設定されたフィルターカード(基本フィルターや、`市場一致`のような詳細フィルター)は一切解除されない。総額調査で「スライサーは全部消した」という報告だけを鵜呑みにせず、必ずフィルターペインの中身(3区分すべて)を直接確認すること。
9. **「絞り込むと合計が増える」ように見えたら負の値を疑う**: `売上総利益`はマイナス値(訂正・戻し等)を含みうる。除外フィルターをかけると表示合計が直感に反して増えることがある——これはバグではなく、除外された行群の合計がネットでマイナスだった場合に数学的に正しく起こる現象。総額が「絞り込むと増える」パターンを示したら、除外対象行の合計値がマイナスかどうかをまず確認する。
10. **ビジュアルレベルのフィルターはビジュアルごとに個別設定が必要**: `市場一致`/`事業区分一致`のような詳細フィルターをテーブルに設定しても、同じページの別のビジュアル(ランキングチャート等)には自動適用されない。同種の絞り込みを複数ビジュアルに効かせたい場合は、ビジュアルの数だけ同じフィルターを個別に追加する必要がある。新しいビジュアルを追加した時は、既存ビジュアルと同じフィルター構成になっているか都度確認すること。
11. **多対多ブリッジのクロスフィルター方向が逆転すると「絞り込んでも件数が一切変わらない」症状になる(2026-09-05確定)**: リレーションシップ編集ダイアログの「テーブルから」欄がBridge側になっていても、「クロスフィルターの方向」が意図と逆(Fact→Bridgeの単一方向)になっていることがある。この場合、Bridge側のスライサーはFact側に一切影響しない(0件になるのではなく、フィルター自体が伝播しないため全件のまま変化なし)。**切り分けのコツ**: スライサーで絞り込んだ時に①件数が0件になる→キー値の不一致を疑う、②件数が全く変わらない→クロスフィルター方向 or アクティブ設定を疑う。再構築したブリッジリレーションシップは、保存前に必ずこのプロパティを目視確認すること(バグクラス1「テーブルからが多側という逆転」の親戚だが別物、方向は別途要確認)。
12. **`〇〇一致`系CONTAINSSTRINGメジューはテーブルごとに専用版が必要、使い回すと「絞り込んだ瞬間に全消え」する(2026-09-05確定)**: `見込市場一致`/`貢献見込市場一致`のような詳細フィルター用メジューは`SELECTEDVALUE('特定のテーブル'[列])`で参照テーブルがハードコードされている。似た名前・同じ目的のメジューが複数テーブル分存在する時、間違ったテーブル用のものを別テーブルのビジュアルに適用すると、対象列が常にBLANKと評価され`IF(ISBLANK(...), 0, ...)`分岐で0を返し続ける。**厄介な点**: フィルター無し(`NOT ISFILTERED`分岐)の時は1を返すため一見正常に見え、実際に絞り込んだ瞬間に初めて全消えするので気づきにくい。ビジュアルに`〇〇一致`系フィルターを追加する前に、必ずそのメジューのDAXを開いてどのテーブルの列を参照しているか確認し、ビジュアルの元データテーブルと一致するものを選ぶこと。
13. **DAX計算列/メジューのVAR名を日本語(全角)にすると新しい列エディタで構文エラーになることがある(2026-09-07確定)**: `VAR 今月初 = ...`のように全角文字始まりのVAR名を使うと「無効なトークン」パースエラーが発生した実例あり。テーブル名・列名・メジュー名自体は日本語で問題なく通っている(既存資産多数)ので、日本語NG自体はDAX言語仕様ではないが、VAR名は`ThisMonthStart`のような英数字にしておくと確実に回避できる。DAXで謎の構文エラーが出たら、まずVAR名が日本語でないか疑うこと。
14. **PowerBI Appの「複数オーディエンス」機能はページ単位の個別制御が実質使えない/ワークスペースメンバーには効かない(2026-09-14確定)**: JCI関連ページだけ他部署に見せたい要望に対しオーディエンス機能を試したが、①コンテンツ選択画面でレポートを展開してもページ単位の表示/非表示トグルがクリック操作不可(表示崩れではなく機能制約と判断、ブラウザ倍率変更・別ブラウザでも改善せず)、②オーディエンスにワークスペースメンバーを追加すると「アクセス権を付与する相手」欄から消えて「ワークスペースのユーザー」欄に統合され、その人はワークスペース直接アクセス経由でページ制限を完全にすり抜けられる(Appのオーディエンス制限はワークスペース非メンバーにしか実効しない)。**回避策として確立**: 見せたいページだけを含む専用の複製レポートを作り(Service上で「名前を付けて保存」、データセット接続は自動的に維持される)、その複製レポートだけを対象オーディエンスに割り当てる方式に変更。詳細経緯は[[work_status/powerbi_jci_app_audience_access_20260914]]参照。

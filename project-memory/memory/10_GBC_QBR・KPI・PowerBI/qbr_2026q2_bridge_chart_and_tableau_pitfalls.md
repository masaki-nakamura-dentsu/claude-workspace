## Tableau sort-by-field pitfalls (found in `1. QBR_CAS実績 V1.0.twb` and `4. QBR_貢献実績 V1.0.twb`)
Both files' クライアント別 bar-chart worksheets had `並べ替え`(sort) set correctly (`computed-sort ... direction='DESC' using=[sum:売上総利益]`) but displayed order looked wrong. Root cause, confirmed by reading the `.twb` XML directly (not guessable from the UI alone):
- The sort's `using` field is a **plain SUM**, computed over the *full current filter context* — which includes a prior year kept in the query only to feed the `LOOKUP(-1)` 前期差 table calc. That prior year is excluded from **display** via a `kind='hide'` filter, but hidden ≠ excluded from aggregation. So the sort key silently became "this-year + last-year combined", not the single displayed quarter.
- Fix that actually works: a **non-table-calc LOD field** isolating just the target period, driven by **Tableau parameters** (`対象年`/`対象四半期`) rather than hardcoded literals so it never needs editing again:
  ```
  {FIXED [クライアント名（調整後）] : SUM(
    IF YEAR([DATEVALUE])=[対象年] AND DATEPART('quarter',[DATEVALUE])=[対象四半期]
    THEN [売上総利益] END
  )}
  ```
  Table-calc fields (e.g. `売上総利益（直近）`, `LOOKUP(...,LAST())`) **cannot** be used in the sort dialog's フィールド dropdown at all (circular addressing) — don't waste time looking for them there.
- Aggregation choice matters: if the LOD's granularity doesn't match the sort dimension's, use 最小/最大 in the 集計 dropdown, **not 合計** — 合計 multiplies the value by however many detail rows share it, scrambling the order in a new way (this bit us mid-session; changing 最小⇄最大 didn't help because the *real* bug was elsewhere that time — see below).
- **Bigger trap, easy to miss**: Tableau crosstab **quantitative filters based on the CURRENT period's value** (e.g. `売上総利益（直近）>= 10000`, `貢献売総（直近）>= 1000000`) silently drop any client whose *current* value is below threshold **from the entire export, including their historical/prior-period contribution**. This made every "previous period total" derived from a Tableau crosstab export understated by the full churned-client amount (e.g. Qiddiya ¥16.7M vanished from a CAS prior-period total because its 2026 value was 0). Always suspect this when a period-over-period total looks implausibly low for the earlier period specifically.

## Bridge (waterfall) chart methodology — built natively in PowerPoint, not Tableau
Tableau has no native waterfall chart type; recreating one via Gantt-bar + running-sum + Union scaffolding was judged too fragile for this data-source setup (relationships, not physical joins). Instead: computed the numbers in Python from Tableau's own exported crosstabs (or, more reliably, straight from the underlying source `.xlsx` — see below), then built a **stacked-column chart in python-pptx** as the classic manual-waterfall trick: 4 series (`基準` invisible/no-fill, `合計` dark for start/end totals, `減少` red, `増加` blue), custom per-point data-label text (needed for negative-sign display since bar heights must stay non-negative magnitudes). Category buckets: top-3 named movers each direction + `その他(増加/減少)` catch-alls, to keep ~10 bars readable.
Reusable build script pattern: `/private/tmp/.../scratchpad/build_bridge_final.py` (this session's scratchpad — not persisted, rebuild the technique from this description if needed again).

## Getting the numbers right — do NOT trust one aggregation path
This was the hard part and took several iterations:
1. **CAS (売上総利益) H1**: independently recomputed straight from `GBC CAS実績_FY22 TO DATE.xlsx` (Raw YTD sheet) + `Client Name_CAS_SF_FY22 TO DATE.xlsx` (List sheet, join on クライアント名) — matched the user's own reference cumulative export almost exactly (2026: exact match; 2025: within 1%, a ¥1.5M residual never fully explained but immaterial).
2. **貢献売総 H1**: naive full-year raw recompute gave 2025 H1 ≈ ¥1.03B, wildly inconsistent with what should've been a comparable live snapshot. Root cause never fully resolved (something about how the 確度 tag convention differs for elapsed vs. in-progress fiscal years — see [[qbr_0708_rollback_tableau]] for the *other* known 確度A inconsistency in this data ecosystem — this may be a third, related but distinct quirk). **Resolution that worked**: went to the actual **official, previously-published `GBC QBR 2025Q2_final20250806.pptx`** deck and read the literal "実績（計上済）" figure off its Tableau-exported dashboard image (¥1,007,855,121) — this is the authoritative, already-vetted number, and no amount of raw-data archaeology should override an already-published official figure when one exists. For 2026's side, matched the *exact* figure already validated against `【GBC】26年度業務指示書` (¥1,064,644,956, confirmed = 確度='A' rows summed across the full fiscal year with **no month restriction** — this "no month filter" nuance is deliberate: GM-approved future-month deals get counted as booked ahead of their calendar month, so the KPI is a moving "confirmed so far this FY" figure, not a strict period revenue figure).
3. **Client-level breakdown for the 2025 anchor**: no historical per-client Tableau snapshot survived (the `GBC 貢献実績+見込_COMBINED.xlsx` file was itself rolled back/overwritten in a prior session, see [[qbr_0708_rollback_tableau]]) — used the best available raw H1-Jan-Jun client mix as a proxy, proportionally rescaled so the total ties exactly to the official ¥1,007,855,121 anchor. Individual client deltas in that specific chart are therefore approximate; the total is exact.

**Lesson for next time**: when a Tableau-derived total looks even slightly off from what the user remembers, don't just recompute harder from raw data — first check whether an **already-published, officially-reported PPTX/deck** exists for the comparison period. That beats any from-scratch recomputation, since it's what was actually presented to executives at the time and any subsequent data-source rollback/correction can no longer be un-done from raw tables alone.

## Japan Client pitch "Won" YTD apparent decrease — resolved, not a bug
User noticed the Won total in `7. QBR_Japan Client ピッチ状況` dropped from Q1 (¥5,347K) to Q2 (¥2,814K/¥3,380K gross) snapshot exports and asked to root-cause it, since a YTD cumulative should only grow.
- **Sub-finding 1 (not a bug)**: "Net Win" ≠ gross "Won" bar by design — `Net Win = SUM(Offensive∩Won) − SUM(Defensive∩Lost)` (literally titled "Off&Won-Def&Lost" in the chart). They coincidentally matched in Q1 only because Defensive-Lost happened to be ¥0 then.
- **Sub-finding 2 (real data-entry fix, confirmed normal by user)**: found monthly dated Salesforce export snapshots preserved at `.../日系ターンアラウンド報告(JCI)／毎月/AllpitchList_Original/` (filenames carry the export timestamp, e.g. `APAC Pitch - List All_v1.31-2026-05-13-14-05-04.xlsx` — this folder is the place to look for **any** future "why did a YTD number move backward" question on this data source). Diffed the 2026-05-13 snapshot against the current live file: 3 deals (Uniqlo メディアピッチ, Uniqlo 26SS/26FW, トヨタ レクサス大型車ブランディング) had their **foreign-currency amount** (not just the GBP conversion — the underlying JPY/KRW/CNY source figure itself) corrected down by an exact 10× factor between June and July 2026, together accounting for ¥4.04M of the ¥2.3M net apparent decrease (the rest of the gap is genuine new wins). User confirmed this 10x correction was a known, already-resolved June data-quality fix — not a new issue.

## How-to for future "why did this Tableau number change" questions on this data ecosystem
1. Check if an official published deck exists for the comparison period — prefer its stated figures over recomputing.
2. If recomputing from raw `.xlsx` sources is unavoidable, check `Client Name_CAS_SF_FY22 TO DATE.xlsx`'s `List`/`List - Project` sheets for the exact join key Tableau uses (relationship vs. physical join — check the `.twb`'s `<relation>` block, don't assume).
3. For "a cumulative total shouldn't shrink" questions, look for dated monthly snapshot folders (pattern: `.../毎月/...Original/` or similar) before concluding it's a bug — GBC's Salesforce-sourced pitch/pipeline data gets corrected in place fairly often.

## FY25 CAS "which deals weren't forecasted at Q2 but got booked by year-end" extraction (2026-07-28, same session)
Task: find the ~¥146M of FY25 CAS 売上総利益 that materialized by year-end but wasn't in the Q2-end (確度 A/B) forecast. Full working method, reusable for FY26 or any future year's equivalent question:

1. **Confirm the aggregate gap first, from KGI-level summary files** — `GBC実績・見込数字（20XX年度）_...（Q2終了時点）.xlsx` vs the equivalent `...（Q4終了時点）...xlsx`, sheet `サマリー（月別見込・予算）`, row `売上総利益（部門利益）`. The "今月時点見込" row's 総計 in the Q2 file (¥289,766,183) is the official Q2-time full-year forecast; the same row in the Q4/year-end file (¥435,524,798) is the final actual. Jan–Jun cells are identical between the two files (already-actual months don't get revised); the Jul–Dec cells are what moved. This confirmed the ¥145,758,615 gap (≈¥146M) the user remembered, and pins down which measure (売上総利益, not 設定売総/取設定) is in scope.
2. **The embedded "月別見込（設定売総 X 部署）" deal-level pivot sheet inside these summary workbooks is STALE and reused verbatim across versions** — checked both the Q2 file and the Q4 file's copy of this sheet: byte-identical, both generated 2025-05-14 (visible in row 3's timestamp). Editing/diffing this sheet is a dead end; it was never regenerated when the surrounding workbook got re-saved for later checkpoints. Always check the embedded generation timestamp (row 2-3 of these Salesforce-report-export sheets) before trusting a "Q2" or "Q4" label in the filename — the label describes the *summary* sheets' vintage, not necessarily every embedded sheet's.
3. **Better deal-level Q2-time forecast source**: `Archive - Data for Tableau/20250723/GBC CAS見込_LATEST.xlsx` (sheet `CAS見込`) — a proper Salesforce pipeline export with 確度 A/B/C/X per 案件, dated 2025-07-23 (8 days before Q2 close, much better vintage than the stale May-14 sheet). This `Archive - Data for Tableau/` folder has dated subfolders (`20250520`, `20250626`, `20250723`, `20250905`, `20260213`, `20260302`, ...) each holding a full snapshot of the whole CAS/貢献 file family — **this is the general-purpose place to look for "what did the data look like as of date X" for any past quarter**, parallel to the pitch-list snapshot folder noted above.
4. **Best single source for the aggregate month-by-month reconciliation**: `.../GBC戦略企画部_GBC設定実績・見込/CAS集計/` has per-month subfolders (`2506`, `2507`, `2508`, ... `2601`, `2602`...) each with that month's actual-detail files. Inside `2507/` (i.e. captured right at Q2-close, dated 2025-08-04) sits `【実績確定】2025下期収益月次見込み_0804.xlsx` — a clean H2-by-month forecast-vs-budget table (sheet `下期`) that is the single best "what did July-end think H2 would look like" artifact found. Diffing its per-month 部門利益 forecast against the eventual actual month-by-month showed **October alone accounted for ¥70.8M of the ¥146M gap** (forecast ¥11.7M vs actual ¥82.5M) — over 47% of the whole-period gap concentrated in one month. Always do this month-by-month breakdown before deal-hunting across the whole H2 — it tells you where to concentrate.
5. **Deal/client-level extraction, once the target period is narrowed**: match `Raw YTD` actual クライアント名 (from `GBC CAS実績_FY22 TO DATE.xlsx`) against the confidence-A/B-only client list from step 3's pipeline export. Exact string match fails badly (companies are written prefix-style `(株)資生堂` in one source, suffix-style `資生堂株式会社` in another, plus half/full-width kana differences) — needed a normalizer that: converts to full-width, uppercases, **strips all parenthetical annotations entirely** (not just corporate suffixes — sub-project tags like `(制作作業)` are common), then strips a list of corporate-entity tokens (株式会社/(株)/有限会社/合同会社/LLC/Inc./Co.,Ltd./Corp./Pte.Ltd./K.K./GK/S.A....) from both ends, then does **substring containment either direction** (not exact equality — `カネボウ化粧品` vs pipeline's bare `カネボウ` needs this). Even so, expect residual noise (~a few % of matched value) — treat the resulting "not found" list as a strong candidate list for human review, not a final answer.
6. Final deliverable saved as `.../QBR_2026Q2/2025Q2見込になく最終的に売総計上された案件リスト.xlsx` — sheet `クライアント別集計` (client-level rollup, 49 clients, ¥130.2M) + sheet `unforecasted_deals_h2_2025` (158 individual クライアント×件名 rows). Biggest single items: ANNAPURNA GAMES,LLC TGS2025 (¥16.5M, entirely new client relationship) and a client literally named `ダミー広告主`("dummy advertiser", ¥8.9M, 件名 "2025年12月のボリュームディスカウント" — looks like a placeholder/bulk-adjustment entry rather than fake data, but flagged to user for their own sanity-check since the client name itself is a red flag worth a second look).

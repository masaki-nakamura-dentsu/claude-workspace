# 構造的問題: 「実績+A+B系の達成度」を3つの独立したDAX式が別々に計算
- `★CAS貢献売総_見込み整理`のカード: `達成率_A後`/`達成率_AB後`(専用メジュー、`実績_A後`=`[売上総利益_遡及]+[見込A_合計_部署別]`等)
- `★予算達成トラッキング`上の横棒グラフ: `積み上げ値`(`凡例_実績見込[項目]`を軸にした集計、実績部分=`[指定指標_年別]`)
- `★予算達成トラッキング`左下の折れ線グラフ: `実績見込_累計`(月次累積、別立てのロジック)
- `★予算達成トラッキング`KPIテーブルの「達成度(見込)」行: `達成度_見込`(=`DIVIDE([年度着地見込],[予算_年間合計])`、`年度着地見込`=`SUMX(VALUES('凡例_実績見込'[項目]), [積み上げ値])`)

同じ指標に対し独立した計算パスが並存する既存パターン([[qbr_powerbi_tableau_verification_20260906]]発見6/7と同種)。

# 根本原因(DAX式レベルで確定、高確度)
`Raw YTD`テーブルに最新実績月を判定するメジューが2本存在:
- `自動検出_最新実績月番号`(**正**): `CALCULATE(MAX('Raw YTD'[月番号2]), ALL('Raw YTD'), 計上年=SelectedYear)` — Power Queryネイティブ列`月番号2`使用
- `最新実績月番号`(**バグ**): `CALCULATE(MAX('Raw YTD'[月番号]), ALL('Raw YTD'), 計上年=SelectedYear)` — DAX計算列`月番号`(`=MONTH('Raw YTD'[計上月])`)使用。[[powerbi_gbc_dashboard_current_state]]§5-4/§6-2の既知バグ(DAX計算列をFILTER(ALL())系で使うと信頼できない)に該当

`売上総利益_遡及`メジュー(`実績_A後`/`実績_AB後`/`年度着地見込_部署別`/`達成度_見込_遡及`の「実績」部分に使われる)は**バグっている方**`[最新実績月番号]`を`CutoffMonth`として参照している。同じ式内の見込部分(`見込A_合計_部署別`等)は**正しい方**`自動検出_最新実績月番号`を参照しており、実績と見込で最新月の判定基準が食い違う矛盾状態。`最新実績月番号`が実際より小さい月を誤検出すれば実績が過少集計され、`達成率_AB後`が本来より低く出る(71.6%<72.7%の説明と整合)。

`★予算達成トラッキング`の`達成度_見込`は月キャップなしの`[指定指標_年別]`(=`売上総利益_合計`、Raw YTD該当年の全行を単純合計)を実績として使うため、この問題の影響を受けない。

**折れ線グラフ側にも同型の別バグ**: `実績見込_累計`の`ActualCumStd`が`FILTER(ALL('Raw YTD'[月番号]), 'Raw YTD'[月番号] <= CurrentMonth)`と、ファイル内で唯一ここだけ安全でない`月番号`を直書きしている(貢献側の`ActualCumKoken`は正しく`月番号2`を使用、非対称)。これが上の横棒グラフ(`積み上げ値`)との不一致原因。

**貢献売総側**: `売上総利益_遡及`の貢献分岐は`CALCULATE([貢献実績_合計], ALL('月'))`で月キャップ自体がなく、上記バグの直接影響は受けないはず。今回のDAXレビューでは貢献側の直接原因は特定できず(構造的な3パス問題は共通して存在するため要注意)。

# 【確定・訂正】真の根本原因(2026-09-08続きセッション、正樹さんの実機検証で確定)

上記の「月番号バグ」仮説は誤りだった。正樹さんが`最新実績月番号`/`実績見込_累計`を修正版に差し替えても数字が変わらず、さらに`[売上総利益_遡及]`と`[指定指標_年別]`を同条件でカード比較したところ**245,320,639円で完全一致**(実績側は無罪と確定)。

正樹さんが★予算達成トラッキングのKPIテーブル実測値をスクリーンショットで提供:
```
実績(計上済)   245,320,639
見込A(確度100%)  52,807,111
見込B(確度50%以上) 36,450,481
見込C            36,342,000
                合計370,920,231 ← 4行を素直に足した額
年度着地見込    376,220,231 ← メジューが返す額
示達予算        467,506,000
達成度(見込)     80.5%
```
差額=376,220,231-370,920,231=**5,300,000円ぴったり**。かつ5,300,000÷467,506,000≈1.13pt——これは最初の乖離報告(72.7% vs 71.6%、差1.1pt)ともほぼ完全一致し、同一原因と確定。

**真因**: 非接続テーブル`凡例_実績見込`は`UNION(ROW("項目","実績",...), SELECTCOLUMNS(DISTINCT('CAS見込'[確度]),...))`で構築されており、`CAS見込[確度]`の実データ値{A,B,C,X}のうち**X`も自動的に項目として含まれる**。一方KPIテーブルの表示行は「実績/見込A/見込B/見込C」の4行のみで「見込X」行が存在しない。

`年度着地見込 = SUMX(VALUES('凡例_実績見込'[項目]), [積み上げ値])`はXを明示的に除外していないため、**画面上どこにも表示されない確度=Xの見込額(5,300,000円)がこっそり合算**されていた。これが「示達予算」との比率(達成度_見込/達成率_AB後系との差)を生んでいた真犯人。

同型のバグが`実績見込_累計`(★予算達成トラッキング左下の折れ線グラフ)にもあり、`FILTER(VALUES('凡例_実績見込'[項目]), [項目] <> "実績")`で**「実績」しか除外しておらずXは素通り**。一方、上の横棒グラフ(`積み上げ値`)を表示するビジュアル自体には個別に「Xを除外」という視覚化レベルフィルターが掛かっていたため、そちらはXが混入していなかった——これが横棒グラフと折れ線グラフの不一致の原因でもあった。

**結論**: ページ間・グラフ間の3つの不一致症状は全て「Xを除外する処理がメジュー自体ではなく個別ビジュアルの視覚化フィルターに頼っていたため、Xを除外し忘れた箇所(`年度着地見込`・`実績見込_累計`)だけ数字が膨らんでいた」という単一の根本原因で説明できる。

## 修正DAX(2026-09-08、正樹さんへ提示済み・適用待ち)

```dax
年度着地見込 = 
SUMX(
    FILTER(VALUES('凡例_実績見込'[項目]), [項目] <> "X" && NOT ISBLANK([項目])),
    [積み上げ値]
)
```
`実績見込_累計`は`FILTER(VALUES('凡例_実績見込'[項目]), [項目] <> "実績")`の2箇所を`[項目] <> "実績" && [項目] <> "X" && NOT ISBLANK([項目])`に変更(貢献側・CAS側の両方の`SUMX`)。全文は会話ログ参照。

**教訓**: `凡例_実績見込`のように`DISTINCT(列)`で非接続テーブルを自動生成する設計は、元データに新しい値(この場合X)が増えると**気づかないうちに集計対象が増える**リスクがある。「Xを除外する」という意図はビジュアルの視覚化フィルターとして個別に散在させるのではなく、集計メジュー自体(`年度着地見込`等の共通ロジック)に組み込むべきだった。[[qbr_powerbi_tableau_verification_20260906]]の発見6/7(同一ロジックが複数箇所に分散して一部だけ修正漏れになるパターン)と同種。

# 教訓(調査プロセス自体について)
1. **「既知バグパターン」への安易な当てはめは検証してから確定と書くこと**: 最初に提示した「DAX計算列`月番号`のバグ」仮説は、このプロジェクトで過去に確定していた別のバグパターン(`FILTER(ALL(列), 列=値)`の等号フィルターでBLANKになる)と「DAX計算列を使っている」という表面的な類似性だけで飛びついてしまい、実際は単純な`MAX()`集計だったため無関係だった。ユーザーの実機検証(「直りません」)で初めて誤りと判明。過去の既知バグを引用する時は、パターンの一致(等号フィルター vs 単純集計など)を式レベルで確認してから「高確度」と書くべきだった。
2. **pbixrayで生データが読めない(Large Semantic Model形式)時、ユーザーに実機の数字を出してもらうのが一番早い**: DAX式の机上比較だけでは「理論上は同じ値になるはず」までしか詰められず、実際の数字(KPIテーブルのスクリーンショット)を見せてもらって初めて「4行の合計と年度着地見込の差がちょうど5,300,000円」という決定的な手がかりが得られた。[[feedback_prefer_deterministic_over_llm]]の実例として、早い段階でユーザーに実測値を求める方が机上推論を重ねるより早く正解にたどり着けた。

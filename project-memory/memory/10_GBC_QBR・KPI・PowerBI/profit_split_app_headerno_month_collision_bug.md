## 事象(2026-09-11、H10-2608042240 / ホーユー（株）)

CAS会計確定タイミングのズレ(8月末に利益確定→9月頭にBP側で金額修正)により、同じ受発注ヘッダNo H10-2608042240に対して依頼月違いで2件の利益スプリット申請が発生:

- 01:51 Naoki Fujii登録: 依頼月=8月、SP2部→AP2部 2,039,355円
- 01:53 Naoki Fujii登録: 依頼月=9月、SP2部→AP2部 -1,416,249円(9月の修正差額分)

両方とも「更新登録されました」メールが届いたが、Requestsシート(`GBC_アレココ - サイトドキュメント/設定関連/GBC利益スプリット管理表.xlsx`)には9月分の1行しか残らず、8月分の行が消えていた。

## 根本原因

「登録」ボタンのOnSelect数式が既存行の検索を**受発注ヘッダNoのみ**で行っており(依頼月を見ていない)、見つかった場合は新規行ではなく既存行をPatchで上書きする仕様。そのため同一ヘッダNoで異なる月の申請をすると、後から登録した方が前の行を上書きする。[[profit_split_app_admin_cc_bug_fixed]]と同じ「登録」ボタン系統だが別原因(あちらはDeptMasterのテーブル範囲外の話、こちらはRequests行のマッチングキーの話)。

## 実施した復旧(直接Excel編集)

ユーザー承認のうえ、消えた8月分の行をopenpyxlで直接復元(`受発注ヘッダNo H10-2608042240、依頼月8月、SP2部→AP2部 2,039,355円、ステータス"更新"、備考は01:51メール本文のまま、登録者Naoki Fujii`)。Requestsテーブル(`SplitRequests`)の範囲をA1:S11→A1:S12に拡張。復元前にバックアップを`memory/backups/profit_split_20260911/`に保存済み。スタイル(日付書式mm-dd-yy、金額書式#,##0)は既存行(row10)からコピー。

## 恒久修正: 完了(2026-09-11)

ユーザーがaiconアカウントでPower Apps Studioを開き、「登録」ボタンのOnSelect数式全文を貼付。2箇所の`LookUp(SplitRequests, Trim('受発注ヘッダNo') = Trim(txtHeaderNo.Text))`(新規/更新判定用、Patch対象特定用)に`&& '依頼月' = ddRequestMonth.Selected.Value`を追加した複合キー版を提示し、ユーザーが貼り替え・保存・公開済み。動作確認はダミーヘッダNo(`TEST-0911`)で別月2回登録し、2行とも残るか確認する方式を提案済み(実施待ち)。

## CAS Raw YTD側への反映: 完了(2026-09-11)

復元したRequests行(依頼月=8月、2,039,355円)は8月分CASデータが既に確定済み(パイプラインは当月分CSV取り込み時にしかsplitを自動適用しないため、事後追加分は自動処理されない)なので、[[cas_profit_split_H10-2601045674_20260907]]と同じ手順で手動反映:

- **file1** `GBC戦略企画部_GBC設定実績・見込/QBR作成/GBC CAS実績_FY22 TO DATE.xlsx`のRaw YTDシート: 6114行目(SP2、H10-2608042240、8月、売上総利益2,039,355)を0に更新・青字化、6116行目に新規行追加(AP2、同額2,039,355、売上金額/原価金額は0、隠れ列P(DATEVALUE数式)も複製)。保存前にArchive - Data for Tableau/20260911/へバックアップ。openpyxl保存後は`_xlsx_recalc_fix.fix_and_recalc()`で数式キャッシュ再計算済み(既知バグ[[openpyxl_empty_v_tag_corruption]]対策)。
- **file2** `CAS集計/CAS集計 FY26_GBC_クライアント_件名別_final20260911.xlsx`(final20260907からコピーして新規dated file作成、既存慣習通り): Raw YTDシート1228行目を0に更新・青字化、1230行目に新規行追加(同内容)。このシートには隠れ数式列が無く(N列自体は他の空白行にはIF数式があるが実データ行は値決め打ち)、recalcは不要と判断。
- 9月分(依頼月=9月、-1,416,249円)は9月のCASデータがまだ確定・取り込みされていない(例年10月頭に確定)ため、通常の自動月次パイプライン実行時に受発注ヘッダNo+依頼月の複合マッチで自動適用される見込み。手動対応は不要、次回9月分パイプライン実行時に反映されるか要確認。

## 教訓

「受発注ヘッダNo」は会計上のキーであって一意識別子ではない(CAS側の月次確定・BP修正の都合で同じヘッダNoが複数月にまたがって使われることがある)。このアプリに限らず、受発注ヘッダNoを一意キーとして扱う他の自動化・照合ロジックがあれば同様の衝突リスクを疑うこと。

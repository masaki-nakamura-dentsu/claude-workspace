**What the VBA does**, in `modClientSearch` (standard module) + matching `Worksheet_SelectionChange`/`Worksheet_Change` in the "A__既存案件（→確認・更新）Total" and "B__新規案件（→追加）Total" sheet modules:
- **AU column (クライアント/Client, ~1061 entries)**: cell `AU5` on each sheet is a persistent search box (shows placeholder "(キーワードを入れてください)" when empty, styled light-yellow/italic-gray). Typing a substring there re-filters a hidden helper column (`EA`) via `InStr`, and rewrites the native list-validation `Formula1` on `AU6:AU800`/`AU6:AU389` to point at just the matching rows. The actual AU cells still use Excel's normal in-cell dropdown — only its source range is dynamically rewritten.
- **Multi-select columns (AX/BD/BF/BK/BN/BT — 市場/スコープ/提供サービス/競合グループ/獲得グループ/勝因敗因, backed by lists on `←選択肢`)**: clicking any data cell in these columns pops a floating panel of real Excel Form-Control checkboxes (not ActiveX, not a UserForm) positioned just to the right of the cell, with a white rectangle backdrop + border behind them. Checking/unchecking writes a semicolon-joined (no space) list into the cell, de-duplicated. Each column's option list is read live from `←選択肢` (columns H/O/Q/V/Y/AE, from row 4 down to last non-blank). The native dropdown arrow on these columns is turned off (`Validation.InCellDropdown = False`, list restriction itself is kept) since it visually collided with the checkbox panel.
- Both features work through the sheet's existing protection (no password) via targeted `Unprotect`/`Protect AllowFormattingCells:=True, AllowInsertingRows:=True, AllowFiltering:=True` around each mutation, matching the sheet's original protection exceptions.

**Mac Excel VBA limitations discovered the hard way** (all confirmed on this machine, worth knowing before attempting anything UI-heavy in VBA on Mac again):
- **No UserForms at all** — `Insert > UserForm` doesn't exist in Mac VBE. Any "popup dialog with controls" design must avoid UserForms entirely.
- **`Worksheet.CheckBoxes` collection is broken** (`_Worksheet` method fails) — use `Worksheet.Shapes.AddFormControl(xlCheckBox, ...)` instead, and index shapes via `ws.Shapes(name)`, never `ws.CheckBoxes(...)`.
- **`Shape.TextFrame.Characters.Text` fails** on Form Control shapes — use `Shape.DrawingObject.Caption` instead (the legacy control-object bridge off a live Shape reference still works even though the collection-based accessor doesn't).
- **`Shape.DrawingObject.Value`** (xlOn/xlOff) works fine for reading/writing checked state.
- **`Shape.ControlFormat.LinkedCell`** works for wiring a checkbox to a cell (tried `DrawingObject.LinkedCell` first without success; switching to `ControlFormat.LinkedCell` with a fully sheet-qualified reference `"'SheetName'!EB5"` is what actually worked).
- **`Application.Caller` inside an OnAction macro is unreliable for exact-match collection lookups** — wrap the resolving code in a manual `For Each shape In sheet.Shapes` + `StrComp(..., vbTextCompare)` loop rather than `sheet.Shapes(Application.Caller)` directly, and don't depend on it as the *only* signal (this build wires both `OnAction` and `LinkedCell`+`Worksheet_Change` in parallel as a redundancy hedge, since it wasn't fully clear which one Mac would actually honor).
- Enabling **"Trust access to the VBA project object model"** does not help automate any of this from outside VBA on Mac — Mac Excel's AppleScript dictionary doesn't expose `Application.VBE` at all (confirmed via the raw `Excel.sdef` in the app bundle), so there is no scripted/headless way to inject VBA code on this platform; all of the above had to be pasted into the VBE by hand, iteratively, with the user reporting back runtime errors each round.
- GUI automation (System Events driving the VBE) was considered and abandoned early — it would require granting Accessibility permission to the whole VS Code app (broad, and the user declined), so manual copy-paste was used for every code change in this session.

**2026-07-30 — root cause found: this is a compile error (VBA locale/codepage mismatch), not run-time error 9.** Continuing on a different Mac (d14461), the user shared a screenshot of the actual error from an India-office copy of the file (titled `India_☆8月依頼用　日系ピッチ案件リスト20260724.xlsm`): a **compile error** ("コンパイルエラーです：無効な文字です") in `modClientSearch`, with the Japanese string literals rendered as mojibake — both `Public Const CLIENT_SEARCH_PLACEHOLDER As String = "(キーワードを入れてください)"` and `Set ws = ThisWorkbook.Worksheets("クライアントリスト")` (inside `GetClientNames`) show garbled bytes instead of Japanese text. Re-decompiled our own Dropbox master copy (`.../BD部集約_JPターンアラウンド/8月依頼用　日系ピッチ案件リスト20260724.xlsm`) via `olevba` and confirmed **our master file's Japanese literals are intact** — the corruption exists only in the India-side copy, meaning it happened locally there, not in what we distributed. Diagnosis: classic VBA double-byte string-literal corruption caused by opening/compiling/saving a Japanese-locale VBA project on a Windows PC with a non-Japanese system locale/ANSI codepage (e.g. English (India)) — VBA's legacy source storage encodes literals via the OS ANSI codepage, not Unicode, so 2-byte Japanese characters get mangled on any recompile-and-save under a mismatched locale. This explains why it only surfaced overseas and never reproduced in Mac (JP-locale) testing, and supersedes the earlier "Run-time error 9 on BQ cell select, unreproduced" lead from earlier the same day — that was a secondhand/imprecise description; the screenshot is the first direct ground truth. Code-reading during this session (before the screenshot arrived) also turned up one real hardening candidate worth revisiting if the locale theory is ever disproven: `ShowMultiPanel` (line ~399) does `Set bg = ws.Shapes(BG_NAME)` and `ws.Shapes(CHK_PREFIX & i)` for i up to `MAX_MULTI_ITEMS=80` with no existence check — this collection-by-name lookup throws exactly "Subscript out of range" if a shape is ever missing, and the only place that (re-)creates missing shapes, `EnsureMultiCheckboxPool`, is only called from `Workbook_Open` (via `InitClientSearchBox` on Sheet1/Sheet3) — if macros are enabled *after* open (clicking "Enable Content" post-open, common on files with Mark-of-the-Web) rather than at open, `Workbook_Open` never fires that session and the pool never gets validated. Not needed to explain the current screenshot, but worth keeping in mind for any *other* Subscript-out-of-range report.

**2026-09-28/29 — performance fix for the multi-select checkbox panel (user reported every click on the sheet was slow, not just multi-select cells).** Root cause: `Worksheet_SelectionChange` (Sheet1.cls/Sheet3.cls) calls `HideMultiPanel` on every cell selection that isn't a multi-select column — i.e. on almost every click anywhere on the sheet — and the old `HideMultiPanel`/`ShowMultiPanel` unconditionally did `ws.Unprotect`/`ws.Protect` (expensive on an 800-row sheet with 13 cross-sheet x14 data-validation ranges) plus a `ws.Shapes("chkMultiN")` name-lookup for all 80 checkboxes every single time, regardless of whether a panel was even showing.

Fix applied to `modClientSearch.bas` only (Sheet1/Sheet3/ThisWorkbook untouched), rolled out via `10月依頼用　日系ピッチ案件リスト20260928.xlsm` (working copy) — **not yet ported back to the `Format/` master template, do that next time this file is touched**:
1. `HideMultiPanel` now exits immediately if `mMultiTargetCell Is Nothing` (no panel currently shown) — eliminates the Unprotect/Protect+shape-scan cost for the vast majority of clicks (anywhere that isn't a multi-select cell while a panel was already open).
2. Shape references (80 checkboxes + 1 background rect) are cached per-sheet in module-level arrays (`mChkShapes()`, `mBgShape`, keyed by `mChkCacheSheetName`), populated in one pass over `ws.Shapes` instead of 80 separate `ws.Shapes(name)` lookups. `ChkMultiClicked` also uses the cache (parses the index out of `Application.Caller`'s name) with the old linear-search kept only as a fallback.
3. `Application.ScreenUpdating = False`/restore wraps the shape-repositioning loops in `ShowMultiPanel`/`HideMultiPanel`.
4. `ShowMultiPanel` skips the whole rebuild if the exact same cell's panel is already showing.
5. `IsMultiSelectColumn`'s 7 `ws.Range(...).Column` lookups are now cached once (`mMultiSelectCols()`/`mMultiSelectColsInit`) instead of recomputed on every single SelectionChange.

**Tried and reverted**: removing `ws.Unprotect`/`ws.Protect` entirely from `ShowMultiPanel`/`HideMultiPanel` (theory: `ApplyMultiSelectItem` already writes to the target cell with no Unprotect at all, implying those data columns are pre-unlocked, so maybe the EB/EC helper cells could be pre-unlocked too and the whole Unprotect/Protect skipped). **This broke on first real test**: runtime error 1004 "CheckBox クラスの Caption プロパティを設定できません" — setting a Form Control checkbox's `.Caption` while the sheet is protected is NOT allowed regardless of the cell-lock state (unlike plain cell value writes), so `Unprotect`/`Protect` around the `shp.DrawingObject.Caption = itemText` loop in `ShowMultiPanel` is mandatory and was restored. Left `ws.Range("EC" & i).Locked = False` in `EnsureMultiCheckboxPool` (harmless, doesn't hurt) but the Unprotect/Protect calls themselves stayed in both `ShowMultiPanel` and `HideMultiPanel`. **Lesson**: Form Control shape properties (at least Caption) are protected independently of `DrawingObjects:=True` not being passed to `.Protect` — don't assume shape property writes are exempt from sheet protection just because plain cell-value writes are.

**Also caught after the fix**: leftover `Application.EnableEvents = False` can get stuck permanently if a runtime error aborts a sub before reaching the matching `= True` line at the end (exactly what happened when the 1004 error hit mid-loop) — this is an **Application-level** setting, not workbook-level, so closing/reopening the file does NOT clear it; only `Application.EnableEvents = True` typed into the VBE Immediate window, or fully quitting and relaunching Excel, fixes it. Symptom was "clicking a multi-select cell does nothing at all, no error" (SelectionChange never fires because events are globally disabled). Worth checking this first if the panel ever silently stops responding after a debug/error dialog was dismissed with "End".

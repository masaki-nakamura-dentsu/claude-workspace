**Key gotchas (all verified live, UI may drift)**:
- Event creation form: `https://timetreeapp.com/calendars/<id>/events/new?date=YYYY-MM-DD&referer=menu` — the `date` query param pre-fills the start date, avoiding needing to click through the date picker.
- Title is `textarea[name="title"]`. **Must use real keystrokes** (`page.keyboard.type`), not `.fill()` — `.fill()` sets the DOM value but doesn't trigger the app's React onChange/dirty-tracking, so the save button stays disabled even though the value looks correct via `inputValue()`. This cost significant debugging time.
- All-day toggle is `button[data-test-id="allday-checkbox"]` with `role="switch"` and `aria-checked` — NOT the `<input type="checkbox">` inside it (that input is `readonly tabindex="-1"`, purely decorative). Clicking it is occasionally flaky (state doesn't always flip on the first click, cause unclear — retry loop checking `aria-checked` up to 5x is the working mitigation).
- Time fields (`input[name="dateTime.startTime"]` / `dateTime.endTime`) are NOT freely typable — clicking one opens a `role="option"` listbox of 30-min-interval slots (`0:00, 0:30, 1:00, ...`). **Displayed without leading zero on the hour** (`9:00` not `09:00`) — must strip leading zeros before building the match regex, or the option locator times out.
- Save button: `button:has-text("保存")`, `data-test-id="event-form-submit-button"`. It's disabled until the form is genuinely valid — always check `isDisabled()` before clicking rather than assuming.
- **The calendar month-view renders a live optimistic preview of the event being edited** (a green pill on the target date) even before saving — don't trust what's visible on the calendar grid while a create/edit form is still open; verify by reloading a fresh page and checking for the event, or checking the form actually navigated away after save.
- Delete flow: open the event (click the event's button element on the calendar month view, matched by title text), click `button[aria-label="メニュー"]` (a ⋮ icon), then a floating popover (`div[role="dialog"]` containing 編集/コピー/削除) appears — click its **last** `<button>` (the 削除 one always has an extra CSS class marking it destructive, but the class name is a build hash, not stable — selecting by "last button in the popover containing 編集 and 削除" is more durable than matching on `削除` text directly, because event titles containing the literal substring "削除" — as all my test event titles did, e.g. "...(削除してOK)" — will falsely match a plain text locator). After that, a confirm dialog `本当に削除しますか？` appears — click its `削除` button (scope the locator to `[role="dialog"]` to avoid the same substring problem again).
- Since Playwright re-`connectOverCDP`s to the *same live tab* across separate script invocations (not a fresh page), state carries over — e.g. a menu opened by one script run stays open when the next run starts. Always navigate fresh (`page.goto`) at the start of each operation rather than assuming a clean state.

**Adding/editing an event's メモ (note) field — ⚠️ CRITICAL PITFALL, read before touching this** (root-caused 2026-08-09 after it silently destroyed the 長崎 trip event, see incident below): the edit/create form has a top-level `予定`/`メモ` toggle (the two pill buttons under the title bar) **and, separately**, a `メモ` row further down the item list (below `ラベル`) that opens a modal to type the actual memo body text. These are two different UI elements that happen to share the exact visible label "メモ", and **naive locators collide them**:
  - `page.locator('button', { hasText: 'メモ' })` or `.locator('button:has-text("メモ")')` matches the **top-level tab toggle**, not the memo-body row. Clicking it does NOT open a modal — it **switches the entire form from "予定" (event) to "メモ" (a separate, independent TimeTree entity type that never renders on the calendar grid)**. The form retains the title/dates/participants you'd already entered (confirmed 2026-08-09: switching tabs back and forth does not lose data), so nothing looks obviously wrong at this point.
  - The **correct** locator for the memo-body row is `page.locator('text=メモ').last()` — page-wide there are exactly two elements with the exact text "メモ": index 0 is the tab-toggle `<button>`, index 1 is a `<p>` tag inside the item-list row. `.last()` reliably hits the `<p>`, which correctly opens the memo-text modal regardless of which tab is currently active.
  - **The failure mode this caused**: after using the memo-body modal correctly once, clicking the wrong locator (`button:has-text("メモ")`) on a later edit **silently left the top-level tab on "メモ"**. Saving in that state converts the *entire event* into a TimeTree "メモ" object — same title/date range, but it no longer appears on the calendar month/week grid, its URL becomes `/calendars/<id>/memos/<eventId>` instead of `/events/<eventId>`, and the detail panel title changes from `予定詳細` to `メモ詳細`. The ⋮ menu on a メモ only offers 編集/コピー/削除 — **there is no "convert back to event" option in the UI.** The only fix is deleting the メモ and recreating the event from scratch (re-entering title/dates/participants/memo text) — the 長崎 trip event (see [[nagasaki_sons_trip_sept2026]]) had to be fully recreated this way on 2026-08-09.
  - **Also discovered**: on a brand-new (unsaved) 予定作成 form, clicking the memo-body row (even via the correct `.last()` locator) does NOT open a modal at all — it just switches to the メモ tab with an empty body, because there's no memo sub-object to edit yet until the event itself has been saved once. **So memo text can only be added in a second pass, after the event exists**: (1) create+save the event as 予定 first (verify the post-save URL is `/events/<id>`, not `/memos/<id>`), (2) reopen it, ⋮ → 編集, (3) confirm the edit form opened with the `予定` tab active (title bar reads `予定の編集`, not `メモの編集` — if it opened on メモ, click the `予定` tab button first), (4) use `text=メモ`.last() to open the modal and type the body, click `OK`, (5) **before clicking the outer 保存, re-verify the `予定` tab is still active** (screenshot or check the pill's class/aria state) — the OK click just closes the modal, it does not itself change tabs, so if step 3 was done correctly this should hold, but always verify rather than assume given how costly the failure mode is.
  - Once the memo modal is correctly open, it contains a *second* `<textarea>` on the page (index 1 — index 0 is the title textarea) with placeholder "予定に関する情報を最大10,000字まで入力できます". **Must use `page.keyboard.type()` into it**, not `.fill()`, per the same React-onChange gotcha as the title field.
  - Success verification: reload the event detail page and confirm (a) URL is still `/events/<id>` not `/memos/<id>`, (b) panel title is `予定詳細` not `メモ詳細`, (c) the memo text appears with a `メモを更新しました` timeline entry, (d) the event still renders as a colored bar on the calendar month grid on the correct dates — this last check is the one that would have caught the original 2026-08-09 mistake immediately, and is worth doing on every メモ edit going forward.

**Bulk-add reliability gotcha (hit 2026-08-07, cost real debugging time)**: running many `addEvent` calls back-to-back in a tight loop (bash `for` loop calling `node timetree_helper.js add ...` repeatedly) silently drops most of them — the script reports `{ok: true}` for all 6 attempted in one run, but re-scraping afterward showed only 1 of 6 actually persisted. Root cause not fully isolated (suspected: the SPA's client-side routing between rapid-fire `/events/new` navigations in the same live tab doesn't always fully remount before the next script's actions fire). **The `isDisabled()` check on the save button is not sufficient proof of a real save.** Fix that worked: add events **one at a time**, with a `waitUntil: 'load'` (not just `domcontentloaded`) navigation, a longer settle wait (~2s) before typing, and — critically — **verify after clicking save that the URL actually navigated away from `/events/new`** (`!page.url().includes('/events/new')`) before trusting success; if still on the form, the save silently no-opped. Always do a final full re-scrape (via the weekly scraper above) after any batch of additions to confirm what's actually there, rather than trusting the per-call return values.

**Multi-day all-day event creation (confirmed working 2026-08-09)**: `timetree_helper.js`'s `addEvent()` only sets a single date (via the `date` URL query param) and doesn't touch the end date — fine for single-day events but silently leaves multi-day events collapsed to one day. To span multiple days: after the form loads, the 終日 row has two date inputs, `input[data-test-id="start-date-picker"]` and `input[data-test-id="end-date-picker"]` (both `role="combobox"`, `name="dateTime.startDate"`/`"endDate"`). Clicking either opens a popup month-grid date picker; click the target day via `page.getByRole('button', { name: 'DD', exact: true })` (day numbers render as two different elements — a plain grid-cell div and an actual `role="button"` — `getByRole` disambiguates correctly, a raw `getByText` throws a strict-mode violation). The start date is already pre-filled from the URL's `date` param, so only the end-date picker needs this treatment. Not yet wrapped into `timetree_helper.js` as a reusable function — done via one-off script so far; worth adding an `endDate` param to `addEvent()` next time this comes up. **Post-save verification timing gotcha**: right after clicking 保存 and confirming the URL left `/events/new`, an immediate reload/re-scrape can show **zero** events on the whole calendar (not just the new one) — the SPA hadn't finished re-fetching yet. A `page.reload()` + ~4s wait resolved it. Don't conclude a save failed from an instant post-save check; wait and re-check before trusting a 0-count result.

**Weekly-view multi-day event span, finally decoded (2026-08-15)**: the earlier "Scraping the 🏠 calendar's all-day events reliably" section above only captured a pill's *start* column (`--lndlxo0`) — enough for single-day flags but silently under-counted multi-day umbrella events (e.g. `父モンゴル？`, `天晴・満天 長崎(祖父母訪問)`) as covering only their first day. Root cause found by dumping a pill's full computed style: **`--lndlxo2` is the column span width** (`--lndlxo1` appears to be a stacking/row slot, not span — still unconfirmed exactly what it's for, but not needed for date-range purposes). Confirmed against real data: `天晴・満天 長崎` had `lndlxo0=2, lndlxo2=3` on a week where col2=9/15, correctly meaning it spans 9/15–9/17 (3 days) — matches the known trip dates exactly. `父モンゴル？` had `lndlxo0=4, lndlxo2=4` (spans through the end of that week's grid, i.e. clips at col 7 — the event continues into the *next* week as a **separate** pill starting at col1, since the weekly grid can't render a bar past its own 7-column boundary; each week-crossing occurrence must be summed independently, not derived from one pill's span alone). `tt_scrape_weeks.js` now captures `span: parseInt(cs.getPropertyValue('--lndlxo2')) || 1` alongside `col`, and the consumer (`~/TimeTreeCheck/timetree_check.py`, see [[continuous_data_capture_setup]]) expands each pill across `col` through `min(7, col+span-1)` when building its date→pills-that-day index, so multi-day umbrella events now correctly suppress gap-detection for every day they cover, not just the first.

**Daily gap-check loop bug found and fixed 2026-09-11**: `~/TimeTreeCheck/timetree_check.py` (the daily 父夜いない registration-gap checker, see [[continuous_data_capture_setup]]) had no memory of past human decisions — a single one-off judgment call (2026-08-15: user decided the 10/1 ANA flight, part of an already-registered ベトナム出張 trip, needs no 父夜いない registration) was never fed back into the exclusion rules, so the exact same item was silently re-flagged as "要確認" in every single daily report for 26 consecutive days (2026-08-16〜2026-09-11) with nobody ever acting on it — the user asked "登録確認されたことがない" after noticing this. Root cause: the script only has static exclusion rules (`EXCLUDE_EXACT`/`ALREADY_EXPLAINED_MARKERS` matched against TimeTree pill text), nothing that remembers "a human already looked at this exact candidate and said no." **Fixed**: added `~/TimeTreeCheck/decisions.json` (list of `{date, subject, decision, note, decided_at}`) and a `load_decisions()`/filter step in `find_gaps()` — once a candidate is marked `no_action_needed` there, it's permanently suppressed from future reports. Seeded with the 10/1 ANA entry after re-confirming with the user the same day. **How to apply going forward**: whenever the user (in an interactive session) makes a "no registration needed" call on a report item, add it to `decisions.json` immediately rather than leaving it to resurface — this is the only way this checker's findings actually reach closure, since the script itself never asks and never auto-registers by design.

**Critical `addEvent({allDay:true})` bug found and fixed 2026-09-15**: `timetree_helper.js`'s `addEvent()` had an `if (!allDay) { ...toggle+set times... }` block — when `allDay:true` was passed, this whole block was **skipped entirely**, meaning the all-day toggle was never touched at all. Since a fresh `/events/new` form's toggle state is NOT a hard default but persists from whatever the user/script last left it at (same cross-session "remembered state" behavior as the calendar's last-viewed date/month, see below), calling `addEvent({allDay:true})` silently created a **timed** event using a leftover/arbitrary time (whatever the form happened to prefill, e.g. `9:00-10:00`, `15:00-16:00`) instead of an all-day event — with no error, no visible symptom in `{ok:true}`. **Fixed**: toggle logic is now unified regardless of `allDay` — check `aria-checked` first, click only if it doesn't already match the wanted state (`'true'` for allDay, `'false'` for timed), before proceeding. Verify allDay events actually landed in the all-day row (`div._1k5qcgp9 button`), not as a timed pill, after any future allDay add.

**Calendar view position (month/week) is remembered across page loads via app state, not derived from the URL alone — critical for verification scripts**: navigating to the bare `https://timetreeapp.com/calendars/<id>` URL does NOT reset the view to "today" — it restores whatever month/week was last viewed (by any script or the human user), even after a full `page.goto` reload. A verification script that clicks `マンスリー`/`翌月` a computed number of times **without first clicking `button:has-text("今日")` to reset to today** will silently drift to the wrong month (caught 2026-09-15: a screenshot taken this way showed 2027年4月 while the calendar was actually on 2026年9月). **Always click `今日` immediately after any `page.goto` to the bare calendar URL before navigating by month/week offset.** The **reliable, direct way to jump to an exact date** (discovered 2026-09-15, better than clicking 翌月/翌週 N times): `page.goto('https://timetreeapp.com/calendars/<id>/weekly/<YYYY-MM-DD>')` — this deep-links straight to the week containing that date, no `今日`-reset or click-counting needed, confirmed reliable across both calendars.

**Verifying event placement — use the weekly all-day-row column scraper (`tt_scrape_weeks.js` pattern), not month-view or free-text search**: matching by `page.locator('button', {hasText: title})` alone is unreliable for confirming *which day* an event landed on — it matches anywhere in the currently-loaded week/month regardless of column, and can also match unrelated buttons (member names, sidebar echoes of a "day detail" panel that shows a cross-calendar-looking agenda for whatever day was last clicked/selected, which is a separate UI element from the actual grid pill and does not reliably indicate the event truly exists on that specific date until cross-checked against the grid). The `--lndlxo0` (col) / `--lndlxo2` (span) CSS custom properties on `div._1k5qcgp9`'s children (documented above) remain the only precise way to confirm exact-day placement for all-day events; for timed events, match on the event's full text including its time suffix (e.g. `'10:00 - 11:00'`) to disambiguate from same-titled all-day items, then use `page.goto(.../weekly/<date>)` to scope to the intended week before searching, still without proof of column — if precision matters, prefer creating a uniquely-named event and confirming via the deep-link date being the one you deep-linked to (self-consistent) rather than trusting text search across a whole week blindly.

**How this played out 2026-09-15 (costly lesson — bulk timetree registration task)**: a batch request to add 4 timed personal events + 8 all-day family-calendar flags (父夜いない/🍙父ランチいらない ×4 dates) resulted in nearly every all-day item landing on the wrong day (±1) due to the `allDay` toggle bug above compounding with stale-view verification giving false confirmations. Recovery required: precise deep-link-based day inspection (`/weekly/<date>`) to find true positions, scoped deletion of the wrongly-placed all-day pills via `div._1k5qcgp9 button` (not a bare page-wide button locator, which also unpredictably matches sidebar echoes — confirmed one such stray match required a scoped-container retry after a bare-locator delete attempt silently no-opped), and full re-creation one-at-a-time with a scrape-based column check after each add before moving to the next date. **Going forward, given the toggle fix above should eliminate the root cause, single sequential adds should no longer need this heavy a verification pass — but do a quick column-scrape spot-check after the first item in any new batch before trusting the rest.**

**Costly deletion mistake 2026-09-15 — never delete a father-flag pill without checking WHY it's there first**: while cleaning up the toggle-bug fallout above, four 父夜いない/🍙父ランチいらない pairs on 9/29, 10/8, 10/29, 11/6 were deleted on the assumption they were leftover artifacts of the buggy bulk-add (since they sat one day off from the 4 intended dates 9/30/10/7/10/28/11/5). **This assumption was wrong and cost the user real data.** Cross-checking `~/TimeTreeCheck/reports/report_2026-09-15.md` (generated at 07:30, *before* this session touched anything) showed only 4 gap candidates (澤本会 etc.) out of 24 total — meaning 9/29/10/8/10/29/11/6 were *already* correctly flagged as "covered" at 07:30, i.e. they held **genuine pre-existing registrations for unrelated real events** (大塚会 9/29, 蓬莱さん上京 10/8, ベトナム交流会 安岡会 10/29 and 11/6) that had nothing to do with the bug. Deleting them removed real coverage; the user had to notice via TimeTree's own edit history ("履歴") and manually re-create them. **Lesson: before deleting any all-day flag pill found on an "unexpected" date, check `~/TimeTreeCheck/reports/` for a report timestamped *before* your session started — if that date was already excluded from gaps then, the pill is doing real work for a real event, not a bug artifact, regardless of how neatly it seems to line up with your own mistake.** TimeTree's own per-event "履歴" (edit history, with relative timestamps like "9分前") is also directly readable by the user and is the ground truth for when an entry was actually created — ask for it (or, if automating, look for an equivalent audit-trail view) before assuming provenance.

**`timetree_check.py` evening-candidate logic overhauled 2026-09-15** (see `~/TimeTreeCheck/timetree_check.py`, [[continuous_data_capture_setup]]), directly prompted by the deletion mistake above surfacing three separate real gaps in the daily gap-checker:
- `LOOKAHEAD_DAYS`: 60 → **90**. A 60-day window could never have caught candidates 61–90 days out (e.g. two real events at 12/11 and 12/16 sat completely outside its reach) — pure design ceiling, not a bug.
- The old "candidate = starts at 17:30 or later" rule missed events starting a bit earlier that still run through dinner (e.g. 大船会 at 17:00 sharp was silently excluded even though it clearly occupies the evening). **Replaced with an occupancy check**: `DINNER_TIME_HOUR = 20` — a candidate is now any non-all-day busy/tentative weekday event whose `[start, end]` span covers 20:00 JST on its start date, computed from the event's own `start`/`end` fields (both now required; an event missing `end` is skipped rather than guessed at). This constant was tuned live with the user: **18:00 was tried first and rejected** — most of this user's real dinner engagements are 19:00-start (澤本会 etc.), and an 18:00-occupancy test excludes any event starting at or after 18:00, so total candidates dropped 24→14 including losing the very events that prompted the whole exercise. **20:00 was confirmed as the final value** (candidates rose to 28, correctly including both the original 19:00-start dinners and the 17:00–18:30-start meetings that run into evening) — don't relitigate 18:00 vs 20:00 without re-testing against real data via `python3 -c "import timetree_check as tc; tc.load_evening_candidates()"` (safe, read-only, no side effects — see [[feedback_verify_gating_logic_without_running_full_script]] for why this import-only pattern is used instead of running `main()`).
- These two changes are independent and were confirmed separately by the user (90-day lookahead was accepted without pushback; the 18:00→20:00 threshold went through one live back-and-forth) — if either needs revisiting later, don't assume the other must change too.

**Always check for an existing 父夜いない/🍙父ランチいらない flag on the target date before adding a new one (found 2026-09-18)**: added a 父夜いない flag to 🏠 calendar for 2026-12-16 (直達会講演 19:00, per [[feedback_timetree_no_specific_content]] — generic flag only, no meeting name) without first checking whether that date already had one. It did — a pre-existing 父夜いない created 2026-09-15 for an unrelated reason — resulting in two identical-titled all-day pills stacked on the same day. Same-titled duplicates can't be told apart by a weekly-view scrape (title/date/col are identical); had to click into each pill and compare the event detail page's creation-date line (`父` / `2026年9月◯日(◯)` / `予定を作成しました`) to identify which was the new one, then delete it by direct event-ID URL navigation (`page.goto('.../events/<id>')` then the ⋮-menu delete flow) rather than `timetree_helper.js delete_by_title`, which would have matched either one ambiguously. **How to apply**: before calling `addEvent` for a 父夜いない/🍙父ランチいらない flag, do a quick weekly-view scrape of the target date first — if the flag already exists there, skip the add entirely (the date is already covered, regardless of what new reason prompted this request).

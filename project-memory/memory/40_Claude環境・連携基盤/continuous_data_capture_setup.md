## Why two different mechanisms
- New Outlook for Mac has no AppleScript/Graph API self-service route (established earlier, see [[local_work_data_export]]).
- IMAP(993)/SMTP(587) ports are network-reachable but tenant policy for actual auth is untested — not pursued, avoided by the option below.
- `~/Library/CloudStorage/OneDrive-電通/` is already synced locally on this Mac → anything written to OneDrive from the cloud (e.g. a Power Automate flow) appears locally within moments, zero custom auth code. Made **Power Automate → OneDrive** the choice for **email**.
- **Gotcha (2026-07-14, now fixed everywhere)**: this Mac has *three* OneDrive accounts synced under `~/Library/CloudStorage/` — `OneDrive-dentsu`, `OneDrive-共有ライブラリ-dentsu`, and `OneDrive-電通`. Only **`OneDrive-電通`** is the user's real work account. If anything OneDrive-related seems missing/empty, check which of the three is being used before debugging further.
- Teams personal-chat messages aren't exposed via a non-premium Power Automate trigger, and there's no admin-consented Graph app — so Teams goes through Playwright web-scraping, turned into a **long-running background daemon** rather than a one-shot script.
- **Important operating constraint (learned 2026-07-15): the user's Mac is fully shut down every evening for security and restarted every morning.** This means the Teams daemon can never truly run 24/7 — it dies every night and must cold-start each morning. The design goal is therefore not "never touch it again" but: (a) `launchd` auto-starts it at login so the user doesn't have to remember, and (b) the morning login step is as close to zero-touch as possible.

  1. **"Set variable" cannot self-reference the variable it's updating** — `union(variables('X'), newData)` or `add(variables('X'), 1)` inside a "変数の設定" targeting `X` itself fails at save time with `Self reference is not supported when updating the value of variable 'X'` (for numbers) or a confusing `cannot be updated with value of type 'String'` (for arrays — same root cause, misleading error text). **Fix: use the dedicated increment/append actions instead** — "変数の値を増やす" (Increment variable) for numbers, "Apply to each" + "配列変数に追加" (Append to array variable) for arrays. These aren't self-referencing under the hood and don't hit the restriction.
  2. **Mixing hand-typed text with a picker-inserted dynamic-content chip in the same field produces a STRING TEMPLATE, not an evaluated expression.** E.g. typing `select(` then inserting a "値" chip then typing `, removeProperty(item(), 'body'))` doesn't call `select()` — it literally concatenates the text "select(" with the JSON-stringified chip value with the text ", removeProperty..." as one big string (confirmed by inspecting the raw output, which began with the literal text `select([{...`). **Fix: never mix typed text and chips in one field.** Either (a) insert only a bare chip with nothing else typed around it (fine — this is the normal/intended usage), or (b) type the entire expression by hand with zero chips, referencing other actions via `outputs('ActionName')?['body/value']` — but first rename the target action to a short ASCII name (no spaces/parens/Japanese) via 「…」→「名前の変更」, since typing a reference to a non-renamed action's original name is itself error-prone (also: click into the field and specifically invoke the ⚡/fx expression-mode icon before typing — a plain textbox may just store literal text without evaluating it as a formula at all, a *third*, related trap hit mid-session where an input's raw output echoed back the literally-typed formula text verbatim).

## Real root cause of the recurring "Resource deadlock avoided" + "only fires once" bugs — found and fixed 2026-07-31, on the d14461 Mac
The 2026-07-29/30 backlog recurrences (see entries above) and the separate "20-min StartInterval only fires once" symptom the user found on ICPTokyo2022 the same day turned out to be **the same root cause**, not two mysteries:
- Caught a `sync_calendar_export.py` launchd run (started at boot via RunAtLoad, PID 1433) sitting alive for 30+ minutes with **zero log output** — `ps` showed it running, but the log file's mtime hadn't moved since the prior day. That means it was stuck inside the very first `open()` call on the oldest pending snapshot CSV, **with no exception raised at all** — not the "Errno 11, retries, eventually gives up after 150s" pattern the existing retry logic was built for. Verified the specific file itself was NOT actually locked (a fresh independent `python3 -c "open(...)"` read it instantly) — so this isn't a permanent per-file lock, it's OneDrive's File Provider occasionally blocking a read indefinitely without ever returning or erroring, especially in the window right after boot.
- Independently corroborated by `brctl status` returning `self-check failed; error: BRCloudDocsErrorDomain Code=141 "Access denied"` on this Mac — real, measurable evidence the OneDrive/CloudDocs File Provider integration is in a degraded state here (not observed/checked on ICPTokyo2022).
- Ruled out overlapping/duplicate processes as the cause (`ps aux` always showed exactly one instance of each sync script; the user's hypothesis was reasonable but not what was happening).
- **This single root cause explains both symptoms**: launchd will not start a second instance of a `StartInterval` job while the previous one is still "running" — so a script that hangs forever (not crashes, not exits) permanently blocks all future scheduled runs, matching "runs stays at 1 forever" exactly, regardless of how much wall-clock time passes. A plain retry-loop (however many attempts/however long) can never fix this, because it only helps when the OS eventually raises an exception — it does nothing when the syscall itself never returns.
- **Fix applied to both `sync_calendar_export.py` and `sync_power_automate_export.py`**: `read_snapshot()` / `read_text_with_retry()` now run each read attempt in a throwaway `multiprocessing.Process`, polling the result with a hard wall-clock timeout (20s calendar / 15s email) and force-`terminate()`/`kill()`-ing the child if it doesn't return in time. This guarantees the parent script can never hang, no matter how badly OneDrive's File Provider misbehaves. `RETRY_COUNT`/`RETRY_DELAY_SECONDS` shortened accordingly (calendar: 15×10s → 5×5s, since the per-attempt timeout is now the real cap, not the retry budget).
- Also aligned `com.nakamura.calendarsync.plist` / `com.nakamura.emailsync.plist` on the **d14461 Mac** to `StartInterval=1200` (20 min), matching the ICPTokyo2022-side jobs (previously still 3600/hourly here — the earlier 07-31 change only touched the ICPTokyo2022 Mac's copies).
- **Verified end-to-end**: manually ran both fixed scripts (calendar cleared a 99-file/multi-day backlog in 2m50s, no hang; email caught up cleanly), then `launchctl unload`→`load`'d both plists and watched `runs` in the background — **confirmed `runs` incremented 1→2 for both jobs ~22–23 min later, both with `last exit code = 0` and no leftover process**, i.e. the fix holds under real launchd scheduling, not just manual runs.
- **Still open, not a script problem**: *why* this Mac's OneDrive File Provider occasionally hangs a read indefinitely (the `brctl` Access-denied finding) is unresolved — the script fix makes the symptom harmless (it can't block the pipeline anymore) but doesn't address OneDrive's own health on this machine. If it recurs or worsens, next step is having the user restart/re-sign-in OneDrive.app on this Mac.
- **Worth checking on ICPTokyo2022 next time it's touched**: its "StartInterval=1200 but runs stuck at 1" symptom was never root-caused there directly (that Mac wasn't touched this session), but given the mechanism found here (launchd never re-fires while a previous run is hung, regardless of *why* it's hung), the same "check `ps` for an abnormally-long-lived sync process" diagnostic likely applies there too.

## 2026-08-02 (same day, later): ROOT CAUSE CONFIRMED AND FIXED on the ICPTokyo2022 Mac — /usr/bin/python3 is an Apple platform binary, TCC auto-denies it File-Provider access

User asked for a real fix, not another manual catch-up ("毎回取り込みが止まってしまうので根本的な解決をしたいです"). Found the actual cause via Unified Logging: `/usr/bin/log show --predicate 'subsystem == "com.apple.TCC"' --style compact --last 3h` showed repeated entries like:
```
kTCCCodeIdentityExecutableURL = "file:///usr/bin/python3";
kTCCIndirectObjectFileProviderDomainID = "com.microsoft.OneDrive.FileProvider/OneDrive - 電通";
...
[com.apple.TCC:access] Platform binary prompting is 'Deny' because: is Platform Binary
```
`codesign -dv /usr/bin/python3` confirms `Platform identifier=26` — it's an Apple system/platform binary (a thin shim that execs into `/Library/Developer/CommandLineTools/.../Python3.framework/.../Python`). **Apple's TCC subsystem categorically refuses to grant platform binaries their own access consent for TCC-gated resources** (anti-malware hardening — otherwise malware could shell out to `/usr/bin/python3` to bypass TCC using a pre-trusted system binary as a proxy) — access is auto-denied with zero prompt and zero error, just a silently empty result.

**Why interactive runs always worked while launchd runs never did**: when `/usr/bin/python3` is spawned interactively (e.g. via Claude Code's Bash tool, itself a child of a GUI app the user already granted access to), TCC can attribute the access request to that **responsible parent process** instead of to the platform binary itself, and the grant is inherited. A `launchd` LaunchAgent has no such GUI-app parent — the request falls back to `/usr/bin/python3`'s own identity, which is unconditionally denied. This explains **every** "works when Claude runs it, silently fails on schedule" incident logged above for both OneDrive (calendar/email) and Google Drive (Facebook) — it was never three separate app-specific bugs, it's one platform-wide TCC rule hitting three scripts that all happened to be launched via `/usr/bin/python3`.

**Fix applied (2026-08-02)**: `brew install python3` (installed non-platform Python 3.14.6 at `/opt/homebrew/bin/python3` — confirmed via `codesign -dv` to have **no** `Platform identifier` field, ad-hoc signed, a normal third-party binary eligible to hold its own TCC grant). Updated `ProgramArguments[0]` in all three plists — `com.nakamura.calendarsync.plist`, `com.nakamura.emailsync.plist`, `com.nakamura.facebooksync.plist` — from `/usr/bin/python3` to `/opt/homebrew/bin/python3`, then `launchctl unload`/`load` all three.

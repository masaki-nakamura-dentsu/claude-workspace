**Rule** (stated explicitly 2026-08-07, generalized beyond the task it came up in): don't launch a new dedicated Chrome profile/process for each web-automation target. Reuse a single, already-running Chrome instance — open a new tab in it via `playwright.chromium.connect_over_cdp("http://localhost:<port>")`, not a fresh `launch_persistent_context`/new profile — for every browser automation need, present and future, not just the task where this was requested.

**Why**: The user was maintaining separate bot browsers (ChatGPT, Gemini, Salesforce, and almost a 4th for Teams) each popping up their own window, and pointed out most of these use the same corporate identity anyway — better to consolidate into one. See [[feedback_browser_automation_no_focus_steal]] for the related "don't steal focus" rule this builds on.

**This rule applies per-machine** — [[reference_mac_naming]] distinguishes d14461 (company Mac) from ICPTokyo2022 (this personal Mac); a browser profile on one machine obviously isn't reachable from the other, so each machine ends up with its own single shared browser, not one global one.

**Reinforced 2026-08-09 (still recurring)**: opening a new tab (`context.new_page()`) or navigating in an existing one can bring the shared browser's OS window to the foreground even if it was previously positioned off-screen, stealing focus from whatever the user is doing. **Root cause found and fixed 2026-09-02, then refined same day after user reported the flash was STILL happening**: the user reported the shared browser (d14461, port 9226) briefly flashing full-size on screen every time some automation ran, even though `minimize_browser_window()`/`reposition_offscreen()` were already being called early (per the rule above).

Round 1 finding: `context.new_page()` unconditionally resets the CDP `windowState` from `minimized` back to `normal` (confirmed via direct CDP testing — a plain `.click()`, JS-evaluated click, or `goto()` do NOT trigger this — only `new_page()` does). The window's on-screen *position* (left/top) had never actually been moved off-screen — it sat at a fully visible `(0, 38)` — so every forced `normal` flash was visible. Fixed by moving the window off-screen and adding `--window-position=-2500,-2500` to every Chrome-launch command (see file list below). **This alone was not enough** — user reported the flash continued.

Round 2 findings (why round 1 wasn't enough, and the actual fix):
1. **This Mac is multi-display** (built-in Retina 3024x1964 + external 1920x1080, positioned such that the combined desktop bounding box is roughly x:[-235,1685] y:[-1080,982] per `Finder`'s `bounds of window of desktop`). Off-screen coordinates get silently clamped by macOS/Chrome to somewhere near the display edges (requesting `-3500,-3500` actually landed at `-1095,-1055`), and that clamped position can still partially overlap a display's edge — off-screen positioning is fundamentally unreliable on a multi-monitor setup, not just a matter of picking a big-enough negative number.
2. Even if perfectly off-screen, **macOS's minimize/restore transition itself is an animated Dock "genie" effect that visibly sweeps across the screen from the Dock icon** (which is always on-screen) to wherever the window ends up — so the sweep itself is visible even when the destination is off-screen. This is the actual mechanism behind "briefly flashing full-size."
3. Tried CDP `Target.createTarget({background: true})` as a way to open tabs without forcing the `normal` state at all — confirmed via raw CDP it does avoid the state reset, but **Playwright (both Node and Python) never surfaces a `Page` object for a background-created target**, so it's unusable from Playwright's own API and was abandoned.

**Actual fix applied 2026-09-02**: two changes, both needed —
(a) Stopped using `windowState: "minimized"` entirely in `minimize_browser_window()`/`reposition_offscreen()` — now sets `windowState: "normal"` and pins position off-screen (`-2500,-2500`, in whatever clamped form the OS allows) instead. Since the window is *already* `normal`, `new_page()` no longer forces a state transition, so there's no minimize↔restore cycle to animate at all. Confirmed via clean CDP testing (no interference) that windowState stays `normal` and position stays off-screen through a full `new_page()`→`goto()`→`close()` cycle.
(b) **User's own suggestion, applied as the real fix for the multi-display clamping uncertainty**: disabled macOS window animations globally — `defaults write -g NSAutomaticWindowAnimationsEnabled -bool false`. This means even if a window transition or partial on-screen overlap does occur (e.g. from the clamped off-screen coordinates), there's no animated sweep to see, just an instant (imperceptible) state change. This is a global setting affecting ALL apps' window open/close/minimize animations, not just Chrome — done with explicit user approval (asked via AskUserQuestion, user chose full animation disable over the narrower Dock-only `mineffect` option).

Files patched to stop using `minimized` and go off-screen+`normal` instead: `~/TeamsExport/teams_daemon.py` (`minimize_browser_window()`), `~/CASExport/cas_download.py` (inline in `download_month()`), `~/SalesforceExport/reports_pipeline/download_all_reports.py` (`reposition_offscreen()`). **Also note for future incidents**: repositioning/minimizing a stray on-screen window does NOT automatically return macOS keyboard focus to whatever app the user was previously using — `frontmost` stayed "Google Chrome" even after the window was moved off-screen in this incident. The user has to click their own app once. This is exactly why the scripts' own `getFrontmostApp()`/`restoreFrontmostApp()` pattern (record-then-restore, tied to each automation's own before/after) is the correct mechanism — an ad hoc reposition from a debugging session can't replicate that restore step because it has no "before" state to return to.

**Practical notes carried over from the Salesforce debugging session that produced this rule**:
- Launch the shared Chrome as a detached OS process (`nohup ... &`, `disown`), not via Playwright's `launch_persistent_context`, so it survives independently of any single script/tool-call lifetime — each subsequent script just attaches via CDP and must NOT call `context.close()` at the end (that would kill the shared browser for everyone else).
- A brand-new login in a new tab needs the window to actually be on-screen and focused for the user to type credentials — if the shared browser was positioned off-screen (e.g. `--window-position=-3000,-3000` to avoid focus-stealing during unattended runs), move it back on-screen first via CDP (`Browser.getWindowForTarget` + `Browser.setWindowBounds`) before asking the user to log in, then it can go back off-screen or just stay wherever afterward since login is a one-time step.

**2026-09-17 addition ([[gbc_intelligence_engine_project]], pasting an updated SYSTEM prompt into Dify's LLM node editor)**: found that **some page-level actions silently no-op when the shared browser window is off-screen/not OS-focused, even though CDP reports the click/keypress as delivered and the DOM shows correct focus**. Specifically on a React-based rich-text `contenteditable` (Dify's SYSTEM prompt editor): clicking into it while off-screen correctly set `document.activeElement` to the right element, but a synthetic `Meta+A` + `Meta+V` (clipboard paste) afterward left the content completely unchanged — no error, no partial effect, just silently reverted-looking (actually never applied). `document.execCommand('insertText', ...)` after `selectAll` also "succeeded" (returned `true`) but the framework immediately reconciled the DOM back to its prior state. The fix was to temporarily bring the window fully on-screen and call `page.bringToFront()` (making the OS's frontmost app genuinely this Chrome window) before the click+paste, verify via text extraction, then immediately move it back off-screen. The same on-screen requirement applied to actually triggering Dify's own "公開する"/"更新を公開" publish action — clicking while off-screen appeared to succeed (no error) but the header's "公開済み ◯時間前" timestamp never updated; moving on-screen first fixed it immediately (confirmed via "公開済み 数秒前"). **How to apply**: if a page interaction that should mutate visible app state (a controlled-component text edit, a publish/save action, anything beyond simple navigation or read-only DOM queries) appears to complete without error but a before/after state check shows no actual change, suspect the off-screen/unfocused window state before assuming a selector or timing bug — bring the window on-screen+frontmost, retry, and restore off-screen immediately after, same as the login pattern above. This cost several wasted round-trips on 2026-09-17 before being diagnosed; check this early next time a "no-op success" pattern shows up on this shared browser.

**2026-09-17 addition, same session, second finding — stale rendered content on a long-lived tab**: after successfully publishing a Dify workflow change, kept re-running `document.body.innerText` extractions against the same long-open tab over many separate script invocations (each reconnecting via `connectOverCDP` and re-finding the page by URL, so the *Playwright object* wasn't stale) — but the actual **rendered DOM content itself stayed frozen** at an old snapshot: the same "自動保存済み HH:MM:SS"/"公開済み ◯分前" timestamps and the same old 4-parameter code-node body kept coming back verbatim across multiple reads, even after the user had actively edited that exact node in the same tab in between reads. No error, no exception — just silently stale text, indistinguishable from "nothing changed yet" without independently knowing a change had happened. `page.reload()` immediately fixed it (fresh timestamps, fresh code content on the next read). **How to apply**: on a tab that's been held open and read from repeatedly over an extended session (minutes, many separate script calls), especially one where a human is also actively editing the same page concurrently, don't trust that a `body.innerText` read reflects the current server/app state just because the call succeeds without error. If a value that should be changing (a timestamp, a just-edited field) reads identical across two checks that should straddle a real change, `page.reload()` before concluding "no change happened yet" or re-diagnosing a wiring/selector problem — this is cheap and resolved the issue immediately here.

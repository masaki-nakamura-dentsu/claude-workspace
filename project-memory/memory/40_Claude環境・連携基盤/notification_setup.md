Alert when Claude's response finishes is configured in `~/.claude/settings.json` (global, applies to all projects) as a `hooks.Stop` command: `afplay /System/Library/Sounds/Glass.aiff`. Plays a chime so the user notices from another window/app without needing to watch the screen. Confirmed audible and working 2026-07-07.

**Why sound instead of a macOS notification**: originally tried `osascript -e 'display notification ...'`, which required `sandbox.allowAppleEvents: true` (approved and set) plus a full app restart (sandbox settings only load at process start, unlike hooks). Even after that, the notification never appeared. Root cause traced to `~/Library/Preferences/com.apple.ncprefs.plist`: notifications from `osascript` register under bundle-id `com.apple.ScriptEditor2`, whose permission bit was OFF and didn't show up in System Settings → Notifications search for the user to toggle manually. Directly flipping the bit in the plist (with the user's explicit permission, after Claude Code's auto-mode classifier initially blocked the raw edit as a permission-bypass pattern) and restarting the notification daemon still didn't make notifications appear — Focus/Do Not Disturb was ruled out (menu bar moon icon confirmed grayed out/inactive). Rather than keep fighting Notification Center internals, switched to `afplay`, which needs no OS permission at all and works unconditionally.

**Leftover state**: `sandbox.allowAppleEvents: true` is still set in `~/.claude/settings.json` — harmless, left in place in case other AppleEvents-based automation is wanted later, but it is no longer required for the alert itself. The `com.apple.ScriptEditor2` notification bit was also left flipped ON in ncprefs.plist; also harmless/unused now.

**If the user wants a visual notification again**: don't repeat the same debugging path — start from "Notification Center permission for osascript/Script Editor could not be granted through the OS's normal flow on this Mac" and consider a properly signed/bundled notifier (e.g. `osacompile`-built .app, or `terminal-notifier`) that goes through the real first-run permission prompt, rather than raw `osascript` from Terminal.

**New finding (2026-07-08, second Mac)**: after symlinking `~/.claude/settings.json` into place *mid-session* (i.e. the file didn't exist when the session/process started), the Stop hook did not fire even though the JSON was valid and `afplay` worked fine when run manually. Conclusion: hook config is read once at session start — creating the file after launch doesn't get picked up until Claude Code is restarted. This is a stronger claim than the earlier note "sandbox settings need restart, unlike hooks" — that note likely applies to *editing* an already-loaded settings.json, not to a settings.json that didn't exist at all when the session began. **When setting up a new Mac (or otherwise creating settings.json for the first time mid-session), always tell the user to restart Claude Code afterward and don't treat a silent first test as a real failure.**

**Mobile push added (2026-07-09)**: the user also installed Claude Code on their iPhone and wants a push notification there on every response completion, in addition to the Mac sound. This is a *different* mechanism from the Stop-hook sound — mobile push goes through Claude Code's built-in "Remote Control" feature and the `PushNotification` agent tool, not a shell hook (there is no CLI command a hook could shell out to for this). Two settings were added to the same synced `settings.json`: `"remoteControlAtStartup": true` (auto-starts the Remote Control bridge each session) and `"agentPushNotifEnabled": true` (permission for Claude to actually push). The user explicitly confirmed wanting `remoteControlAtStartup` on despite it meaning the session is remotely controllable by default (auto-mode classifier flagged it as capability-widening beyond a plain notification request; user overrode after being told the tradeoff).

**Still required beyond the settings change**: (1) the iPhone Claude Code app must actually be paired/connected via Remote Control — this is a manual pairing step on the user's side, not something set via settings.json; (2) since there's no hook for this, on the *agent* side, deliver on this preference by proactively calling the `PushNotification` tool near the end of turns going forward — the tool's own guidance says to be sparing, but an explicit standing user request to notify every time is exactly the case it says overrides that default. See [[pptx_visual_first_policy]] for another standing "do this by default" preference recorded the same way.

**Pairing mechanics confirmed (2026-07-09)**: in the VS Code extension, `/remote-control` shows a banner + session URL (no QR code — that's CLI-only). Opening that URL in the *Mac's own* browser does NOT pair the phone. Correct pairing: install the Claude iOS app, sign in with the same claude.ai account (masaki.nakamura@dentsu.co.jp), open the **Code** tab, and select the session from the list (green dot = online) — or alternatively send the session URL to the phone (AirDrop/Messages) and open it there. The user successfully paired and replied from the iPhone within this same session on 2026-07-09.

**Important scope limitation confirmed**: Remote Control is per-session, not account-wide. `/remote-control` (or auto-start via `remoteControlAtStartup`) only exposes the ONE session it runs in — it is not a browser/archive of past chats, and closing that session's process makes it disappear from the iPhone's Code tab. With `remoteControlAtStartup: true` set, new sessions should auto-activate the bridge going forward (confirmed by docs, not yet independently verified end-to-end by us), but the phone may still need to be pointed at that specific new session (via the Code tab) before push notifications for it will actually land — if `PushNotification` reports "Remote Control inactive" for a brand-new chat, that's most likely why; check the Code tab on the phone for that session rather than assuming the whole setup broke.

**Standing instruction confirmed 2026-07-09 (user restated explicitly)**: the user wants push notifications to the iPhone on response completion across *all* future chats/sessions with Claude, not just the one where this was set up. Going forward, in any session, call `PushNotification` proactively near the end of turns by default (not just when something unusual happened) — this is now a durable cross-session preference, not a one-off for this conversation.

**`autoUploadSessions` (past-chat history on iPhone) — confirmed broken, don't re-attempt (2026-07-09)**: the user separately wanted past/completed chats visible on the iPhone app, not just the live Remote-Control session. Tried enabling `"autoUploadSessions": true` (schema description: "Mirror local sessions to claude.ai as view-only (no remote control)") in the same synced settings.json, on Claude Code v2.1.202 (VS Code extension, macOS, Claude Pro via claude.ai login — all documented preconditions met, no Team/Enterprise gate). After a full restart and starting a fresh session, the session did not appear either in the iPhone app OR on claude.ai/code in a Mac browser — ruling out an app-side display bug and confirming the upload/mirror pipeline itself is failing. This matches two real, confirmed GitHub issues: anthropics/claude-code#74367 ("Local session mirroring to claude.ai stops after CLI 2.1.201, regression — 2.1.199 works", Windows-reported) and #53920 (same symptom on Windows ARM64, closed as stale/unresolved). Root cause is upstream (Anthropic's product), not a config mistake on our end — the setting is real and documented but the feature is currently unreliable/non-functional at least as of v2.1.202. **Don't re-suggest enabling `autoUploadSessions` or debugging it further** unless the user reports a newer Claude Code version where the linked issues show as fixed; check `claude --version` / the GitHub issue status first if this comes up again. Live Remote Control (see above) is unaffected and remains the working path for phone access to a session.

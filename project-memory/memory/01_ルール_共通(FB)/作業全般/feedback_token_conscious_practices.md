Six separate incidents, in unrelated projects (Power Automate browser automation, Power BI Service work, OneDrive sync cleanup, a photo-booklet PDF audit, a Premiere project file, a Salesforce data-integration design), all drew the same complaint or correction from the user: Claude reached for a token-expensive method (full-page screenshots, repeated `ps aux`/`tail` polling, opening many images to eyeball them, driving a UI click-by-click, calling an LLM to read structured data) when a cheaper method would have gotten the same answer.

**Why this is a standing pattern, not six unrelated incidents:** in every case a cheaper path existed and was checkable directly — DOM text (`innerText`/`getAttribute`) instead of a screenshot, the completion notification instead of a manual poll, the source edit file (Illustrator `.ai`, pptx, `.prproj`) instead of the rendered output, a regex/pick-list instead of an LLM call, or simply asking the user to do a one-click step himself. The user has raised this explicitly and repeatedly enough (2026-08-17, -22, -23, -24, -27, -28) that it should be treated as a default operating mode, not a per-project reminder.

**How to apply — before starting a token-heavy step, ask "is there a cheaper way to get this same fact?"**:
- Driving a browser UI → get facts via `innerText()`/`getAttribute()`/`evaluate()`, not full-page screenshots; screenshot only for first-time layout discovery or a cropped `element.screenshot()`. See [[feedback_reduce_browser_automation_tokens]].
- Waiting on a long background task → don't `ps aux`/`tail` repeatedly; wait for the completion notification (or a long `ScheduleWakeup` interval) instead. See [[feedback_avoid_excessive_background_polling]].
- A click-heavy, low-automation-value web UI (e.g. Power BI Service) → default to giving instructions/DAX/explanations for the user to execute himself rather than driving the browser, unless he explicitly asks Claude to drive it. See [[feedback_token_conscious_powerbi]].
- A task that will require opening many images (rendering PDF pages, generating thumbnails, comparing multiple photo candidates) → flag the expected volume and confirm before starting, rather than just doing it. See [[feedback_confirm_before_image_heavy_work]].
- Trying to identify what's inside a rendered output (PDF, exported image) → check whether the original editing-source file (Illustrator `.ai`, pptx, InDesign, a video-editor project file) is available and text-parseable first (`strings`/`grep` for embedded paths and metadata, `python-pptx` for text/notes) before falling back to viewing images. See [[feedback_trace_to_source_files_to_save_tokens]] and [[feedback_extract_from_project_files_before_asking]] (the latter specifically for structured project files like `.prproj`/`.aep`, and for preferring extraction over asking the user a question he'd have to type in by hand).
- Deciding whether a data-processing step needs an LLM at all → sample the actual data first; structured/pick-list data should be parsed deterministically (regex, existing master list, DB index), not routed through an LLM. See [[feedback_prefer_deterministic_over_llm]].

**New incident category added 2026-09-17 ([[currencysort_app_project]], iOS実機デバッグ)**: iterative native-app build→install→launch→ask-user-to-test→screenshot→repeat cycles (Xcode/`xcodebuild`/`devicectl`) are also token-expensive — each cycle carries large build logs, multiple device-state round trips, and screenshot reads. During an extended OOM-crash debugging session, several single-hypothesis fixes were tried one at a time (resolution cap → downscale → autoreleasepool → request reuse → adaptive TTA) before finding the real root cause (two heavy Vision pipelines — OCR `.accurate` and 4-orientation Core ML TTA — running concurrently via `async let`), at which point the user explicitly flagged token usage and asked for more careful, consolidated changes rather than continued trial-and-error. **Lesson for next time**: when a crash/bug survives 2+ incremental fix attempts, stop and audit *all* concurrent/heavy code paths touching the same resource (not just the most recently-edited one) before trying another incremental patch — bundle the next attempt as one well-reasoned, multi-part fix rather than one variable at a time. Also worth noting as a recurring friction (not token-related but adds a round-trip each build): `xcodegen generate` silently resets the Xcode-GUI-only Signing Team setting, requiring the user to re-select it in Xcode every time — expect this after any `project.yml`-affecting change and don't add resources/files without batching other changes into the same regenerate.

**Escalation added 2026-09-03**: user noticed heavy overall token consumption and asked, unprompted, whether it was this session's work or a different session running in parallel (he regularly has multiple Claude Code sessions/windows open at once — confirmed via `ListAgents` in that session showing 5 concurrent peer sessions). Beyond "quietly prefer the cheaper method" (the existing rule above), the user wants an explicit **consent gate**: when a task is about to become token-heavy, stop and get his approval before proceeding, rather than just picking the cheaper option silently and continuing. Apply this across all projects. Since one session cannot see another session's token usage or activity, if the user asks "is this heavy usage you or another session," answer honestly from what's actually checkable in the current session (own context-budget remaining, whether any subagents were spawned from here) and say plainly that other concurrent sessions aren't visible — don't guess at what another session is doing.

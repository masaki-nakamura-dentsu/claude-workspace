2026-08-26、[[powerbi_gbc_dashboard_current_state]]作成のきっかけとなった発言: 「このプロジェクトはすべてあなたと相談をしながらやっているのですべての設定は過去の履歴を整理すると分かると思います。一度すべての設定を書き出してMDファイルに保存してておいてはどうでしょうか？今後の更新もそのファイルに更新情報を入れるのが良いと思います。...確認作業が多発しており、情報をまとめたほうが良いと思います。」

**背景**: [[powerbi_migration_gbc_dashboard]]は1000行超の時系列トラブルシューティングログになっており、「今何がどうなっているか」を都度過去ログから再構成する必要があり、同じ確認作業(スライサー構成・リレーションシップ・メジューの現状等)を繰り返す非効率が発生していた。

**Why**: 時系列ログは「経緯・デバッグ過程」の記録には強いが、「現在の状態」を知るには不向き(過去の記述が後から上書き・訂正されていることが多く、末尾まで読まないと最新状態が分からない)。プロジェクトが長期化・多セッション化するほどこのコストが積み上がる。

**How to apply**: 同種の長期プロジェクト(1つのシステム/ダッシュボード/自動化パイプライン等を何セッションにもわたって育てているもの)で、確認作業の繰り返しが目立ってきたら、ユーザーから言われる前でも「現状スナップショット」ドキュメントの作成を提案する価値がある。構成の目安:
- 時系列ログ(既存)はそのまま残し、詳細な経緯・デバッグ手法の参照先として使い続ける
- 新しい「現状」ドキュメントは、データソース/構成要素一覧/主要な設計パターン(evergreenな再利用可能知識)/既知の罠一覧/現在の未解決事項/更新ログ、のようにセクション分けする
- 「現状」ドキュメントは設定を変更するたびに更新するのが前提——時系列ログへの追記だけで済ませず、該当する「現状」セクションも都度書き換える
- 断定できない部分(ログから確実に読み取れない設定)は「要確認」と明記し、ライブの実物を正とする姿勢を明示する

関連: [[powerbi_gbc_dashboard_current_state]](このパターンの最初の実装例)、[[feedback_token_conscious_powerbi]](同プロジェクトの別の運用方針)。

Discovered 2026-10-15 while building Japanese demo documents (client brief, contract) for [[ai_katsuyo_pj_weekly_tips]]'s ChatGPT lecture. The docx skill's standard verification step (`soffice --headless --convert-to pdf` → `pdftoppm`/`qlmanage` → visual check) produced a blank-looking page for Japanese text. Investigated further with `pypdf` text extraction and found the PDF's actual text layer was corrupted — all distinct Japanese characters were being mapped to the same single glyph (e.g. "クライアントブリーフ" became "ククククククククク", "新商品" and other 新-containing words all became strings of "新"). This is **not** a rendering-only/visual problem fixable by viewing in a different app — the exported PDF's text content stream itself is wrong, so it would look broken/garbled in any PDF viewer, not just in this sandbox's thumbnail tools.

**Root cause (as far as diagnosed)**: `soffice` on this Mac is `~/Applications/LibreOffice.app` (not a system install), invoked headless via `SAL_USE_VCLPLUGIN=svp`. No CJK-capable font was resolvable at export time — `/Library/Fonts/Microsoft/` has real Japanese fonts (MS Gothic, Yu Gothic, Yu Mincho) installed system-wide, but headless soffice's font resolution didn't pick them up even when explicitly set via `font: 'Yu Gothic'` in the docx-js source. `fc-list`/`fc-cache` are not installed on this machine (no working fontconfig CLI to diagnose/fix the cache directly), and `/usr/local/etc/fonts/fonts.conf` doesn't exist, so there's no straightforward one-line fix available; didn't pursue further (e.g. installing a bundled Noto Sans CJK font into LibreOffice's own `Resources/fonts/truetype/`) since it wasn't necessary for the task at hand.

**How to apply**: On this Mac, don't trust `soffice`-generated PDF output for any Japanese/CJK content without verifying the actual text layer (`pypdf`/`pdftotext`, not just a visual thumbnail) — a visual check alone can miss this because the corrupted glyphs may still *look* plausible at a glance or render as blank space (easy to mistake for a font-substitution issue rather than data corruption). Until this is fixed (e.g. by getting a real CJK font into LibreOffice's bundled font directory and confirming fc-cache rebuilds), prefer delivering Japanese documents as `.docx`/`.xlsx` directly (opened and rendered correctly by real Word/Excel, which the user has installed) rather than pre-converting to PDF via this pipeline. If a PDF is specifically required, consider driving actual Word via AppleScript/"Save as PDF" instead (uses real macOS font rendering), or ask the user to export manually.

**Workaround confirmed for .pptx specifically (2026-10-15)**: `qlmanage -t -s <size> -o . file.pptx` (macOS QuickLook thumbnailing, not `soffice`) renders Japanese text correctly — QuickLook uses the real macOS font system (CoreText), not LibreOffice's broken fontconfig path, so this sidesteps the corruption entirely for visual QA. `qlmanage` only thumbnails the *first* slide of a multi-slide deck, so to QA other slides: copy the `Presentation`, strip all `sldId` entries except the one you want to inspect (`prs.part.drop_rel(rId)` + `_sldIdLst.remove(sldId)` per [[dentsu_pptx_template]]'s safe-deletion pattern), save as a single-slide `.pptx`, then `qlmanage` that. Used successfully to QA a 13-slide deck's layout (text overflow, placeholder collisions) for [[ai_katsuyo_pj_weekly_tips]]'s ChatGPT lecture PPTX. This does NOT help for `.docx`/`.xlsx` review (QuickLook's Office previewer for those formats was not tested here) — only confirmed for `.pptx`.

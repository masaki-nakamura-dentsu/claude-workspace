**Rule**: whenever Nakamura-san (or anyone) reports that ChatGPT's "Agency OS" Skill gave a low-quality answer — no internal citations, a fabricated name, or it jumped straight to clarifying questions without searching anything — check which ChatGPT model the conversation is using *before* suspecting the Skill's data or instructions. If it's an Instant/fast model, that's very likely the entire explanation.

**Why**: confirmed as a reproducible pattern across at least 3 separate incidents:
- 2026-09-11: 4 shared-link test conversations on the same KFC Malaysia brief — the only one with successful internal-knowledge citation used a Thinking model; the 3 that failed all used "5.5 Instant" (one literally said "アイディア出し段階なので内部検索していません", another falsely claimed "このチャット環境ではKnowledge Pack本体にアクセスできていません" even though the bundled pack is the same for every user).
- 2026-09-15 (topic_expert_index incident): asked "GBCの法務担当は誰ですか", got a fabricated name ("佐藤 真理" instead of the real "佐多 茜"). Verified via direct Skill-editor inspection that the data and `SKILL.md` were both correct and saved. On "5.5 Instant" it still couldn't search and answered wrong; switching to "5.5 Thinking" in the same chat immediately produced the correct, cited answer.
- 2026-09-15 (this incident, same day, [[gbc_intelligence_engine_project]] Global Department Index work): "ユニ・チャームの海外向け契約交渉について相談したい" — the ChatGPT Skill answer did zero internal search and went straight to a clarifying-questions list, while the exact same prompt on the Dify deployment (which enforces search via hard-wired workflow nodes, not a soft instruction) returned full CASE records, a matching Global Department, and overseas staff — proving the SKILL.md content itself was fine.

The structural reason Dify doesn't have this failure mode: its knowledge search is a dedicated workflow node that runs unconditionally before the main LLM call — search isn't something the model can choose to skip. ChatGPT's Skill has no equivalent hard guarantee; it relies entirely on the model voluntarily invoking a search tool mid-turn, and Instant-tier models are measurably less reliable at this than Thinking-tier models. No amount of added `SKILL.md` prompt text ("always search," "attempt search before saying unavailable," etc. — already tried) fixes this, because it isn't a compliance-wording problem, it's a tool-calling reliability gap tied to the model tier itself.

**Confirmed 2026-09-15 (same day, this incident)**: Nakamura-san switched the model to **"ChatGPT 5.5" with reasoning effort set to 高 (High)** — the current UI exposes a 5-level effort selector, and 高 is the middle (3rd of 5) rather than the top setting — and got the correct Global Department / CASE / staff results immediately. So the earlier "Instant vs Thinking" framing above was a simplification from before this 5-level selector existed/was noticed; the actual mechanism is a reasoning-effort slider.

**Revised same day, second follow-up test — this is NOT a clean threshold, treat it as probabilistic, not deterministic**: Nakamura-san then tried the 2nd-from-bottom level and it *also* correctly retrieved internal knowledge, and noted the lowest level might sometimes succeed too — "何が本当の要因かはまだはっきりしません" (what the real cause is isn't actually clear yet). This matches what tool-calling reliability research generally shows: reasoning effort shifts the *probability* a model chooses to invoke a tool mid-turn, it doesn't gate it at a hard cutoff. **Do not state or imply a specific effort level "guarantees" success, and do not claim a specific level is the minimum that works** — both of those framings go beyond what's actually been observed (a handful of manual tests, not a controlled sample). What's actually established: (a) the *lowest* effort setting is visibly less reliable at calling the search tool (multiple confirmed failures there), (b) higher effort settings have so far always succeeded when tested, (c) the precise relationship between effort level and search-tool-call probability is unknown and may not be worth pinning down further — treat "higher effort = more reliable, not more guaranteed" as the honest takeaway rather than continuing to chase an exact boundary.

**Confirmed 2026-09-29 (4th occurrence, [[gbc_intelligence_engine_project]] credentials_facts_01.md verification) — AND a new complication, raising effort alone did NOT fix this one**: after re-uploading an updated `credentials_facts_01.md` to both ChatGPT Skill and Dify, ran the same COMMON KNOWLEDGE TEST MODE prompt (dentsuグループの従業員数/Net Revenue/地域別構成比/クライアント数) on both. Dify (hard-wired knowledge-search node) passed cleanly via direct hit-testing. ChatGPT Skill failed on Instant with the usual signature (live web search — response URLs carried `utm_source=chatgpt.com` — mismatched page citations, restated the old "11,000+ clients" figure the pack had deliberately changed to "ー(非公表)", no mandatory "Test provenance" footer). Nakamura-san then raised the model to **中程度 (medium) reasoning effort** and retried the identical prompt in the same chat — **it failed again with the exact same signature** (still `utm_source=chatgpt.com` web-fetched URLs, still Financial Report/Integrated Report page numbers that don't match the bundled pack, still no Test provenance footer), though this retry did correctly avoid asserting "11,000+" as current (instead surfaced an unrelated, unverified "Global Accelerator clients: 40" figure it found on the web).

**Retracted same day — the "browsing tool preference" hypothesis above was wrong; real cause found**: Nakamura-san reported the actual reason both the Instant and 中程度(medium) attempts failed — **the Skill itself was still in "Needs Review" (unapproved) state after the `credentials_facts_01.md` re-upload, so it wasn't active/loaded in that chat at all**, and ChatGPT was just behaving as plain ChatGPT with web browsing (explaining every symptom: `utm_source=chatgpt.com` URLs, mismatched page citations, no "Test provenance" footer — the SKILL.md text defining that mode was never in context). Once the pending approval was cleared and the identical prompt re-sent at 中程度 reasoning effort, it passed cleanly and precisely: `p.3` for employees(約67,000)/Net Revenue(1,197.5bn), `p.20` for regional split (Japan 42%/Americas 26%/EMEA 23%/APAC 9%, matching the bundled pack exactly), clients correctly stated as 非公表 (not "11,000+" or any fabricated figure), and a fully-formed Test provenance footer (mode/sources/buckets/no-external-use, per SKILL.md's own required format). This confirms `credentials_facts_01.md`'s content and the 非公表 fix are correct on the ChatGPT side too — the whole detour above was a false lead caused by testing before the pending approval was cleared, not a reasoning-effort or tool-choice issue at all for this incident.

**New standing lesson from this**: [[feedback_agency_os_is_chatgpt_skill_not_gpt]] already documents that editing a Skill's files can put it into a "Needs Review" state requiring a UI approval click before it's usable again. **Add this as step 0 of this memory's diagnostic checklist, before touching the model/effort dial**: any time Skill files were just edited/re-uploaded and the very next test looks like a total non-engagement with the internal pack (live web search, no Test provenance footer even though a test-mode phrase was used, citations to sources/pages that don't exist in the bundled files) — check the Skill editor for a pending "Needs Review"/approval banner FIRST, before concluding it's a reasoning-effort/model-tier problem. A skill stuck in Needs Review looks behaviorally identical to the classic low-effort failure signature, so don't skip straight to the effort-dial diagnosis when a file was just changed.

**How to apply**: 
1. When Agency OS on ChatGPT looks broken (no citations, fabrication, straight to clarifying questions with no search attempt), the first diagnostic step is "what model/effort is this chat set to" — check the model picker near the message composer. If it's at the lowest effort setting, raise it (higher has been more reliable in every test so far, though not proven to be a hard guarantee) and retry the exact same prompt in the same chat before doing anything else (don't touch `SKILL.md`/Knowledge files first). Don't frame this to the user as "level X definitely fixes it" — frame it as "lower effort measurably increases the risk of this failure, higher effort reduces it."
2. This has been identified 3 times now and each time the immediate fix (switch model, retest) worked, but the broader mitigation — telling every actual user/PoC participant of Agency OS to default to a Thinking model — has been flagged as an open action item across multiple sessions (2026-09-11, 2026-09-12) and never actually completed. Next time this comes up, suggest formalizing it: a short standing note in wherever Agency OS is introduced to new users (PoC recruitment deck, onboarding doc, or a visible line in the Skill's own description) rather than re-diagnosing this from scratch yet again.
3. Dify's dedicated-node architecture doesn't have this problem — this is specifically a ChatGPT Skill deployment issue. Don't assume a ChatGPT-side symptom also affects Dify (and vice versa) without checking; treat them as genuinely independent behaviorally, per [[feedback_agency_os_skillmd_multi_deployment_sync]].

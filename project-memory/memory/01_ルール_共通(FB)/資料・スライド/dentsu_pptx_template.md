**Gotcha — Statement-family layouts have huge negative letter-spacing baked in**: `Statement slide-01`'s body placeholders define `spc="-700"` (i.e. -7pt tracking) in their `lstStyle`, tuned for ~120pt display text. If you grab `placeholder.text_frame` and just `paragraph.add_run()`, you append your text after the existing example run instead of replacing it. Always call `text_frame.clear()` first before adding your own paragraphs/runs to any placeholder pulled from this template.

**`Contents-01` layout's list placeholder inherits auto-numbering that isn't visible in the layout's own paragraph XML (2026-08-25, [[ai_agency_team_build]])**: the body placeholder (idx 14) on `Contents-01` renders each paragraph with a native `1. / 2. / 3.` auto-number prefix even though the layout's own `<a:p><a:pPr lvl="0"/>...` XML has no `buAutoNum` element — the numbering is inherited from the master/layout's list style further up the style chain. If your own text already supplies a number/section-code prefix (e.g. `"01  Client Challenge"`), the rendered result doubles up (`1.  01  Client Challenge`). Fix: after writing your text, explicitly disable the inherited bullet on each paragraph by adding a bare `<a:buNone/>` to that paragraph's `pPr` (remove any existing `buChar`/`buAutoNum`/`buNone` first, then append):
```python
from pptx.oxml.ns import qn
def disable_auto_bullet(paragraph):
    pPr = paragraph._p.get_or_add_pPr()
    for tag in ('a:buChar', 'a:buAutoNum', 'a:buNone'):
        el = pPr.find(qn(tag))
        if el is not None:
            pPr.remove(el)
    pPr.append(pPr.makeelement(qn('a:buNone'), {}))
```
This generalizes the bullet-doubling gotcha already noted in [[feedback_bilingual_single_file_pptx]] (there observed on a "Statement"-style headline placeholder with a manual `1./2./3.` prefix) — check any placeholder you're feeding manually-numbered or manually-prefixed text into, not just Statement layouts.

**`Chart-grey`/`Chart-off-black`/`Chart-off-white` layouts have a real `CHART` placeholder (idx 11) usable with python-pptx's native chart API (2026-08-25, [[ai_agency_team_build]])**: `chart_ph.insert_chart(XL_CHART_TYPE.COLUMN_CLUSTERED, chart_data)` (from `pptx.chart.data.CategoryChartData`) works directly and renders correctly (verified via qlmanage) — no manual XML needed for bar/column charts. Two practical lessons from building a 6-category comparison chart: (1) `XL_CHART_TYPE.COLUMN_CLUSTERED` (vertical bars) auto-skips every-other category label when there are ~6+ categories with Japanese+English mixed text, making some bars unlabeled — switch to `XL_CHART_TYPE.BAR_CLUSTERED` (horizontal bars) instead, which lays labels out one-per-row on the left and reads far better for ranked/comparison data with long category names; note `BAR_CLUSTERED` puts the first category at the *bottom* by default, so set `chart.category_axis.reverse_order = True` if you want your #1/highest item to appear at the top. (2) Always explicitly set `chart.value_axis.minimum_scale`/`maximum_scale` (e.g. 0/100 for a percentage or /100-score axis) — python-pptx's auto-scaling can pick a much larger max than the data warrants (e.g. axis topping out at 200 for data maxing at 88), wasting most of the plot area. Apply `set_run`-style explicit `font.size`/`font.name` to `plot.data_labels.font` too, not just the category/value axis tick labels, or data-label text falls back to a mismatched default font/size.

**Resizing a placeholder's box collapses left/width to 0 if you only set top/height (2026-08-27, [[nihon_gakudosya_proposal]])**: many layouts in this template (`Section divider-*`, `Statement slide-01`, `Closing-01`) ship placeholders sized/anchored for exactly one short line (e.g. `anchor="ctr"` in a box only ~0.9in tall) — stuffing multi-paragraph text into them as-is causes vertical overlap since the box doesn't grow. The fix is to reposition the placeholder (bigger height, `anchor="t"`) via its `.top`/`.height`/bodyPr `anchor` attribute — **but if the slide-level placeholder has no explicit `<a:xfrm>` yet (true whenever you haven't touched its geometry, since it's normally inherited from the layout), setting only `.top =`/`.height =` makes python-pptx create a *fresh* xfrm with `off.x`/`ext.cx` defaulting to 0**, i.e. left and width silently collapse to zero even though you never touched them. Symptom: text renders as a single character per line cascading down the far-left edge of the slide (word-wrap trying to fit into a ~0-width box). Fix: **read `ph.left`/`ph.top`/`ph.width`/`ph.height` first (this reads the correctly-inherited layout values even with no explicit xfrm), then re-assign all four** (the two you're changing plus the two you want to keep) in one go — never set just one axis on a placeholder that might still be inheriting its geometry.

**Safe patterns for adding/reordering slides (2026-08-06, [[toyota_india_aot_hyryder_project]])**: (1) to clone a simple slide (e.g. a divider with a couple of text shapes), don't hand-write new XML — call `prs.slides.add_slide(existing_slide.slide_layout)` to get a genuinely new, properly-named part through the normal API, strip its auto-created placeholder shapes, then `copy.deepcopy()` the source slide's shape elements into the new slide's `spTree` and edit the text. This is a pure *add*, so it doesn't trigger the delete+add part-collision bug below. (2) Pure slide reordering — removing `sldId` elements from `prs.slides._sldIdLst` and re-appending them in a new order, with no part added or dropped — is safe and doesn't corrupt anything; use it freely to consolidate scattered content instead of physically moving slide content. (3) When renumbering circled-digit (①②③④) labels across many slides in a restructure, use one atomic `str.translate({'②':'③','③':'④'})`-style map applied in a single pass, not sequential `.replace()` calls — a single sentence can reference two different renumbered directions at once (seen on a real slide), and sequential replacement would double-translate the second occurrence.

**Cross-presentation slide copying (2026-08-06, [[toyota_india_aot_hyryder_project]])**: to clone a slide from a *different* `Presentation` object (not the same file), plain `copy.deepcopy()` of the shape XML is not enough — any `<p:pic>` element (including ones nested inside `<p:grpSp>` group shapes, at any depth) carries an `r:embed` relationship id that only resolves inside the *source* file's `.rels` part; pasted as-is into the destination it's a dangling reference. Fix: after deepcopy, recursively find all `p:pic` elements (`el.findall('.//' + qn('p:pic'))`, plus the element itself if it's directly a `p:pic`), resolve each one's image part via `src_slide.part.related_part(rId)`, pull `.blob`, re-embed into the destination via `dst_slide.part.get_or_add_image_part(io.BytesIO(blob))`, and overwrite the copied element's `r:embed` attribute with the new rId. Match the destination slide's layout by *name* (`find layout in dst_prs.slide_masters where layout.name == src.slide_layout.name`) via `dst_prs.slides.add_slide(matching_layout)`, then strip its auto-created placeholder shapes before appending the copied ones — this only works when both files share the same underlying template (so a same-named layout actually exists on both sides); verified safe via qlmanage pixel comparison against the source slide, including for a slide with nested-group pictures.

**Multi-run paragraph restyling — always iterate every run, not just the first (2026-08-06, [[toyota_india_aot_hyryder_project]], hit 3x in one day)**: when a paragraph has an embedded-foreign-word or hyperlink split across multiple `<a:r>` siblings (e.g. a Japanese sentence containing an English proper noun as its own run, or a URL broken into `youtube.com`/`/`/`watch?v`/`=id` fragments), any bulk restyle/duplicate/**or plain single-run text edit** must check `len(para.runs)` first and strip/update *every* run, not just `para.runs[0]` — editing only the first run leaves the rest as stale trailing text glued onto the new content (garbled overlapping text if restyling, or literally leftover old text/URL fragments appended if just changing wording). This is common enough on this specific deck that it should be a reflexive first check before editing *any* existing text run, not something to rediscover per-slide.

**Flipping which language is "primary" requires a full layout re-check, not just a recolor (2026-08-06, [[toyota_india_aot_hyryder_project]])**: swapping which language gets the larger/bold styling changes how much space is needed — English words run longer than the equivalent Japanese, so a caption box that fit fine with JP-primary can overflow to 2 lines the moment EN becomes primary at the same size, even though nothing about the box itself changed. Any hierarchy-direction change must re-verify every affected box's height/wrap behavior from scratch, treating an already-working layout fix for one direction as no guarantee for the reverse.

**Positioning/quadrant-map slides — no existing recipe, build from primitives**: for a 2×2 strategy map (distinct from this deck's usual photo+caption pattern), build via `add_slide()` on any existing content layout, then compose manually: `MSO_SHAPE.RECTANGLE` for the plot box, `shapes.add_connector(1, ...)` for the two axis lines, `MSO_SHAPE.OVAL` + centered text for circular markers, plain textboxes for axis-end and marker labels. Two label-collision traps to design around from the start: (1) axis-end labels sitting just outside the box can collide with the *nearest row* of marker labels if that row's labels also point outward — give axis labels extra clearance or shrink/reposition the plot box, don't just eyeball a fixed offset; (2) marker labels should point *away* from the nearest plot-box edge (e.g. labels for markers in the bottom half of the box should render *above* the marker, not below), otherwise they run off the box into the axis label. Verify empirically via qlmanage — the exact wrap width of marker names makes hand-computed EMU math for label collision unreliable in practice.

**Retrofitting a custom-built (non-template) deck onto this template, and sourcing case-study photos from the web (2026-09-04, France pitch "National Resilience" deck)**: when asked to "make this look dentsu" for a deck that was built from scratch with plain textboxes/autoshapes (slide_layout.name == "DEFAULT" for every slide — i.e. not derived from any template), the fastest reliable path is NOT to hand-copy background art, but to (1) open this template fresh, strip its sample slides, (2) for each source slide pick the real layout whose native placeholder count/shape matches the content (a "3 items with number+heading+body" slide maps directly onto `3x column-plain off-white`'s 3 BODY placeholders; a "2 comparison panels" slide onto `2x column-plain off-white`; a single photo + text case-study onto `Image right-off-white`'s TITLE+BODY+PICTURE placeholders), (3) build brand-new slides via `add_slide(layout)` and fill the *native* placeholders with multi-paragraph text (chip/heading/body as separate paragraphs in one placeholder) rather than reproducing the many small custom textboxes from the source deck. This gets the correct background art, footer wordmark, and live page-numbering for free with far less code than copying graphic elements. **Gotcha — build slides grouped by type, then reorder**: it's much simpler to write one generation loop per content-shape-pattern (all 3-column-card slides together, all 2-photo-panel slides together, etc.) than to preserve the source deck's narrative order inline — but that scrambles the deck. Fix: keep a `built[original_index] = slide` dict as each slide is created, then at the very end do a pure reorder (safe per the technique below in this file): clear `prs.slides._sldIdLst` and re-append each entry's sldId in `range(n_slides)` order looked up via `{id(slide.slide_layout... wait — via a `part -> sldId` map built by walking `prs.slides._sldIdLst` once and matching `slide.part`}`. No slides are added or dropped, so this is the safe pure-reorder case, not the delete+add part-collision hazard.
**Gotcha — a wrapped 2-line title collides with a JP-subtitle textbox placed "right after" the title placeholder**: if page titles vary in length, some will wrap to 2 lines inside a 1-line-tall title placeholder box (the box doesn't auto-grow), and a JP subtitle textbox positioned at `title.top + title.height` will overlap the wrapped second line. Fix: always give the title placeholder a fixed height sized for the worst case (2 lines) regardless of actual content, and hang every subsequent content region off that same fixed offset — don't compute per-slide from the placeholder's actual (unwrapped) height.

**Fitting a downloaded photo of unknown/awkward aspect ratio into a template's PICTURE placeholder**: don't rely on the placeholder's own `insert_picture` (it center-crops to fill, which badly over-zooms a thin banner-shaped logo forced into a tall portrait placeholder). Instead delete the empty placeholder shape (an unfilled picture placeholder shows an ugly "click to add picture" ghost icon if left in the saved file) and draw your own: a plain light-grey/off-white rectangle panel at the placeholder's old bounds, then a picture scaled via `min(avail_w/img_w, avail_h/img_h)` ("contain", not "cover") and centered inside it with ~8% padding. Works uniformly for logos, screenshots, and photos of any aspect ratio.

**Dynamically-positioned text blocks need line-count estimation — use `math.ceil(len(text)/chars_per_line)`, not `len//N+1`, and don't compound safety buffers across stacked elements (2026-10-15, [[ai_katsuyo_pj_weekly_tips]] ChatGPT lecture PPTX)**: when a slide's content is built from variable-length strings (descriptions, prompts, bullet steps) and each subsequent textbox's `top` is computed from the previous one's estimated bottom (`y += estimated_lines*line_height + gap`), getting the line-count estimate right matters a lot — both under- and over-estimating cause visible bugs. Under-estimating (`len(text)//N + 1` with too-large `N`, i.e. too many chars/line assumed) causes real overlap: later text renders on top of earlier text's visually-wrapped last line. Over-correcting by adding a flat `+2` lines of buffer *per text block* looks fine for one block but **compounds** when several blocks stack on the same slide (desc → steps → workaround → note), pushing later content below the 7.5in slide bottom entirely (content silently vanishes off-slide — easy to miss without rendering every slide). The fix that worked: `lines = math.ceil(len(text) / chars_per_line)` (one clean estimate per block, no stacked padding), `chars_per_line` calibrated empirically per font-size/box-width combo via the render-and-check loop below (for 16pt Verdana-ish body text: roughly 62-66 chars/line at ~11.4in full slide width, 42-50 chars/line at ~6.9in half-width-with-image), and only a modest *flat* gap (~0.25-0.3in) added once after each block, not folded into the line-count. **How to apply**: for any slide-generation script with cascading dynamic `y` positions and 16pt+ body text, calibrate `chars_per_line` empirically (render a real content-heavy slide, measure actual wrapped line count against the estimate, adjust the divisor) rather than guessing, and keep line-height and block-gap as separate, non-compounding terms.

**When a single slide's full-fidelity content (long description + long prompt + caveat + source + a closing "point" line) doesn't fit even after tightening spacing, split by concept rather than shrinking type below the user's stated minimum (2026-10-15, same session)**: a two-concept guide card ("Custom GPT" + "Projects" explained together with a 2-column step list and a shared screenshot) kept overflowing at 16pt no matter how tightly packed — the fix was to **split into two single-concept slides** (one per explained feature), each getting the full slide width for its own step list and its own screenshot, rather than cramming two into one. Separately, a recurring per-topic "ポイント" (conclusion) line appended to the last technique's slide kept colliding with that slide's own content on the longest cards — fixed by **promoting it to its own dedicated slide** (one per topic, title + large centered conclusion text) instead of trying to append it after already-dense content. General lesson: once a content-fidelity requirement (don't trim) and a minimum-font-size requirement both constrain a slide and it still won't fit, the answer is usually to add another slide (split by concept), not to fight the layout harder.

**Critical gotcha, actually caused real data loss (2026-08-04, [[toyota_india_aot_hyryder_project]])**: deleting N slides (`drop_rel` + `_sldIdLst.remove()`) and then *adding* new slides in the same script can make python-pptx's part-namer reuse `ppt/slides/slideN.xml` numbers that are still physically referenced by *other, untouched* slides elsewhere in the deck (not the ones just deleted). The save succeeds with only a quiet `zipfile` `UserWarning: Duplicate name` (easy to miss in output), and `Presentation(path)` reopens "fine" but silently resolves both the old and new content to whichever bytes were written last for that name — meaning two unrelated slides (in this case the deck's summary and closing slides) appeared to have vanished, replaced by duplicates of the newly-added ones. **Mandatory after any save that both deletes and adds slides**: `from collections import Counter; Counter(zipfile.ZipFile(path).namelist())` and confirm no entry appears more than once, *before* telling the user the edit is done — don't rely on `len(prs.slides)` or a title scan alone, both looked plausible while the file was actually corrupted. If it does happen, both blobs are still physically recoverable: open with `zin.infolist()` (position-ordered, duplicates preserved), read the *first* occurrence of the colliding name (the original, older content) and the *second* (the new content) by exact ZipInfo object, rename the second's part + its `_rels` file to an unused slide number, patch the one `presentation.xml.rels` relationship that pointed at the old name, and add a matching `[Content_Types].xml` `<Override>` for the new part name. Safer prevention going forward: add all new slides *first*, confirm the save is clean, *then* delete the ones you meant to remove in a separate save — don't interleave add+delete in one script.

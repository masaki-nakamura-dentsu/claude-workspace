配信済み/作業中のファイル(デッキ・ドキュメント・スプレッドシート等、拡張子問わず)を修正するときは、絶対に元ファイルを上書きしない。新規保存する際のファイル名ルール:
- ファイル名の末尾(拡張子の直前)に**既にYYYYMMDD形式の値がある場合は、その値を今日の日付に置き換える**(新しい日付を付け足さない)。例: `report_ver20260724.xlsm`を8/7に修正 → `report_ver20260807.xlsm`(`report_ver20260724_20260807.xlsm`のように二重に付けない)。
- 末尾にYYYYMMDDが**まだ無い場合のみ**、今日の日付をYYYYMMDD形式で付け足す(例: `report.pptx` → `report_20260718.pptx`)。
- 同じ日にさらに修正する場合は、日付の後ろに2桁の連番`_01`, `_02`...を付ける(`report_20260718_01.pptx`, `_02`...)。

**2026-08-07 訂正**: 上記の「既存YYYYMMDDを置き換える」ルールは、当初(2026-07-18〜2026-08-05時点)は明文化されておらず、JCIピッチリストのVBA修正(ver20260724.xlsm → ver20260724_**20260807**.xlsmと日付を付け足してしまった)でユーザーから直接指摘を受けて確定した。CLAUDE.mdの該当ルールもこのタイミングで同様に修正済み。

**Why:** ユーザーが2026-07-25に明示的に再確認したグローバルルール(CLAUDE.mdにも既存記載あり)。写真塾78回の制作でこのルールを徹底できておらず、同日中に同じファイル名へ複数回上書きしてしまい、ユーザーの手動修正を失う事故につながった([[feedback_pptx_edit_existing_not_rebuild]]参照)。

**How to apply:** ファイルを保存するたびに、まず対象フォルダで同日の既存バージョン(`_YYYYMMDD`, `_YYYYMMDD_01`など)を`ls`/`find`で確認し、最新の連番+1のファイル名で保存する。ユーザーが「保存し直した」「名前を変えた」と言った場合は、まずそのフォルダを検索して実際に今どのファイルが最新かを特定してから作業を始める。

**2回目の違反、新しい失敗パターン(2026-08-05, [[toyota_india_aot_hyryder_project]])**: 8/3に作成したデッキを、同じ会話セッション内で8/4・8/5と複数日にわたって延々と同一ファイルへ上書きし続けてしまった(コンテンツ修正・破損復旧・新方向性追加など計10回以上の保存)。日付は`ls`結果からではなく、会話開始時に一度見ただけの「今日の日付」を保持し続けており、セッションが日をまたいでもファイル名の日付を再チェックしなかったのが原因。ユーザーから指摘されて気づいた。**教訓:長時間・複数ターンにわたる同一ファイルへの反復編集セッションでは、保存のたびに`date`コマンドで実際のシステム日付を確認し、ファイル名の日付と食い違っていないか毎回チェックする**(タスク開始時に一度確認するだけでは不十分)。同日内の複数回保存についても、実際には`_01`/`_02`を付けずに同名へ上書きし続けていたため、既存バージョンは実質的に失われている(過去の中間状態は復元不能)。今後は本当に「保存するたびに」連番判定を行うこと。

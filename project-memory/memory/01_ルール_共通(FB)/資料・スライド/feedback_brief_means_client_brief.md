広告代理店の実務で「ブリーフ」と言うときは、まず「クライアントから電通側に届く入力ドキュメント」の意味を最優先で疑う。Agency OS([[gbc_intelligence_engine_project]]参照)のworkspace用語でも"CLIENT BRIEF"はこの意味で使われている。

**Why**: 2026-09-09、GBC Agency OS PoC説明会用に6人のGM(AP2部小川様/AP3部金井様/BD部新保様/SP1部山本様/SP2部土門様/SK部山田様)分の「仮ブリーフ」を依頼された際、最初はHTML Artifactで「各GMの実案件にAgency OSの各エージェント(Researcher/Strategic Planner等)がどう効くか」を説明する内部向け資料を作ってしまった。ユーザーから「私のお願いしたことではありません。通常、みんなが入手するブリーフはWordやメールでもらいます。クライアントから来ている想定で書かれているブリーフです」と明確な訂正が入り、Word文書(python-docx、クライアント一人称視点、背景/依頼内容/ターゲット/現状課題/成果物/予算感・スケジュール/留意事項)として作り直した。

**How to apply**: 依頼に「ブリーフ」という言葉が出てきたら、それが (a) クライアント視点の入力ドキュメント(オリエン資料)なのか、(b) 何かを説明・提案するための内部資料なのか、を最初に見極める。(b)が欲しい場合ユーザーは通常「説明資料」「提案書」「PoC資料」等の別の言葉を使う傾向がある。曖昧なままAgency OSやAI活用文脈が絡む依頼で「ブリーフ」と言われたら、(a)をデフォルト解釈とし、早い段階で一言だけ確認するか、着手前に解釈を明示してから作業に入ると手戻りを防げる。

同じセッションで、GMごとの実案件と紐付けるにあたり「本人が責任者(GBC)として登録されている案件が見つからない部署は、部の代表事例で代替してよい」という運用も確認済み。さらに、その代替事例が案件データ的に薄い(SK部=戦略企画部はクライアント業務が少ない)場合、ユーザーは機械的な抽出結果に固執せず、別の実プロジェクト([[france_pitch_national_resilience_deck]]、フランス政府のレジリエンス・コミュニケーション事例依頼)への差し替えを自ら指示した。GM別に実案件を紐付ける依頼では、Salesforceデータだけに頼らず、ユーザーが把握している他の実プロジェクトも候補になり得ることを念頭に置く。

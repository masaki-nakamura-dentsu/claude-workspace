Playwrightでのブラウザ自動操作時、操作のたびに全画面スクリーンショットを撮って確認する進め方は、画像トークンのコストが非常に高い。[[powerautomate_attendance_summary_project]]の作業で、Power Automateのデザイナー画面を延々とクリック→スクリーンショット確認で操作した結果、ユーザーから明示的に「トークンの消費が激しい」と指摘された。

**Why:** 画像1枚(特に2800×1626のようなRetina解像度のフルページ)は、同等の情報をテキストで取得する場合に比べて桁違いに高コスト。今回、実際には「入力した文字列が正しいか」「ボタンが有効か」といったテキストで十分確認できる内容のために、何十回もスクリーンショットを撮っていた。

**How to apply（今後の標準方針）:**
1. **テキストで分かることはテキストで取る**: `innerText()`, `getAttribute()`, `evaluate()`等でDOMの値を直接取得し、Bash経由のconsole.logで確認する。スクリーンショットは使わない。
2. **スクリーンショットは初見のレイアウト把握時のみ**: 一度セレクタや座標が分かった画面は、以降は見ずに操作し、結果はテキストで検証する。
3. **画面を見る必要がある場合は該当箇所だけを切り取る**(`element.screenshot()`)。全画面スクリーンショットは最終手段。
4. **複数操作をまとめてから1回だけ確認する**。クリックごとに確認しない。
5. **対象システムがエクスポート/インポートに対応しているなら、UIを延々操作するより「設定ファイルを書き出す→テキストとして直接編集→書き戻す」方法を優先する**(Power Automateの「パッケージのエクスポート/インポート」が好例。[[power_automate_gotchas]]のルール7参照)。
6. **簡単でリスクの低い最後の確認・クリック操作は、ユーザー自身にお願いする選択肢を積極的に提示する**。特に本人がすでにブラウザ画面を見ている状況では、その場でのワンクリックの方が速くて確実なことが多い。

この方針はPower Automateに限らず、今後のあらゆるブラウザ自動操作作業(Salesforce, Teams, ChatGPT/Gemini操作等含む)に適用する。

**2026-08-22追記（[[subway_photo_booklet_project]]、ストック写真の価格/ライセンス調査中）**: 複数サイト(Adobe Stock, Getty, Alamy)を横断してログイン・検索・価格スクレイピングを行った際、セレクタが当たらず何度も小さいデバッグスクリプトを書き直す(og:imageがダミー画像だった→CDN画像を探す→価格の通貨記号が¥でなく$だった、等)進め方でツール呼び出しが積み重なり、ユーザーから「トークンを大量に消費しているようなので私の方で進める」と指摘された。**How to apply**: (1)最初の1回で本文テキスト全体をダンプして構造を把握してから狙いを定めたスクリプトを書く(推測でセレクタを当てて外れるたびに書き直さない)。(2)同種の対象(複数URLの価格取得等)は最初から1本のスクリプトでループ処理し、結果を見てから微調整する—1URLずつ試行錯誤しない。(3)想定より試行回数が嵩んできたら、残タスクを整理してユーザーに「続けるか/ここで区切るか」を一度確認する(今回は確認したところユーザーは続行を選び、範囲を絞って完了できた)。

**2026-08-24追記([[memory_weekly_review_automation]]、Outlookカレンダーへの繰り返し予定登録中)**: タイトル入力→定期化ボタン探索→ボタン一覧ダンプ、とスクリーンショット+DOM調査を重ねていたところ、ユーザーから「トークン消費しそうだから、私の方で登録しましょうか？スケジュールのファイル作ってくれたらすぐに登録できます」と申し出があった。これはルール6の理想的な適用場面だったが、今回はユーザーからの指摘で気づいた形になった。**How to apply(強化)**: 「単純な設定を1件登録するだけ」で、かつユーザーが手動でもすぐできる作業(カレンダー予定・フォーム1件など)は、ブラウザ自動操作を始める前に「内容をまとめたファイルを渡すのでご自身で登録しますか、それとも自動化しますか」と先に選択肢を提示する。試行錯誤が数回(3〜4回)続いた時点で自動的にルール6を思い出し、指摘される前にこちらから提案する。

**2026-09-12追記・ルール格上げ（重要）([[gbc_intelligence_engine_project]]、Dify「GBC Agency OS」ワークフローにノード追加・配線する作業中)**: Dify Studioのキャンバス上でノード追加・ドラッグ配線・変数集約器へのスロット追加を、都度スクリーンショットで確認しながら数十回繰り返した（座標のズレ、ウィンドウ幅/DPRの変動、誤クリックでの手戻りも重なった）。ユーザーから3回にわたり「トークンたくさん使いそうであれば私の方でやります」「トークン消費が激しいようです」「一旦止めてください」と段階的に指摘され、最終的に「今回のあなたの動きはトークンの消費が激しすぎます。トークン消費が激しい作業は私に許可を取ってください」と明示的な恒久ルールが示された。

**Why**: 既存のルール6(「最後の確認・クリックはユーザー自身に」)は作業の**終盤**でのオファーだったが、今回のようなDify/Figma的なキャンバスGUI操作（座標推測に頼る・要素が視覚的にしか判別できない・スクリーンショット確認が本質的に必須）は、**着手前の時点で**「これは screenshot 往復が多くなる種類の作業だ」と判断できるケースが多い。手が付いてから「重くなってきたので聞く」では遅く、ユーザーが何度も同じ指摘を繰り返す羽目になる。

**How to apply（新ルール、既存ルールより優先）**:
1. 着手前に「この作業はスクリーンショットを伴う試行錯誤が多くなりそうか」を自己評価する。該当するもの: キャンバス型ワークフローエディタ(Dify Studio, Figma等)でのノード追加・ドラッグ配線、座標クリックに頼る操作が3手以上連続しそうなGUI操作、セレクタが不明で探索が必要なUI。
2. 該当すると判断したら、**着手前に**ユーザーへ一言確認する（AskUserQuestion等で「この作業はスクリーンショットを多用しそうです。続けますか、それともそちらで操作しますか」）。ユーザーが明示的に「進めて」と言った場合のみ着手する。
3. 作業中にユーザーから停止指示（「止めてください」等）が出たら即座に全てのブラウザ操作を止め、それ以上のスクリーンショットやクリックを行わない。状態確認のテキスト取得(inner_text等)程度に留め、詳細は簡潔に報告する。
4. 同一の確認を複数回求められた場合（今回のように3回連続）は、次回から「毎回本人に確認する」をデフォルト挙動にする——過去に何度も指摘された分野だと自覚し、指摘を待たずに先回りする。

**2026-09-30追記([[gbc_business_trip_management_powerbi]]、承認メール本文の末尾にテキストを1行追記する依頼)**: 「Power Automateフローのメール本文に指定文言を追記してほしい」という、本質的には単一フィールドへのテキスト追記だけのタスクで、確認や提案より先にいきなり共有ブラウザ(port 9226)でフローを開きに行った。しかも環境IDを決め打ちしたため対象フローが見つからず、無駄な探索コールを重ねかけたところでユーザーから「私の方で操作するのであなたがブラウザ操作する必要はありません」と止められた。スクリーンショットは使っておらずトークン消費自体は小さかったが、**そもそも自動化に着手する前の判断が抜けていた**: 単一フィールドへの短いテキスト追記は、正確な編集箇所と文面さえテキストで渡せばユーザーが数十秒で自分で終えられる作業であり、ルール6/2026-08-24追記が想定する「簡単でユーザーが手動でもすぐできる作業」の典型例だった。**How to apply(強化)**: Power Automateに限らず、依頼が「既存の1フィールド(メール本文の1文、件名、宛先など)に決まった文言を追加/変更するだけ」と分かった時点で、まず編集箇所と正確な文面をテキストで提示し、「この内容を反映してください、必要であれば代わりに編集します」と選択肢を添える。着手前にブラウザを開いて場所を探しにいくのは、対象が複数フィールドにまたがる/条件分岐の組み替えを伴う/新規アクション追加を伴うなど、ユーザーが自分では組みにくい変更だと分かってからでよい。

**2026-09-17追記([[gbc_intelligence_engine_project]]、dentsudot連携がDifyに反映済みか確認する作業中)**: 静的な状態確認(SYSTEM prompt本文の差分、ナレッジベースのファイル一覧・ステータス)はテキスト抽出のみで問題なく完結できた。一方、実際にDifyのプレビュー/デバッグチャットへ**動作確認クエリを送って実行させる**試みは、類似した複数のtextarea/contenteditable(LLMノード設定パネルのコンテキスト欄、Startノードのデバッグ用デフォルト値欄、実際のチャット送信欄)が見分けにくく、テキスト抽出だけで正しい入力先を特定できずに数往復失敗した(結局ワークフローは実行されず、Startノードの表示用デフォルト値欄に文字列が残っただけだった)。中村さんから作業中に「画面キャプチャは使わないでください、トークンを大量に消費します」と明示的な指摘も受けた。

**Why**: 「テキストで分かることはテキストで取る」(ルール1)は静的な内容確認には強いが、**入力欄が複数あり見た目でしか区別できない状況でどこに入力すべきかを当てる**タスクには弱い——結果的に、迷ったまま何度もスクリプトを書き直す方が、的を絞った1回のスクリーンショットより高コストになった。

**How to apply(精緻化)**: (1) 静的な状態確認(設定内容・ファイル一覧・公開状態など)は今まで通りテキスト抽出のみで行う。(2) しかし「実際にワークフロー/チャットを動かして応答を検証する」という**動的な機能テスト**は、類似入力欄が複数あるUIでは特に、テキスト抽出だけで正しい入力先を当てにいかない——(a) 中村さんに一言「この機能が正しく動くか、お手数ですが一度実際の画面でXXと聞いてみていただけますか」とその場のテストを依頼する、または(b) どうしても自動化が必要なら、最初に1回だけ対象範囲を絞ったスクリーンショット(全画面でなく該当パネルのみ)で入力欄を確定させてから操作する、のどちらかを選ぶ。何度も文章化だけで当てずっぽうに試行するのが一番トークンを消費する。

Salesforceエクスポートのxlsxを自動整形する`apply_forecast_trim_formatting`
([[sf_reports_qbr_download_automation]])を書いた際に実際に起きた事故から。

**Why**: 見出し行のすぐ下に「各年月列に同じメジャー名(例:
'GBC設定売総/SETTEI Rev(JPY) 合計:')を繰り返すラベル行」が存在するSalesforce
レポート形式があり、この行は一見データ行のように見えるが実際はテキストしか
入っていない。合計列を再計算する条件を最初「残り列に数値がある、**または**
合計列の元の値がNoneでない」としたところ、ラベル行の合計セル(文字列)が
「Noneでない」に該当し、再計算結果の0(数値)で上書きされてラベルが消える
事故になった。既に保存済みだった25ファイル全件が同じバグの影響を受け、事後の
復旧作業が必要になった。

**How to apply**:
- 一括再計算/一括書き込みの実行条件は「値が存在するか(not None)」ではなく
  「値が期待する型(数値なら`isinstance(v, (int, float))`)であるか」で判定する。
  Noneでない=データ行、という直感的だが緩い判定は、ラベル/見出しなど
  文字列が混在するテーブルでは事故る。
- 見出し行の直下に「もう1段の見出し/ラベル行」が存在するケースは実務上
  珍しくない(このレポート形式で複数回確認済み)。ヘッダー行を1行だけ
  決め打ちせず、処理対象範囲に含まれる各行が本当にデータ行かどうかを
  型チェックで都度確認する。
- 本番ファイルへの一括処理を書いたら、対象ファイル全件に対して
  「代表的な非データ行(ラベル行・小計行・合計行)の値が壊れていないか」
  「再計算結果が実データの合計と一致するか」を機械的に検証してから
  完了報告する([[feedback_verify_full_schema_before_pipeline_writes]]と
  同じ「書く前/後に実際の構造を確認する」系の教訓)。

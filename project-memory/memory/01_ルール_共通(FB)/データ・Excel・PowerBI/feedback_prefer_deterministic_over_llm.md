技術的な設計判断(LLMを使うか/どう検索を速くするか等)を中村さんに委ねられた際、
「どちらが良いか自分で考えて」と言われることがある。[[gbc_intelligence_engine_project]]
の2026-08-17のSalesforceデータ統合で、以下の判断基準が実際にうまく機能した。

## 判断基準
1. **データが既に構造化されているか確認してから、LLMを使うかどうかを決める**。
   確認せずに「とりあえずLLMで抽出」を選ばない。実例: Salesforceの5W1H欄は
   ラベル付き構造化フォーマットに従っているのはわずか2.8%で、地域(Region)列は
   実は6値のピックリストだった(事前の思い込みでは正規化やLLM読み取りが必要と
   思っていたが、実測したら不要だった)。**必ず実データをサンプリングして
   構造化度を確認してから設計する。**
2. **LLMが必要なのは「非構造化文書から事実を読み取る」段階だけ**で、
   正規化・分類・検索・集計は決定的な方法(正規表現、既存の選択肢マスタとの
   突き合わせ、DBインデックス)で代替できないか毎回検討する。決定的な方法は
   LLMより速く・無料で・ハルシネーションリスクがゼロという明確な優位がある。
3. **「検索が速い方で」のような速度要件が出た時、まず遅さの本質を特定する**。
   今回は「ファイルを1つのフォルダにまとめるか分けるか」という表面的な問いが
   出たが、本質は「毎回全ファイルを読んでいること」だった(インデックスが
   無いこと)。SQLite+FTS5のインデックスを作れば、統合するかどうかの問い自体が
   実質的に無意味になった(複数テーブルを同時にクエリしても十分速い)。
   **表面的な問いに直接答える前に、本質的なボトルネックが別にないか疑う。**

## Why
この日の作業の前半(SharePoint資料のLLM抽出)では、プロンプトの指示だけでは
ローカルLLM(qwen3:8b)の捏造("Digi-Keyは米国企業だから"、evidence中に企業名すら
無いのに"Dentsu"を生成、等)を防げず、最終的にコード側の機械的検証
(`_grounded_in_evidence()`)に頼らざるを得なかった。この苦い経験から、
後半のSalesforceデータ統合では「そもそもLLMを使う必要があるか」を先に疑う
姿勢に切り替え、結果として全く別のより安全なアーキテクチャ(決定的パース+
既存ピックリスト+FTS5)にたどり着いた。

## How to apply
今後、中村さんから「LLMを使うべきか」「どちらが良いか考えて」と技術判断を
委ねられたら、まず実データをサンプリングして構造化度を確認し、上記3点を
判断基準として提示する。単に選択肢を並べて聞き返すのではなく、実測に基づいた
結論を出してから進める(これが2026-08-17に高く評価された進め方)。

より広い「トークン意識」全般の括りは[[feedback_token_conscious_practices]]参照(2026-08-31統合)。

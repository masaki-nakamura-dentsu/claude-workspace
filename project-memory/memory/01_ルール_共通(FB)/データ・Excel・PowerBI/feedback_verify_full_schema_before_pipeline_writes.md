自動化スクリプトが「自分が書き込む対象と思っている列」と「実際にシートに存在する列」が一致しているか、書く/デバッグする前に必ずシートのヘッダー行全体をスキャンして確認すること。

**Why**: [[cas_csv_download_automation]]の2026-09-02〜03インシデントで発生。`cas_pipeline_lib.py`の`append_rows_to_workbook()`は`OUTPUT_COLUMNS`(A:N、14列)だけを書き込んでいたが、実際のRaw YTDシートにはP列(ヘッダー名「DATEVALUE」)というPower BIが日付型認識に使う隠れた計算列が存在した。この列は自動追記のスキーマ定義に含まれていなかったため、新規行(8月分)だけ空欄のまま残り、Power BIが8月データを丸ごと弾く事故になった。

ユーザーからの明示的な指摘: 「17時の更新履歴は成功」「元データは8月まで入っている」等、こちらが提示したPower BI側の診断手順(更新履歴・DAXクエリ・Power Query Editorプレビュー)は一通り実施したが、いずれも**ソースファイル自体の列構造**を直接見る手順ではなかったため、最終的にユーザー自身がシートを開いて気づいた。ユーザーは「あなたのデータ確認不足で原因究明に時間がかかりました」と明言 — Power BI側だけでなく、まず自動化が書き込んでいるソースファイルの実際の全列を確認すべきだった。

**How to apply**:
- 既存の本番ファイルに追記/更新するスクリプトを書く、または動かなくなった時にデバッグする際は、まず対象シートの1行目(ヘッダー行)を`openpyxl`等で全列スキャンし、スクリプトが認識している列リストと突き合わせる。認識外の列があれば「なぜ存在するか」「何が依存しているか(この件ではPower BIのDAX)」を先に確認する。
- 「他システム(Power BI、Tableau等)がこのファイルを読んでいる」ケースでは特に要注意 — 見た目の主要列(売上・原価等)が正しくても、その他システムだけが依存する補助列(日付変換用の計算列など)が見落とされやすい。
- こうした隠れ列が見つかったら、該当列だけをピンポイント修正するのではなく、「スキーマ外の列を検出して直前行から複製する」ような汎用的な仕組みにし、かつ複製に失敗したら処理自体を失敗させる(サイレントに壊れたまま「成功」を報告しない)設計にする。[[cas_csv_download_automation]]の`detect_last_header_col`/`shift_formula_row_refs`パターンを参照。
- Power BI側のトラブルシューティング(更新履歴・DAXクエリ・クエリエディタプレビュー等)だけで原因が掴めない場合、早めにソースファイル自体の生の列構造確認に切り替えること。
